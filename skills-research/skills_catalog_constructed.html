What a constructed skills catalog actually looks like

Companion to how harnesses bound their skills catalog, using the same sample and revisions. Rendered out, the seven catalogs fall into two syntax families:

  • Hosts that emit one XML <skill> element per skill
  • Hosts that emit one plain text line per skill

Every host puts a preamble above the list. Most of them name the tool that loads a skill body, though goose’s does not and codex’s is model-gated. Examples were produced by running each host's own formatter or taken from its test fixtures, trimmed to one or two entries.

the XML family

pi is the minimal form; opencode is the same three fields behind a different intro:

The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.
[...]

<available_skills>
  <skill>
    <name>pdf-tools</name>
    <description>Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents.</description>
    <location>C:\skills\pdf-tools\SKILL.md</location>
  </skill>
</available_skills>

fast-agent adds resolved paths for the skill directory and any scripts/, references/, and assets/ subdirectories.

openclaw adds a <version>sha256:9a41cf00e2c1d3b8</version> (first 16 hex chars of the SKILL.md content) so a mid-session edit triggers a re-read, rewrites home paths to ~/, and prepends an imperative ## Skills header above that same preamble: Scan <available_skills>. Clear match: read exact <location> with `read`; obey.

the line-per-skill family

codex wraps markdown bullets in a <skills_instructions> developer message:

<skills_instructions>
## Skills
A skill is a set of instructions provided through a `SKILL.md` source. [...]
### Available skills
- demo: Demo skill. (file: /Users/test/.codex/skills/demo/SKILL.md)
</skills_instructions>

goose is the same idea minus the wrapper and the path, with the description never truncated. Its default loop renders • name - description under ## skills; the state machine behind GOOSE_STATE_MACHINE=1 (off unless set) renders - name: description under its own # Skills heading.

hermes is a hybrid — <available_skills> tags around category-grouped lines, descriptions clipped at 60 characters (the first entry below shows the clip), under a ~400-token preamble that orders the model to err toward loading:

## Skills (mandatory)
Before replying, scan the skills below. If a skill matches or is even partially
relevant to your task, you MUST load it with skill_view(name) [...]

<available_skills>
  devops: DevOps workflows and runbooks
    - deploy-checklist: Pre-deploy verification steps for the staging and product...
    - incident-response: Triage steps for production incidents
  writing:
    - blog-voice: House style for blog posts
</available_skills>

degraded forms

The budgeted hosts keep the same shape as they degrade and say so in the catalog itself.

openclaw protects identities before descriptions: it drops every description, binary-searches the skill count down until that description-free block fits, then spends whatever budget is left on a per-description cap binary-searched between 4 and 220 chars. A catalog that loses entries is prefixed with ⚠️ Skills truncated: included 19 of 40 (compact format, descriptions omitted). Run `openclaw skills check` to audit. One that keeps every skill but degrades the format says so instead: ⚠️ Skills catalog using compact format (descriptions shortened). Run `openclaw skills check` to audit.

codex cuts descriptions mid-string and ends a truncated list with - N additional skills omitted from this bounded skills list. Under budget pressure it also aliases shared path prefixes via a ### Skill roots table, shrinking locators to (file: r0/skill-0/SKILL.md). hermes's clip is always on and its focus mode collapses out-of-context categories to a names-only line while keeping every name visible.
