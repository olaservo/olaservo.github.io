Ola’s MCP Tool Result Research

How strands handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the Strands Agents Python SDK source (clones/strands, checked out at commit 46cbb8c94c93468cd1f06bbb8fff1e6384c9106f (46cbb8c), read on 2026-11-14). Only the Python package in strands-py/ is covered. File references are relative to strands-py/src/strands/ unless they name pyproject.toml or an SDK file. strands-py/pyproject.toml declares "mcp>=1.23.0,<2.4" and there is no lockfile; today that range resolves to the mcp 2.3.0 wheel with mcp-types==2.3.0, and the newest 1.x release is 1.30.0. SDK references are to those two wheels.

Entry: results enter through the SDK ClientSession, typed as CallToolResult, read through a version shim

tools/mcp/mcp_client.py MCPClient._async_background_thread opens mcp.ClientSession directly and negotiates with negotiate_session from tools/mcp/_compat.py. MCPClient._create_call_tool_coroutine sends tools/call through _compat.call_tool, which on 2.x calls session.call_tool(...) inside _drive_input_required to resolve InputRequiredResult rounds. The result type is mcp.types.CallToolResult (MCPCallToolResult). _compat.structured_content reads call_tool_result.structured_content if MCP_V2 else call_tool_result.structuredContent, and MCP_V2 is hasattr(ClientSession, "discover"). MCPAgentTool.stream in tools/mcp/mcp_agent_tool.py calls MCPClient.call_tool_async, which passes the SDK result to _handle_tool_result.

structuredContent survives parsing on both lines: CallToolResult declares structuredContent: dict[str, Any] | None = None in mcp 1.30.0 (mcp/types.py) and structured_content: Any = None in mcp-types 2.3.0 (mcp_types/_types.py). Both declare content: list[ContentBlock] with no default, so a result without a content key fails SDK validation inside session.call_tool. The except Exception in MCPClient.call_tool_async catches that error, and _handle_tool_execution_error turns it into Tool execution failed: <validation error> with status error, so the model sees the validation message and nothing from structuredContent. In mcp 2.3.0 session.call_tool parses the result with _CallToolResultAdapter, a TypeAdapter(types.CallToolResult | types.InputRequiredResult) in mcp/client/session.py, so the message is pydantic’s union error with one failure per arm: CallToolResult.content Field required and InputRequiredResult.resultType Input should be 'input_required'. A {} result fails the same way.

Model path: content only

MCPClient._handle_tool_result maps each call_tool_result.content block through map_mcp_content_to_tool_result_content into the content list of an MCPToolResult (tools/mcp/mcp_types.py), a ToolResult TypedDict with extra keys. The structured value goes on a separate key: if structured_payload is not None: result["structuredContent"] = structured_payload. Result _meta is copied to result["metadata"] and the error flag to result["isError"]. event_loop/event_loop.py appends [{"toolResult": result} for result in tool_results] to the conversation, so the whole dict, extra keys included, sits in agent.messages.

Every provider converter reads only toolResult["content"], and no file under models/ reads structuredContent:

  • models/anthropic.py _format_request_message_content builds tool_result from content["toolResult"]["content"].
  • models/bedrock.py _format_request_message_content builds the Converse toolResult from tool_result.get("content") or [{"text": ""}].
  • models/openai.py format_request_tool_message joins text blocks and returns "content": merged[0]["text"] if merged else "".
  • models/openai_responses.py _format_request_tool_message turns tool_result["content"] into function_call_output parts.
  • models/gemini.py _format_tool_result sets FunctionResponse.response={"output": output} from tool_result["content"], keeping text and JSON blocks in output and sending image and document blocks as FunctionResponse.parts referenced by {"$ref": display_name}.
  • bidi/models/bedrock.py _send_tool_result sends tool_result.content to Nova Sonic and raises ValueError on any block that is not text or JSON. A result for a tool use from an earlier connection goes through _send_tool_result_after_restart as user text, with [non-text content omitted] in place of such a block.

With both fields present, the model receives the mapped content blocks and nothing from structuredContent. With empty content and structuredContent present, content stays [] and the model receives an empty result: an empty string on OpenAI chat, an empty string as function_call_output.output on the Responses API, a single {"text": ""} block on Bedrock, and an empty list on Anthropic.

The answer is the same whether the text mirrors the JSON or differs from it, because no converter compares the two. There is no duplicate-removal step, and structuredContent is not serialized into the request in any form. Non-text blocks do not change which field reaches the model, since structuredContent never does.

Per block, map_mcp_content_to_tool_result_content returns {"text": content.text} for TextContent. ImageContent becomes an image block with "format": MIME_TO_FORMAT[image_mime], and MIME_TO_FORMAT lists only JPEG, PNG, GIF and WebP. Any other image MIME type raises KeyError inside _handle_tool_result, which call_tool_async catches, so the whole call becomes Tool execution failed: '<mime>' with status error. EmbeddedResource with text contents becomes a text block, and a blob becomes text when its MIME type is text/*, a listed JSON/XML/YAML/JavaScript type or a +json/+xml suffix, an image block when the MIME type is in MIME_TO_FORMAT, and is dropped otherwise. AudioContent, ResourceLink and any other type hit self._log_debug_with_thread("unhandled content type: %s - dropping content", ...) and return None.

No file under strands-py/src/ reads audience, and map_mcp_content_to_tool_result_content does not read a block’s annotations (grep for audience under strands-py/src/ returns no hits). A text block annotated audience: ["user"] is mapped like any other text block and reaches the model.

outputSchema: copied onto the ToolSpec, validated by the SDK, surfaced as an error string

MCPAgentTool.tool_spec reads _compat.output_schema(self.mcp_tool) and sets spec["outputSchema"] = {"json": tool_output_schema}. Every provider builds its tool list from name, description and inputSchema only, for example "input_schema": tool_spec["inputSchema"]["json"] in models/anthropic.py. The only other readers are telemetry/tracer.py _construct_tool_definitions, which exports "outputSchema": spec.get("outputSchema") into gen_ai.tool.definitions when OTEL_SEMCONV_STABILITY_OPT_IN contains gen_ai_tool_definitions, and the mcp_router vended tool described below.

Strands does no validation of its own. The SDK validates inside ClientSession.call_tool. In mcp 2.3.0 (mcp/client/session.py) the check is if isinstance(result, types.CallToolResult) and not result.is_error: await self.validate_tool_result(name, result), which raises RuntimeError(f"Tool {name} has an output schema but did not return structured content") or RuntimeError(f"Invalid structured content returned by tool {name}: {error}"). In mcp 1.30.0 the same check is if not result.isError: await self._validate_tool_result(name, result). MCPClient.call_tool_async catches the exception and _handle_tool_execution_error returns MCPToolResult(status="error", content=[{"text": f"Tool execution failed: {str(exception)}"}]). The model sees that sentence and nothing from the original result. On the task-augmented path the create round passes allow_claimed=True and gets either a direct CallToolResult, which the SDK validator checks as above, or a task handle, and for a task handle the final result comes from _resolve_v2_terminal_state (2.x) or get_task_result (1.x), neither of which calls the SDK validator.

Other paths: hooks, direct calls, sessions, conversation managers, telemetry, the MCP router

tools/executors/_executor.py passes the MCPToolResult as result on AfterToolCallEvent (hooks/events.py), so hooks see structuredContent and metadata, and the value they leave in event.result is what is appended to the conversation. A direct call through agent.tool.<name>(...) in tools/_caller.py returns tool_results[0], the full MCPToolResult, to the calling Python code. session/repository_session_manager.py append_message stores the message through SessionMessage.from_message in types/session.py, which keeps the dict as is, so the sidecar keys persist in session storage. agent/conversation_manager/sliding_window_conversation_manager.py rebuilds truncated results with {k: v for k, v in tool_result.items() if k != "content"}, which keeps the sidecar. vended_plugins/context_offloader/plugin.py _handle_tool_result replaces an oversized result with ToolResult(toolUseId=..., status=..., content=new_content), which drops structuredContent, metadata and isError.

In telemetry/tracer.py, end_tool_call_span exports only tool_result.get("content", []). Under the default conventions, _add_event_messages and end_event_loop_cycle_span export serialize(message["content"]), which carries the whole toolResult dict including structuredContent. With gen_ai_latest_experimental set, _map_content_blocks_to_otel_parts exports "response": tool_result["content"] only.

vended_tools/mcp_router/mcp_router.py make_mcp_router builds an opt-in tool that lets the model connect to allowlisted servers at run time. Its list_tools command returns [{**t.tool_spec, "name": t.mcp_tool.name} for t in all_tools], which the @tool decorator serializes with json.dumps in DecoratedFunctionTool._wrap_tool_result, so the model reads each tool’s outputSchema as text. Its call_tool command returns the MCPToolResult from call_tool_async, and _wrap_tool_result passes a dict with status and content through unchanged, so the model again receives content only. vended_tools/python_repl/python_repl.py exposes no tools to the script it runs. There is no MCP Apps handling. Result _meta lands in result["metadata"] and nothing reads it. Request _meta comes from the MCPClient meta argument or the per-call meta, with trace context added by inject_trace_context.

Grep for visibility, ui:// and "ui" under strands-py/src/ returns no hits, so _meta.ui.visibility is not read. No MCPClient.__init__ argument in tools/mcp/mcp_client.py changes what _handle_tool_result puts in content, and _handle_tool_result reads no _meta key or schema to decide it. The model input changes only when an AfterToolCallEvent hook rewrites event.result or a subclass overrides _handle_tool_result or map_mcp_content_to_tool_result_content.

Protocol revision: negotiated by the SDK, chosen by which mcp line is installed

Strands pins no protocol string for ordinary calls. _compat.negotiate_session calls negotiate_auto(session) from mcp.client.client on 2.x, and mcp/client/_probe.py negotiate_auto sends server/discover with LATEST_MODERN_VERSION (“2026-07-28”) and falls back to session.initialize(), which offers LATEST_HANDSHAKE_VERSION (“2025-11-25”) from mcp_types/version.py. On 1.x it calls session.initialize(), which sends protocolVersion=types.LATEST_PROTOCOL_VERSION (“2025-11-25” in mcp 1.30.0). The one fixed value is _TASKS_PROTOCOL_VERSION = "2026-07-28" in tools/mcp/mcp_tasks.py, and MCPClient._require_v2_task_lifecycle raises unless the negotiated session.protocol_version equals it.

Upstream history: #528 put structuredContent beside content to keep it away from the model

The upstream repository is now strands-agents/harness-sdk, and gh api repos/strands-agents/sdk-python redirects there. The MCPToolResult sidecar came from strands-agents/harness-sdk#528, “feat(mcp): retain structured content in the AgentTool response”, merged 2025-07-29. Its body describes an earlier design that appended structuredContent as a json block at the end of content, and the review threads on src/strands/tools/mcp/mcp_client.py replaced it. One reviewer wrote: “I would like to avoid adding this to the tool result content array. MCP currently recommends that if a tool previously returned json in its result as serialized text, it SHOULD continue doing so. By appending the structuredContent to the content array, we are duplicating the number of tokens provided to the model.” The same comment proposed: "Im thinking we extend the ToolResult type with an MCPToolResult, and when we call the bedrock model, we filter out only the required keys needed. This way we can include additional information like structuredContent in the ToolResult, while also not impacting how the model uses it.“ The author had earlier written that ”This comes down to if we view structuredContent as something that is just intended to be used by the user or not“, quoted the spec’s backwards-compatibility SHOULD, and noted ”We could take the opinionated view that if a text block is not present we stringify the json and add it though.“ That option was not implemented. The author’s closing comment: ”the strategy implemented here was to introduce a MCPToolResult. This reduces duplication and allows users to effectively persist the structuredContent to be used not by the agent/llm, but instead by the user via a mechanic like Hooks.“ It adds: ”Unlike other providers, Bedrock throws ValidationExceptions when additional fields are provided in the ToolResultBlock. So, some filtering was needed in the BedrockModel when presented with a toolResult."

At the time of reading, #3431 (open) and #4363 (open) would surface structuredContent in the TypeScript SDK under strands-ts/, which this note does not cover. #4363 describes the Python MCPToolResult.structuredContent and MCPToolResult.metadata as the behaviour it matches. The clone is a depth-1 checkout, so git log and git blame show only 46cbb8c and could not trace when _handle_tool_result switched to the is not None check. Searches of PRs and issues in strands-agents/harness-sdk for structuredContent returned the PRs above, PRs on isError and _meta (#2118, #1237) and the 2.x call_tool port (#4090). A PR search for structured content hit the GitHub search rate limit and was not completed.

Quirks

_handle_tool_result stores any structuredContent that is not None, with the comment that “the 2026-07-28 spec allows any JSON value here, so 0, False, ”“, [], and {} are all valid payloads”. An array, a scalar and {} are therefore kept on the result, while MCPToolResult in tools/mcp/mcp_types.py types the key as dict[str, Any]. A null value leaves the key absent, the same as a missing field.

models/openai.py format_request_tool_message joins text blocks into a string only when the result has no image or document block. Otherwise it keeps a list of parts, and _split_tool_message_images moves the image_url parts into a user message placed after all the tool messages, leaving the tool message with the text parts plus Tool successfully returned an image. The image is being provided in the following user message. models/openai_responses.py _format_request_tool_message keeps the image as an input_image part inside function_call_output.
