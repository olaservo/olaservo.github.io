Ola’s MCP Tool Result Research

How codex handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the codex source (clones/codex, checked out at commit b1573f1, read 2026-11-14). File references are relative to codex-rs/.

Entry: results enter through rmcp 3.5.1 and are copied into a four-field struct that keeps structuredContent

The workspace pins rmcp = { git = "https://github.com/modelcontextprotocol/rust-sdk", rev = "98a54789b80110ad210495c4ad845c89e1980471", version = "=3.5.1", default-features = false } in Cargo.toml. RmcpClient::call_tool in rmcp-client/src/rmcp_client.rs sends ClientRequest::CallToolRequest through call_tool_inner and returns the SDK’s rmcp::model::CallToolResult unchanged via ServerResult::CallToolResult(result) => Ok(Ok(result)). On a 2026-07-28 session the same request goes through call_tool in rmcp-client/src/request_input.rs, which returns the result the same way (ServerResult::CallToolResult(result) => Ok(result)). call_tool_result_from_rmcp in codex-mcp/src/binding.rs copies it into codex_protocol::mcp::CallToolResult (protocol/src/mcp.rs), which holds content: Vec<serde_json::Value>, structured_content: Option<serde_json::Value>, is_error and meta. The copy is field by field, so structuredContent survives as untyped JSON.

The rmcp source at the pinned rev is not in clones/, and crates/rmcp/src/model.rs and crates/rmcp/src/model/annotated.rs were read at that rev through the GitHub contents API. rmcp’s CallToolResult deserializer defaults a missing content to [] when any of structuredContent, isError or _meta is present. A result with none of the four fields does not deserialize as CallToolResult, and both call_tool functions map any other ServerResult variant to ServiceError::UnexpectedResponse. call_tool_result_from_rmcp serializes each ContentBlock with serde_json::to_value, so block annotations, including audience, survive into content as JSON.

Model path: structuredContent replaces content whenever it is non-null, except when an encrypted-content flag is set

CallToolResult::as_function_call_output_payload in protocol/src/models.rs builds the function_call_output body. It first converts content with convert_mcp_content_to_items. If any item is FunctionCallOutputContentItem::EncryptedContent, the content items are returned and structured_content is ignored. Otherwise if let Some(structured_content) = &self.structured_content && !structured_content.is_null() returns FunctionCallOutputBody::Text(serialized_structured_content), the JSON serialized with serde_json::to_string, and nothing from content reaches the model. The test preserves_structured_mcp_content in the same file fixes this with a text block named "ignored". There is no non-empty guard, so a {} payload replaces the content. Only when structured_content is None or Null does the body become FunctionCallOutputBody::ContentItems(content_items).

When both fields are present, the model gets only the serialized structuredContent, whether the text is an exact JSON mirror or differs from it. content: [] with structuredContent gives the same body. The client has no duplicate check, since content does not reach the model when structuredContent is non-null. serde_json::to_string emits compact JSON, which goes out as a plain string body with no envelope other than the Wall time header described below.

McpContent in protocol/src/models/mcp_content.rs declares only text, data and mimeType, and FunctionCallOutputContentItem::from_mcp_content_block reads _meta from the raw block, so annotations is not read on the model path and a block with audience: ["user"] reaches the model like any other block. A grep for audience across codex-rs returns only the Annotations type in the code-mode TypeScript preamble in code-mode-protocol/src/description.rs, unrelated JWT, OAuth, websocket and TUI feedback-disclosure audience code, and test fixtures, including an audience: ["user"] text block in the mcp_output_deferral_items history-deferral fixture in app-server/tests/suite/v2/thread_read.rs. sanitize_mcp_tool_result_for_model in core/src/mcp_tool_call.rs checks only the block type.

Content items map per block type in FunctionCallOutputContentItem::from_mcp_content_block, which convert_mcp_content_to_items calls for each block: text becomes InputText, image becomes InputImage with a data:{mime_type};base64, URL and a detail level read from _meta["codex/imageDetail"], audio becomes InputAudio, and resource, resource_link and malformed blocks become InputText holding the block serialized as JSON (McpContent::ResourceLink { .. } | McpContent::Resource { .. } => Self::InputText { text: serde_json::to_string(block)? }, and from_mcp_content_block(block).unwrap_or_else(|_| FunctionCallOutputContentItem::InputText { text: serde_json::to_string(block)... }) for blocks that fail to deserialize); the malformed branch is unreachable from a live server, because rmcp’s ContentBlock is a closed tagged enum and an unknown type fails deserialization of the whole result. When structuredContent wins, every content block is dropped, images and audio included. Before this conversion, sanitize_mcp_tool_result_for_model in core/src/mcp_tool_call.rs rewrites image blocks into the text <image content omitted because you do not support image input> and audio blocks into <audio content omitted because you do not support audio input> for models whose input_modalities lack them, and leaves structured_content untouched.

Empty content with no structuredContent yields ContentItems(vec![]). On every path, McpToolOutput::response_payload in core/src/tools/context.rs then inserts a Wall time: {wall_time_seconds:.4} seconds\nOutput: header as the first item (or prefixes it to the text body), and calls truncate_function_output_payload with a token budget from the per-tool output_token_limit (config/src/mcp_types.rs) or the model’s truncation_policy. The result goes out as ResponseInputItem::FunctionCallOutput. The second impl, impl ToolOutput for codex_protocol::mcp::CallToolResult in tools/src/tool_output.rs, emits ResponseInputItem::McpToolCallOutput, and core/src/stream_events_utils.rs folds that into a FunctionCallOutput through the same as_function_call_output_payload.

No placeholder text stands in for an empty result. response_payload sets an empty text body to the header alone and inserts the header before an empty item list.

outputSchema: read from tools/list, never validated, rendered into code-mode TypeScript

parse_mcp_tool_with_description_limit in tools/src/mcp_tool.rs copies tool.output_schema into ToolDefinition.output_schema as ToolOutputSchema::from_mcp_output_schema. mcp_call_tool_result_output_schema wraps it as the structuredContent property of a synthetic CallToolResult object schema with content, isError and _meta. ResponsesApiTool.output_schema in tools/src/responses_api.rs carries #[serde(skip)], so the schema never appears in the provider request. No code in core/src/mcp_tool_call.rs, core/src/tools/handlers/mcp.rs, codex-mcp/src or tools/src references a validator; a grep for jsonschema against those paths returns nothing, validate matches only codex-mcp/src code unrelated to results, such as validate_mcp_server_name and validate_tool_call, and Cargo.lock has no jsonschema, boon or valico crate. rmcp at the pinned rev does not validate either: crates/rmcp/Cargo.toml has no schema-validation dependency, and its CallToolResult deserializer in crates/rmcp/src/model.rs checks only that resultType is complete and that at least one known field is present, keeping an explicit null distinct from an absent structuredContent. The only consumer is code mode: collect_code_mode_tool_definitions in tools/src/code_mode.rs passes the schema into CodeModeToolDefinition.output_schema, and render_code_mode_sample_for_definition in code-mode-protocol/src/description.rs unwraps the envelope with mcp_structured_content_schema and renders Promise<CallToolResult<{structured_content_type}>> in the tool declaration prompt text. core/src/tools/code_mode/tool_definitions.rs sets definition.input_schema = None and definition.output_schema = None on every definition after augment_tool_definition has rendered the schemas into the description, so the rendered TypeScript type reaches the model and the raw schema does not.

Since nothing validates structuredContent against the schema, the model sees no validation failure text.

Other paths: code mode gets the whole result, hooks and app-server get both fields, two private _meta keys

Code mode receives the full result. impl ToolOutput for CallToolResult::code_mode_result in tools/src/tool_output.rs serializes the struct to JSON and removes only _meta (fields.remove("_meta")), so sandbox scripts see content, structuredContent and isError together; core/src/tools/code_mode/mod.rs returns it via result.await?.code_mode_result(). PostToolUse hooks receive the same whole struct: McpToolOutput::post_tool_use_response in core/src/tools/context.rs returns serde_json::to_value(&self.result), fed to run_post_tool_use_hooks in core/src/hook_runtime.rs as tool_response. core/src/tools/registry.rs runs them only when success holds, which for an MCP result is is_error != Some(true); a hook that blocks turns the result into FunctionCallError::RespondToModel, and a hook feedback_message wraps the result in PostToolUseFeedbackOutput, whose to_response_item sends the hook text to the model while code_mode_result still returns the original. Extension contributors can mutate the result before the model path through process_mcp_tool_result in core/src/tools/lifecycle.rs, which passes result: &mut CallToolResult to each on_mcp_tool_result. App-server clients get McpServerToolCallResponse and McpToolCallResult in app-server-protocol/src/protocol/v2/mcp.rs, both with structured_content and content. Telemetry reads structured_content.get("error_code") in core/src/mcp_tool_call/telemetry.rs. Review evidence for Node-REPL-backed connectors (on_tool_result_accepted in core/src/tools/handlers/mcp.rs) records content items and inserts structuredContent as text only when no non-blank text block and no encrypted block exists.

The private _meta flag is confirmed. from_mcp_content_block reads meta.get("codex/encryptedContent"); a text block whose _meta["codex/encryptedContent"] is true becomes EncryptedContent { encrypted_content: text }, and that item’s presence is the one condition under which content beats structuredContent. The other key is "codex/imageDetail", which selects the image detail level. Both are read on the model path and in the review evidence above. codex/imageDetail is also read by parse_mcp_media_block in code-mode-runtime/src/runtime/value.rs, through from_mcp_content_block, when a script passes an MCP image block to the image() helper. On the tool-list side, tool_is_model_visible in codex-mcp/src/connection_manager/tool_catalog.rs hides a tool from the model’s declarations when its _meta.ui.visibility array lacks "model"; tools without the key stay visible. prepare_call in codex-mcp/src/binding.rs applies the same filter to calls, and the app-server reports the flag as model_visible.

For MCP Apps, get_mcp_app_resource_uri in core/src/mcp_tool_call.rs reads the tool’s _meta.ui.resourceUri, falling back to _meta["ui/resourceUri"] and _meta["openai/outputTemplate"], and stores it as mcp_app_resource_uri on the McpToolCall turn item. That item’s result carries both content and structured_content to app-server clients (app-server-protocol/src/protocol/v2/item.rs), so the field a view uses is chosen by the app-server client. A grep of tui/src for mcp_app, McpApp and ui:// returns only test files, mcp_approval_meta imports and a ui:// prefix check in tui/src/statusline_provider/descriptor.rs, which picks a statusline resourceUri from a tool’s _meta["openai/ui"].entrypoints for a McpResourceRead request and does not touch tool results, so the TUI does not render a view.

No config key, feature flag or constructor option changes which field reaches the model. A grep for structured in config/src, features/src and core/src/config returns only circuit-breaker error settings, feature-path merging, requirement-override warnings and the apply_patch progress feature comment. The codex/encryptedContent flag and a null value are the only inputs that make content reach the model when structuredContent is present in the result.

Protocol revision: 2025-06-18 by default, 2026-07-28 behind a feature flag

McpProtocolMode in rmcp-client/src/protocol_mode.rs maps Legacy => ProtocolVersion::V_2025_06_18 and V20260728 | DiscoverLocalStdio => ProtocolVersion::V_2026_07_28. Config::mcp_protocol_mode in core/src/config/mod.rs picks V20260728 only when Feature::Mcp20260728 is enabled; features/src/lib.rs registers that feature as key: "mcp_2026_07_28", stage: Stage::UnderDevelopment, default_enabled: false. In the modern mode client_lifecycle returns ClientLifecycleMode::Auto with preferred_versions: vec![V_2026_07_28] and legacy_version: Some(V_2025_06_18). DiscoverLocalStdio uses the same lifecycle for eligible local stdio servers and is selected in codex-mcp/src/connection_manager.rs when Feature::McpConnectionSharing is enabled, registered as key: "mcp_connection_sharing", stage: Stage::UnderDevelopment, default_enabled: false. The hosted Codex Apps server over streamable HTTP takes its mode from host_owned_apps_protocol_mode instead, which core/src/config/mod.rs sets to V20260728 only when Feature::CodexAppsMcp20260728 is enabled, registered as key: "codex_apps_mcp_2026_07_28", stage: Stage::UnderDevelopment, default_enabled: false.

Upstream history: structuredContent preferred since 2025-08, encrypted content exempted in 2026-07

The routing rule came in through openai/codex#2594, “fix: prefer sending MCP structuredContent as the function call response, if available”, by Michael Bolin, merged 2025-08-22. It added convert_call_tool_result_to_function_call_output_payload in codex-rs/core/src/codex.rs with the same non-null guard and the prefers_structured_content_when_present test with the "ignored" text block. The PR body: "Though reading https://modelcontextprotocol.io/specification/2025-06-18/schema#tool, it appears that if outputSchema is specified, then structuredContent should be set, which seems to be a “higher-fidelity” response to the function call. This PR updates our handling of CallToolResult to prefer using the JSON-serialization of structuredContent, if present, using content as a fallback." Before it, the client sent the JSON-serialized content array and dropped structuredContent. #33509, merged 2026-07-16, added the codex/encryptedContent exemption, and its body says it makes the client "Prefer the content-item payload whenever encrypted content is present so that structured_content does not replace the encrypted output."

Issue #10334, "Codex drops MCP tool content[] blocks when structuredContent is present“, opened 2026-02-01, is open. A contributor, etraut-openai, replied: ”We previously included both structuredContent and content to the model, but we received a bug report asking us to change this behavior. It was pointed out that other tools like Claude Code ignore content if structuredContent is provided.“ and ”So the current behavior in Codex is by design." The linked comment on #9251 is about the results codex mcp-server returns, which #9192 had given a structuredContent holding only threadId, and #9338 fixed by putting threadId in both fields. Open issues #38287 and #45637 report the same routing from the user side. The clone is shallow (one commit), so git log and git blame do not reach these changes. Searched: gh search prs for structured_content, structuredContent and structuredContent null, and gh search issues for structuredContent, all in openai/codex.

Quirks

Arrays, strings, numbers and booleans in structuredContent take the same path as objects, so a string value reaches the model as a quoted JSON string (as_function_call_output_payload in protocol/src/models.rs). isError sets only the payload’s success flag, and the text comes from whichever field wins. truncate_mcp_tool_result in utils/output-truncation/src/lib.rs replaces an oversized result with one text block holding a preview of the serialized result and sets structured_content: None; for a non-error result with no structuredContent or _meta whose blocks all pass plain_output_text (protocol/src/mcp.rs), the preview is of Truncated tool output: followed by the block texts instead. It is applied to the McpToolCall event result at DEFAULT_OUTPUT_BYTES_CAP (truncate_mcp_tool_result_for_event in core/src/mcp_tool_call.rs) and to persisted rollout items at 64 KiB (PERSISTED_MCP_RESULT_MAX_BYTES in rollout/src/policy.rs), and not to the model payload.

An empty {} result, which rmcp fails to deserialize, reaches the model as an error result. PreparedMcpCall::call_with_preparation in codex-mcp/src/binding.rs adds the context tool call failed for {server}/{tool_name} , handle_mcp_tool_call in core/src/mcp_tool_call.rs formats the error as tool call error: {error:?}, and CallToolResult::from_error_text in protocol/src/models.rs wraps that string in one text block with structured_content: None and is_error: Some(true). The model gets the Wall time header and a text item ending in Caused by:\n Unexpected response type.

thread/items/list in the app-server accepts an experimental deferOutput.mcpToolCall option. defer_item_output in app-server/src/request_processors/thread_processor.rs clears result.content and sets output_deferred on a completed MCP call item with no error, no mcp_app_resource_uri, no mcp_app_ui, no app-context resource URI and a server other than codex_app, when is_deferrable_mcp_result holds: it returns false if result.structured_content.is_some() || result.meta.is_some(), and otherwise requires every block to pass plain_output_text with at least one non-empty text. plain_output_text accepts only a block with exactly the type and text keys whose text does not start with {, [, or ~~~. Results carrying structuredContent` are therefore always listed inline. This affects only app-server history listing, not the model payload.
