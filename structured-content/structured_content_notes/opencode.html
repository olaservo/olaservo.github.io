Ola’s MCP Tool Result Research

How opencode handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the opencode source (clones/opencode, checked out at commit d759c54, read 2026-11-14). File references are relative to the clone root.

Entry: results enter through @modelcontextprotocol/client 2.4.0 and keep structuredContent as structured

packages/core/package.json depends on @modelcontextprotocol/client and @modelcontextprotocol/core at 2.4.0. The root package.json applies patches/@modelcontextprotocol%2Fclient@2.4.0.patch, which changes OAuth code and leaves tools/list entries unchecked (tools: z.array(z.unknown())), with outputSchema on the SDK’s tool schema loosened to z.looseObject({ $schema: z.string().optional() }). packages/core/src/mcp/client.ts constructs the SDK Client inside initialize and calls client.callTool(...). The SDK result type SdkCallToolResult is converted at once by toCallToolResult into opencode’s own CallToolResult, whose fields are isError, structured?: unknown and content: ReadonlyArray<CallToolContent>. The line structured: result.structuredContent, carries the structured payload across. CallToolContent has two variants, text and media (base64 data plus mimeType, and uri for an embedded resource). The SDK 2.4.0 bundle was read from the npm tarball (dist/src-CeKsbNLO.mjs of @modelcontextprotocol/client@2.4.0). Its tools/call result schema for the legacy revision, CallToolResultWireSchema, runs normalizeContentlessToolResult, which gives a result with no content key content: [] unless it carries task, inputRequests or requestState, so a result without content reaches toCallToolResult as an empty array. On the 2026-07-28 revision the tools/call wire schema is CallToolResultSchema$1 built by wireResult, with content: z.array(ContentBlockSchema$1) required and no such normalization, so a result without content fails with Invalid result for tools/call: ... and becomes a ToolFailure as described under Quirks. toCallToolResult copies structuredContent unchanged whatever its type, and drops each block’s annotations and _meta.

Model path: content blocks go to the model, structured is dropped before persistence

This path is reached directly only for servers configured codemode: false, or for every server when the execute permission is wholly denied. packages/core/src/tool.ts splits the active tools into direct (tool.options?.codemode === false, or all active tools when execute is wholly denied) and codeModeTools (codemode !== false), and the model’s tool definitions are direct plus the single Code Mode execute tool when it is enabled; a name that is not in direct and is not execute is rejected with No tool named "<name>" is currently available. With the default configuration every MCP tool is therefore called from inside an execute script, and the conversation receives the script’s return value as described under Other paths. The same McpTool execute runs in both cases.

packages/core/src/tool/mcp.ts registers every discovered MCP tool through editor.add in the McpTool layer. Its execute first turns isError into a ToolFailure whose message is the joined text blocks. For a success it maps result.content to Tool.Content: text stays text and, through toContent, a media part whose MIME is in ReadToolFileSystem.MEDIA_MIMES (PNG, JPEG, GIF, WebP, PDF) becomes { type: "file", uri: "data:<mime>;base64,<data>", mime }, a textual MIME becomes a text block headed [Resource <label> (<mime>)], and anything else, audio included, is saved through ToolOutput and becomes a text block [Binary resource <label> (<mime>, <n> bytes) saved to <file>]. The output() helper then picks the structured value: if (result.structured !== undefined) return result.structured, else null for empty text, else the text, parsed with JSON.parse when the server declared no outputSchema and the text starts with { or [. The return is { output: output(), ...(content.length === 0 ? {} : { content }) }.

packages/core/src/tool/runtime.ts execute then calls normalizeContent(result.content, output), which returns the content array when it is non-empty and otherwise [{ type: "text", text: stringify(output) }]. So when both fields arrive, the model receives the content blocks and structuredContent goes only into output. When content is empty and structuredContent is present, or when only structuredContent arrives, JSON.stringify(structuredContent) becomes the single text block. packages/core/src/session/runner/publish-llm-event.ts toolExecution publishes SessionEvent.Tool.Success with content and metadata only, and packages/schema/src/session-message.ts ToolStateCompleted has no output field, so the structured value is not persisted. packages/core/src/session/runner/to-llm-message.ts toolResult builds the provider part from tool.state.content: a single text block becomes { type: "text", value }, anything else { type: "content", value: content }. Text-only providers flatten the latter with toolResultText in packages/ai/src/protocols/shared.ts, which is encodeJson(part.result.value). No code compares the text with structuredContent, so a text block that mirrors the JSON reaches the model once, as sent, and a text block that differs from it reaches the model in the same way. For a success with no content blocks and no structuredContent, output() returns null and normalizeContent sends the text null. For an isError result with no text blocks, the ToolFailure message is MCP tool returned an error.

Non-text blocks are mapped in toCallToolResult in packages/core/src/mcp/client.ts: image and audio become media; resource_link becomes a text block holding the uri; an embedded resource becomes text when it has text, media when it has blob and mimeType, and otherwise a text block holding its uri. Any other block type is dropped by the final return []. packages/core/src/tool.ts normalizeImages resizes image files through the Image service and replaces undecodable or oversize ones with a short omission note. packages/core/src/session/model-request.ts unsupportedMedia swaps a file the model cannot take for an ERROR: Cannot read ... text, and boundImages drops the oldest images past a byte target. packages/core/src/session/recent-text.ts applies truncateToolOutput only to the recent, verbatim part of a summary compaction, and packages/core/src/session/compaction.ts applies clip only to the compaction transcript.

annotations.audience is not read on the model path. toCallToolResult builds CallToolContent without annotations, and a grep for audience under packages/core/src, packages/schema/src, packages/ai/src and packages/codemode/src finds only an OAuth audience in packages/core/src/plugin/provider/chatgpt.ts. A text block annotated audience: ["user"] therefore reaches the model like any other text block, and its text is also part of the joined text that Code Mode receives when structuredContent is absent.

outputSchema: not validated, used only for the Code Mode signature

packages/core/src/mcp/client.ts lists tools with cacheMode: "bypass", keeps outputSchema only when it is a record, and passes the listed entry as toolDefinition on every client.callTool, or a stub for a tool it has not listed, in both cases with outputSchema: undefined set over it. The SDK’s Client.callTool compiles the definition’s outputSchema through _compileOutputValidator (published bundle dist/public-CvV4ZHkX.mjs of @modelcontextprotocol/client@2.4.0, not vendored in the clone), which returns undefined when outputSchema is absent, so the SDK’s checks (Tool ${params.name} has an output schema but did not return structured content and Structured content does not match the tool's output schema: ...) never run. The comment above toolDefinition gives the reason: "Leaving out outputSchema skips the SDK’s output check: servers return results that miss or break their own schema (Zoom answers a 204 with nothing), and failing the call would report a completed action as failed." mcp/index.ts does not reference outputSchema, so no client code validates structuredContent against it. A result that misses or breaks the declared schema is returned as the server sent it; with no structuredContent, output() in packages/core/src/tool/mcp.ts falls back to the text, unparsed because the tool declares a schema, or null.

packages/core/src/tool/mcp.ts passes output: (tool.outputSchema ?? {}) into the tool registry. packages/core/src/tool/runtime.ts encodeOutput treats a JSON Schema output only with Schema.decodeUnknownEffect(Schema.Json), a JSON-ness check. definition copies the schema into ToolDefinition.outputSchema, and no adapter under packages/ai/src/protocols reads that field, so it reaches no provider request and no prompt text on the conversational path.

Other paths: Code Mode is the default route and consumes structured directly

Every MCP server defaults to Code Mode (codemode is an optional boolean on LocalConfig and RemoteConfig in packages/schema/src/mcp.ts, annotated “Defaults to true” with no schema default; tool/mcp.ts sets codemode: tool.codemode !== false). packages/core/src/codemode/tool.ts create exposes one execute tool that runs model-written JavaScript; its executeTool callback returns executed.output when defined, so the sandbox receives the raw structuredContent (or the parsed JSON text), and falls back to joined text, with file parts collected into files. The model then sees formatResult's pretty-printed JSON of whatever the script returned, which is persisted as the execute tool’s text content. When the execute permission is wholly denied, codeModeEnabled is false in packages/core/src/tool.ts and the Code Mode tools are exposed as direct tools, so no execute tool exists and each MCP tool follows the Model path. inventoryTools builds each sandbox stub with output: child.outputSchema ?? Schema.NullOr(Schema.String), and packages/codemode/src/tool-schema.ts outputTypeScript renders a JSON Schema output with jsonSchemaToTypeScript into the Promise<...> signature shown in the catalog; decodeOutput returns a JSON Schema value unchanged, so Code Mode does no validation of its own. packages/core/src/mcp/client.ts appends ?codemode=false to remote URLs unless rejectsUnknownQuery matches, and packages/core/src/plugin/mcp-codemode-defaults.ts sets codemode: false for executor.sh remote servers and for local servers whose command is executor mcp.

Other routing: packages/core/src/tool.ts executeTool passes { output, content, metadata } to tool.execute.after plugin hooks, which can rewrite both; normalizeContent has already run once inside runtime.execute, so the hook sees the JSON fallback block when content was empty, and tool.ts normalizes again afterwards. The only _meta use on tools/call is outbound, _meta: { "ai.opencode/sessionID": input.sessionID } in mcp/client.ts, which also copies each listed tool’s _meta into its Tool record, a copy no code reads. No code under packages/core/src or packages/schema/src reads result _meta, ui:// resources or an MCP Apps output template. The built-in Parallel web search plugin, packages/core/src/plugin/websearch/parallel.ts, calls a fixed MCP endpoint over its own HTTP helper and reads result?.structuredContent.results only; it does not apply to configured servers. The claude-agent provider plugin hands opencode tools to Claude Code through its own MCP server, and convert in packages/core/src/plugin/provider/claude-agent/tools/result.ts builds that result from the provider tool result as { content, isError }, with no structuredContent.

Protocol revision: legacy initialize by default, 2026-07-28 by config

packages/schema/src/mcp.ts Protocol is Schema.Literals(["legacy", "auto", "2026-07-28"]). negotiation in packages/core/src/mcp/client.ts returns undefined for legacy or an absent setting, { mode: "auto" } for auto, and { mode: { pin: protocol } } otherwise, passed as versionNegotiation to the SDK Client. The SDK’s legacy list SUPPORTED_PROTOCOL_VERSIONS begins with LATEST_PROTOCOL_VERSION = "2025-11-25" and its modern list is ["2026-07-28"].

Upstream history: the V1 routing PRs, the maintainer’s position, and the V2 JSON-text parse

The clone is shallow (one commit, d759c54), so git log and git blame do not reach the commits that introduced the current code. The routing pull requests and issues found on GitHub all concern the V1 file packages/opencode/src/mcp/catalog.ts, which is not in the clone. anomalyco/opencode#32074, merged 2026-06-12 and closing issue #27263 (a Qt Creator server that sends content: [] with structuredContent), made V1 "prefer non-null MCP structuredContent over unstructured content“ and ”serialize structured results as compact JSON text for the model“, and its body says ”This matches Codex behavior". Issue #32832 then reported an image dropped when structuredContent was also present. The maintainer closed it on 2026-06-22 with: “This isn’t a bug because the MCP spec does not require clients to merge content with structuredContent or preserve both in model context; preferring the stringified structuredContent is valid. It also matches the behavior of Claude Code and Codex, so preserving images alongside it would be unexpected”. #34505, “fix(mcp): prefer content over structured output”, merged 2026-06-29, reversed the V1 order: “Preserve MCP content when structuredContent is also returned” and “Only fall back to structuredContent when content is empty”. Its body records no rationale beyond those lines.

Issue #38923 reported that a summary in content hid the data in structuredContent, and #43123 proposed appending the compact JSON after the existing content. The PR was closed unmerged on 2026-09-17 by an automated cleanup of PRs older than a month with fewer than two positive reactions. The issue was closed as not planned on 2026-10-22 with: "This was traced to V1 code (packages/opencode/src/mcp/catalog.ts), which isn’t part of OpenCode 2.0. V1 now only gets critical fixes, and this isn’t one. If you’d like this in OpenCode 2.0, please open a new issue for 2.0."

For the V2 code in packages/core, #48357, merged 2026-09-10, added the JSON-text parse in output() in packages/core/src/tool/mcp.ts, with the rationale “Agents assume JSON returned as text is already an object, so parse it for them.” Its body states the scope: "output is in-process only: the persisted tool state (ToolStateCompleted) has content, not output, and the model, TUI, and history all read content, which is unchanged. Only code mode programs see the parsed value.“ #48937, merged 2026-09-14, reworked the MCP client for SDK v2 and the 2026-07-28 revision and does not discuss field routing. #61254, ”fix(core): don’t fail MCP tool calls whose results break their output schema", merged 2026-11-08, removed outputSchema from the toolDefinition passed to the SDK. Its body cites Zoom tools that declare an empty-object schema but return no structuredContent after a 204, and a tool whose structuredContent uses an enum value its schema leaves out, both of which had failed calls that succeeded on the server; it says "Listed tools keep outputSchema, which still types results for Code Mode." No PR or issue was found that records why V2 normalizeContent sends content and falls back to the stringified output. Searches run: gh search prs and gh search issues in anomalyco/opencode for structuredContent, MCP structured, code mode MCP output, normalizeContent, McpTool and (merged PRs) output schema mcp, and the comment threads and timelines of #27263, #32074, #32832, #32867, #32868, #34505, #38923 and #43123.

Quirks

In the SDK 2.4.0 legacy-revision schema, CallToolResultSchema$1 declares structuredContent: z.record(z.string(), z.unknown()).optional(), so an array, scalar or null structuredContent fails result validation and the call rejects with Invalid result for tools/call: .... callTool in packages/core/src/mcp/index.ts wraps it as ToolCallError with the message MCP tool "<name>" on server "<server>" failed: ... (on client for a client-attached server), and packages/core/src/tool/mcp.ts turns that into a ToolFailure with the same message. The 2026-07-28 schema declares structuredContent: z.unknown().optional() and passes such values through (dist/src-CeKsbNLO.mjs). Both revisions' ContentBlockSchema$1 is a union of the five known block types, so an unknown block type fails the whole result before the return [] in toCallToolResult is reached. On the model path stringify in packages/core/src/tool/runtime.ts returns a string structuredContent as the bare string, without JSON quoting. isError text comes from content text blocks only, and structuredContent on an error result is not used. On the Model path a ToolFailure becomes the session error { type: "tool.execution", message } (toSessionError in packages/core/src/session/to-session-error.ts), and toolResult in packages/core/src/session/runner/to-llm-message.ts sends it as an error result with the value { error: tool.state.error, content: tool.state.content ?? [] }. Text providers encode that with toolResultText as JSON, so the model receives {"error":{"type":"tool.execution","message":"<text>"},"content":[]}. packages/cli/src/acp/content.ts contentBlockToParts reads audience on ACP prompt blocks sent by an editor, marking an ["assistant"] block synthetic and a ["user"] block ignored. That code handles user prompts and does not see MCP tool results.
