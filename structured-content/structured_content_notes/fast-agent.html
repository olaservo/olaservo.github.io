Ola’s MCP Tool Result Research

How fast-agent handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the fast-agent source (clones/fast-agent, checked out at commit c551658, read on 2026-11-12). File references are relative to src/fast_agent/ unless they name pyproject.toml or an SDK file. SDK references are to the mcp and mcp-types 2.3.0 wheels, which pyproject.toml pins as "mcp==2.3.0" and "mcp-types==2.3.0".

Entry: results enter through the SDK Client, typed as mcp_types.CallToolResult, with structured_content kept

mcp/client_connection.py defines MCPClientConnection, which constructs mcp.client.Client in __init__ and delegates call_tool to self.client.call_tool(...) inside _interactive_operation. The result type is mcp_types.CallToolResult (mcp_types/_types.py), whose fields are content: list[ContentBlock], structured_content: Any = None, is_error: bool = False and result_type. The wire key structuredContent lands in structured_content, documented as “Any JSON value on 2026-07-28; restricted to a JSON object on 2025-06-18 and 2025-11-25”. mcp/mcp_aggregator.py MCPAggregator.call_tool reaches the connection through _execute_on_server(method_name="call_tool", ...) and _execute_session_method. agents/mcp_agent.py McpAgent.call_tool sends exec_sandbox to _call_ptc_tool when programmatic tool calling is enabled and everything else to _dispatch_tool_call, which tries _call_local_tool first (filesystem, shell, skill and builtin runtimes) and otherwise calls self._aggregator.call_tool.

content has no default on mcp_types.CallToolResult, so on a 2026-07-28 session a result without the content key fails result_type.validate_python(raw, by_name=False) in ClientSession.send_request (mcp/client/session.py). InputRequiredResult, the other arm of _CallToolResultAdapter, rejects it too, because its validator requires input_requests or request_state. The check before it, _methods.validate_server_result(method, version, raw), validates against the revision’s wire type from SERVER_RESULTS in mcp_types/methods.py. On 2025-11-25 that type is CallToolResult from mcp_types/_v2025_11_25, which also requires content, so the result fails there with an error naming CallToolResult alone. On 2026-07-28 it is CallToolResult | InputRequiredResult from mcp_types/_v2026_07_28, whose InputRequiredResult has optional input_requests and request_state and no validator, so a result carrying resultType passes and fails at result_type.validate_python. MCPClientConnection._interactive_operation re-handles only MCPError, so the pydantic validation error reaches the generic except Exception branch of MCPAggregator._execute_on_server, and the model receives the Failed to call_tool '{tool}' on server '{server}': {exc} text described under outputSchema.

Model path: structuredContent replaces every text block and keeps non-text blocks

mcp/helpers/content_helpers.py canonicalize_tool_result_content_for_llm is the single model-facing view. When structured_content is None it returns content unchanged. Otherwise it drops every text block, serializes the structured value with json.dumps(structured_content, ensure_ascii=False, sort_keys=True, separators=(",", ":")), and returns [text_content(structured_text), *non_text_blocks]. The check is is None, so {} or [] also replaces the text. With both fields present the model receives the compact JSON plus any image, audio or resource blocks and none of the server’s text. With empty content and a structured value, or with only structuredContent, the model receives the one JSON text block. A warning is logged only when a logger is passed and there are more than one text block; the Anthropic, OpenAI chat and OpenAI Responses converters pass a logger, the Google and Bedrock converters do not.

Every provider converter starts from that list. llm/provider/anthropic/multipart_converter_anthropic.py handles TextContent, ImageContent, EmbeddedResource and ResourceLink; AudioContent matches no branch and is dropped, and an unsupported image MIME type becomes the text Image with unsupported format '...'. llm/provider/openai/multipart_converter_openai.py convert_tool_result_to_openai puts text in the tool message and non-text blocks in a separate user message, with audio rendered by _convert_audio_content as [Unsupported audio content: {mime}]. llm/provider/openai/responses_content.py _tool_result_item_to_part sends images and resources as attachment parts and anything else as [Unsupported content: {type}]. llm/provider/google/google_converter.py _google_tool_result_item_part returns None, None for audio, so it is dropped. llm/provider/bedrock/multipart_converter_bedrock.py keeps only TextContent from the canonical list. Empty canonical content becomes [No content in tool result] (Anthropic, Bedrock) or [Tool completed successfully] (OpenAI chat), and an empty-string output in the Responses converter. Before any converter, _sanitize_call_tool_result in mcp/client_connection.py replaces a ResourceLink with a file: URI with the text [Local file attachment from a remote MCP server was blocked.], which the canonical function then drops like any other text block when structuredContent is present. agents/llm_decorator.py _prepare_llm_call also runs _sanitize_messages_for_llm on the outgoing messages, and _filter_block_list removes from each tool result’s content every non-text block that _block_supported rejects through model_info.supports_mime. A model name with no ModelDatabase entry gets the text-only default from ModelInfo.from_name (llm/model_info.py, tokenizes=["text/plain"]), so for such a model images, audio and blob resources are removed before the converters, and when every block of a result is removed the text [{category} content was removed - {model} does not support this content type] takes their place.

Before conversion, agents/mcp_agent.py _prepare_planned_tool_result runs bound_tool_result_for_llm (mcp/tool_result_truncation.py) on every non-shell result, except that a read_text_file call to the local filesystem runtime (no namespaced MCP tool) first tries page_read_text_file_result, which, for a non-error result with no structured_content and a single text block over the limit, keeps whole lines and appends a [File read truncated: showing lines ...] notice. bound_tool_result_for_llm measures the canonical text in UTF-8 bytes against _model_tool_output_byte_limit(), which defaults to DEFAULT_TERMINAL_OUTPUT_BYTE_LIMIT = 16_000 in constants.py through ShellSettings.output_byte_limit; setting that to None selects "auto", and the limit becomes calculate_terminal_output_limit_for_max_tokens(max_output_tokens) from llm/terminal_output_limits.py, floored at 16,000. Over the limit it returns result.model_copy(update={"content": content, "structured_content": None}) where content is a head-plus-tail text block from truncate_text_output followed by the blocks for which get_text returns None; ResourceLink and text EmbeddedResource blocks have text, so they are folded into the truncated text, and images, audio and blob resources survive as blocks. The retain callback runs spool_tool_result (mcp/tool_result_spool.py), which writes the structured value as indented JSON to a transient .json file when it fits in TOOL_RESULT_ARTIFACT_MAX_BYTES (32 MiB) and otherwise writes the text version; the returned notice (“The complete {tool} result is available during this session at {path}...”) becomes the guidance inside the truncation marker. McpAgent._temporary_artifact_environment returns None unless the shell runtime is enabled and no external runtime is set, so with the shell off (for example --no-shell) nothing is spooled and the marker carries _TOOL_RESULT_TRUNCATION_GUIDANCE, “Use a narrower query or request a smaller result to retain the relevant content.”

A grep for audience under src/fast_agent/ returns only _convert_annotations in acp/content_conversion.py, which copies the audience of ACP prompt blocks into MCP annotations on user input. Neither canonicalize_tool_result_content_for_llm nor any provider converter reads annotations. A ["user"] text block reaches the model when structured_content is None and is dropped with the other text blocks when it is set. A ["user"] image or resource block reaches the model in both cases, subject to the per-provider handling above.

outputSchema: parsed by the SDK, validated by the SDK, surfaced to the model as an error and, under programmatic tool calling, as a stub return shape

mcp_types.Tool.output_schema is populated from tools/list by the SDK, and ClientSession.list_tools caches it in _tool_output_schemas (mcp/client/session.py). ClientSession.call_tool calls validate_tool_result when not result.is_error; Client.call_tool (mcp/client/client.py) revalidates claimed results on the same condition. validate_tool_result re-lists tools if the name is not cached, raises RuntimeError(f"Tool {name} has an output schema but did not return structured content") when the field is absent, and raises RuntimeError(f"Invalid structured content returned by tool {name}: {error}") on a jsonschema mismatch. fast-agent calls Client.call_tool, so the validation runs. MCPAggregator._execute_on_server catches the exception in its generic except Exception branch and _handle_session_method_error returns the error_factory result, CallToolResult(is_error=True, content=[TextContent(type="text", text=msg)]), where msg is Failed to call_tool '{tool}' on server '{server}': {exc}. The model sees that sentence and nothing from the original result. Outside programmatic tool calling, fast-agent itself never reads output_schema on the model path; the other reader is commands/renderers/tools_markdown.py render_tool_schema_markdown, which prints a ## Structured output schema section for the tool-schema slash command. Local tools register with output_schema=None (tools/function_tool_loader.py, mcp/server/harness_adapter.py).

A grep for output_schema and outputSchema under src/fast_agent/ returns no hits outside ptc/ and the three files above. The provider tool declarations are built field by field from tool.input_schema (llm/provider/anthropic/llm_anthropic.py, llm/provider/openai/llm_openai.py, llm/provider/google/google_converter.py, llm/provider/bedrock/llm_bedrock.py), so the output schema is not in the tool declaration or the description.

Other paths: ACP forwards content blocks, MCP Apps metadata affects listing and display

acp/tool_progress.py on_tool_complete builds the ACP tool_call_update from _convert_mcp_content_to_tool_content(content), and MCPAggregator._notify_tool_complete passes result.content if result.content else None, so the ACP client receives the raw content blocks and never the structured value. mcp/app_integrations/ reads _meta.ui.resourceUri (or ui/resourceUri) and _meta.ui.visibility from tool definitions; MCPAggregator.list_tools skips a tool when discovered_tool.is_app_only, so a tool declared with visibility exactly ["app"] never reaches the model. extract_app_tool_metadata returns None when neither ui.resourceUri nor the OpenAI Apps SDK resource URI is set, so a tool with visibility: ["app"] and no resource URI is not hidden. On results, ui/tool_display.py _resolve_app_integration_result_details renders the structured value in the terminal under an app resource: {uri} label and _has_structured_text_content_mismatch compares parsed text blocks against it; neither affects the model path. mcp/tool_result_metadata.py writes fast_agent/display, fast_agent/fatal_tool_error, fast_agent/url_elicitation_required and fast_agent/media_preview_content into result _meta for display and control. config.py MCPServerSettings.management = "provider" delegates MCP execution to the model provider, and results on that route never pass through fast-agent.

fast-agent hosts no MCP App view. mcp/app_integrations/ defines the text/html;profile=mcp-app and text/html+skybridge MIME constants, and a grep under src/fast_agent/ for iframe, postMessage and ui/notifications finds no view host, so no view receives either field.

agents/tool_runner.py ToolRunnerHooks has before_tool_call and after_tool_call hook points, set per agent through tool_hooks (agents/agent_types.py) and loaded from module.py:function_name specs by tools/hook_loader.py. after_tool_call receives the PromptMessageExtended returned by run_tools, whose tool_results hold the CallToolResult objects stored by _store_planned_tool_result after _prepare_planned_tool_result, so a hook sees structured_content unless truncation set it to None. The runner stages that same message for the next LLM call (_ensure_tool_response_staged), so a hook that edits content or structured_content in place changes what the converters canonicalize. The ToolRunnerHooks docstring calls the hooks “intentionally low-level and mutation-friendly”. An exception in after_tool_call is logged as “Tool hook failed after tool call” and the tool message is kept.

plugins/tool_call_review.py defines a plugin tool_call_review hook, declared in a schema_version: 3 plugin manifest. ToolAgent.run_tools (agents/tool_agent.py) and McpAgent._run_mcp_tools call _review_planned_tool_calls before any call in the assistant message runs. A reviewer receives a PluginToolCallReviewContext holding the agent instruction, the tool declarations, the history, the request and the pending calls, and no tool result. It returns denied call ids mapped to text, and _record_tool_error_result stores CallToolResult(content=[text_content(error_message)], is_error=True) as each denied call’s result, so the model receives that text and the tool never runs. A reviewer that fails to load, raises or returns something other than a mapping or None denies every pending call with a Tool call blocked: ... message. Calls made from programmatic tool calling sandbox code go through _call_ptc_nested_tool to _dispatch_tool_call and are not reviewed.

canonicalize_tool_result_content_for_llm takes only the result, a logger and a source label. No _meta key, server setting, agent option or schema changes which field the model gets on the MCP path. The routes that change it are programmatic tool calling, where the model gets the exec_sandbox result, and management = "provider", where fast-agent does not see the result.

Programmatic tool calling: on by default for some models, scripts receive the structured value

config.py ProgrammaticToolCallingSettings.enabled defaults to None, “null uses the model default”, and is “Local POSIX only”. agents/mcp_agent.py _ptc_selection takes --ptc/--no-ptc first, then ResolvedModelSpec.resolve_ptc_enabled (llm/resolved_model.py) applies the ptc model-string query, then ptc.enabled, then the catalog’s ModelParameters.ptc_enabled (llm/model_database.py), which defaults to False and is True for gpt-6-astra, gpt-6.1-sol, gpt-6.1-terra, gpt-6-luna, kimi-k3.1-pro (also through Hugging Face) and glm-5.3-flash. _ptc_enabled_for checks _ptc_environment_supported, which is false for non-POSIX hosts and for ACP-owned, remote, Docker or custom environments; there it raises when the choice was explicit and leaves PTC off when it came from the model default. When it is on, ptc/runtime.py ProgrammaticToolRuntime.model_tools replaces the agent’s tools with one tool, exec_sandbox, plus any tool matched by ptc.direct_tools or declaring expose: "direct" or "both" under _meta.fast_agent.ptc and not matched by ptc.nested_tools. The model writes Python that runs in a pydantic-monty sandbox where each remaining tool is an async function. _call_ptc_nested_tool sends those calls through _dispatch_tool_call, so MCP results take the same aggregator and SDK validation path, and a tool hidden by is_app_only is not a sandbox function either.

ptc/values.py tool_result_to_value builds what the script receives. A fast-agent-ptc-value key in result _meta is returned first, even for an error result; the shell, attach_media and subagent tools set it, and the key is read from any result with no check on its source. Any other error result raises ToolCallFailed, a RuntimeError, carrying the fast-agent-ptc-error _meta string when it is a string and otherwise the error text. When structured_content is not None, text blocks are dropped and the script gets the raw value, or {"structured_content": ..., "content": [...]} when non-text blocks are present. Without a structured value each block is converted: text starting with { or [ is parsed as JSON and otherwise stays a string, images, audio and blob resources become {"media_id": ...} handles, and a ResourceLink becomes a dict. One block is returned bare, several as a list, none as None.

The model receives only the exec_sandbox result. _success builds CallToolResult(content=[*content, *media]) with one text block holding the status line, the printed output and the final value through render_value, plus the media whose handles appear in the final value. That result has no structured_content, so canonicalize_tool_result_content_for_llm returns it as is, and bound_tool_result_for_llm caps it like any other result. Nested results do not pass through _prepare_planned_tool_result, so the script sees them untruncated.

ptc/stubs.py _build_function takes output_schema from _meta.fast_agent.ptc.returns or else tool.output_schema. The stub then declares -> dict[str, Any] in place of -> Any and _returns_shape adds a compact Returns: line to the docstring. Those stubs appear in the exec_sandbox description, and with ptc.type_check (default True) Monty type-checks the code against them before it runs.

Protocol revision: negotiated by the SDK, selectable per server through protocol_mode

No protocol string is pinned in fast-agent. MCPClientConnection.__init__ passes mode=sdk_connect_mode(protocol_mode), where protocol_mode comes from MCPServerSettings.protocol_mode or MCPDefaultsSettings.protocol_mode in config.py and defaults to "auto". In auto the SDK’s negotiate_auto (mcp/client/_probe.py) sends server/discover with LATEST_MODERN_VERSION (“2026-07-28”) and falls back to initialize() offering LATEST_HANDSHAKE_VERSION (“2025-11-25”). "modern" uses _ForcedModernClient, which sends session.send_discover(LATEST_MODERN_VERSION) and raises on failure. "legacy" runs the handshake only. The registry is KNOWN_PROTOCOL_VERSIONS in mcp_types/version.py.

Upstream history: a display PR that became the model-path rule

canonicalize_tool_result_content_for_llm came in through evalstate/fast-agent#703, merged 2026-04-09, in commit 8b47458 (“update structured content handling, with plan”). That commit also edited the Anthropic, OpenAI chat, OpenAI Responses, Google and Bedrock converters and llm/internal/passthrough.py to call it. The PR was opened by iqdoctor as a terminal-preview change, with the body “No MCP contract change. This is display-only.” Its stated basis: "So for clients, structuredContent is the canonical structured payload; content is the compatibility mirror.“ The maintainer, evalstate, added the model-path change and commented: ”fast-agent was using the text content block. I’ve updated the handling with what I think is most appropriate; and run the prompt for the plan."

The same commit added plan/03-07-structured-handling.md, which is not in the tree at c551658. The plan names the mismatch it addresses: “the user sees one payload in the tool result panel” and “the model reasons over a different payload”. Its reason for the rule: "the presence of structuredContent is a strong signal that the structured payload is the authoritative result“ and ”using divergent text as canonical input is the riskier default“. It lists the cost: ”if a tool intentionally included useful narrative explanation in text blocks, that prose will no longer be the primary text passed to the model“. On the serialization: ”compact JSON is cheaper for model input than indented JSON“, ”ensure_ascii=False preserves readable Unicode“ and ”sort_keys=True improves determinism in tests and logs“. On the warning: ”semantic comparison would require parsing arbitrary text and would likely be noisy and brittle“. The docstring at c551658 keeps the reasoning: ”MCP intends content text and structuredContent to agree semantically, but that invariant is not enforced in practice." #990, merged 2026-09-30, added spool_tool_result, and its body says structured content "is retained as indented JSON (.json) so line ranges and grep are useful".

The clone is shallow with one commit, so git log and git blame do not reach these changes. gh search prs for “structuredContent”, “structured_content”, “canonicalize”, “structured content” and “canonical tool result”, and gh search issues for “structured content”, “structuredContent”, “outputSchema” and “audience”, found no other PR or issue about the rule.

Quirks

canonicalize_tool_result_content_for_llm does not check is_error, and the converters call it on every result (for example llm/provider/anthropic/multipart_converter_anthropic.py), so an error result that carries structured_content reaches the model as the JSON with its error text dropped.

A non-object structuredContent depends on the revision. On 2025-11-25 the wire CallToolResult in mcp_types/_v2025_11_25 declares structured_content: dict[str, Any] | None, so _methods.validate_server_result rejects a string or array and the model receives the Failed to call_tool ... text in place of the whole result. On 2026-07-28 the field is Any, and canonicalize_tool_result_content_for_llm serializes a string as a quoted JSON string.
