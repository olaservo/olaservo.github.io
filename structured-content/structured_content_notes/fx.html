Ola’s MCP Tool Result Research

How fx handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the fx source (clones/fx, checked out at commit 3fd4905, read 2026-11-14). File references are relative to the clone root. fx has two client paths. The native engine (src/mcp/, connected through src/core/mcp_host/) is the default, and it serves the terminal app, fx ask, and ACP editors. The JavaScript library libfx does not own an MCP connection: sdk/mcp.js createMcpAdapter wraps a client the host supplies.

Entry: a hand-written Zig client that keeps three fields and drops _meta

fx has its own MCP client and no MCP SDK dependency. Server.callAnswer in src/mcp/server.zig passes the decoded response to classifyCall in src/mcp/protocol/tools.zig, which reads three raw JSON slices:

wire.objectFields(result.raw, &.{ "content", "structuredContent", "isError" }, &found) catch return .invalid;
const content = found[0] orelse return .invalid;

The result type is Call.result, struct { content: []const u8, structured: ?[]const u8, is_error: bool }, with the comment "structured is passed on unvalidated". Result _meta and any other key stop here. A result with no content key, or a content that is not an array, is .invalid. copyCall in src/core/mcp_host/runtime.zig turns that into .ended (“An answer that isn’t a result ended the call”), and ended in src/core/mcp_host/model.zig gives the model a failure text beginning MCP server '<name>' ended the call:. So a structuredContent-only result without a content key does not reach the model.

Catalog.callTool in src/core/mcp_host/model.zig calls render, which writes the three fields back into a JSON-RPC response and passes it to tool_result.extract in src/core/mcp/tool_result.zig. extract calls parseCallOutcome in src/core/mcp/features/tools.zig, which validates each content block. An unknown block type or a malformed annotation fails the whole result, and the model gets MCP protocol failure: InvalidContent.

build.zig.zon lists no dependencies and gives fx version 0.0.0. sdk/package.json (libfx 0.0.0) has no dependencies field. No MCP SDK source was read because neither path uses one.

Model path: the whole result is stringified inside a server and tool envelope

extract projects media out of content and hands the entire parsed result to serialize_capped. write_envelope in src/core/mcp/tool_result.zig then writes the text the model receives:

try writer.writeAll("{\"server\":");
try std.json.Stringify.value(server_name, .{}, writer);
try writer.writeAll(",\"tool\":");
try std.json.Stringify.value(tool_name, .{}, writer);
try writer.writeAll(",\"result\":");
try writeJsonProjection(alloc, writer, result, false);

With both fields present the model receives {"server":…,"tool":…,"result":{"content":[…],"structuredContent":…,"isError":false}} as one string. Text blocks stay as block objects with their annotations and _meta. No code compares the text mirror to the structured value. With content empty the same envelope arrives with "content":[] beside structuredContent. writeJsonProjection replaces any string holding a NUL byte or invalid UTF-8 with binary or non-utf8 tool output omitted (<n> bytes), inside structuredContent too. An isError result keeps the same envelope and its structuredContent, and tool_mcp_registry.call returns it as .failure. Text that differs from the JSON arrives the same way, with both copies in the envelope. writeJsonProjection writes compact JSON with no whitespace and keeps object keys in parsed order, so structuredContent is a JSON value inside the envelope string. No placeholder replaces an empty result. extract sends {"content":[]} through write_envelope like any other result, so the model receives "result":{"content":[]}, and a test in src/core/mcp/tool_result.zig checks that its status is success.

Size changes the answer. resultBytes in src/core/tooling/tool_mcp_registry.zig asks for up to stored_text_max_bytes (8 MiB) when a session store exists. prepareManaged and prepare in src/core/session/result_store.zig store the envelope when it exceeds large_result_threshold_bytes (16 KiB) or the inline cap (default_max_tool_result_bytes, 64 KiB), and the model receives the first preview_bytes (4 KiB) of it inside <tool_result_preview> with a handle for read_tool_result. content is written first, so with a text mirror over 4 KiB the preview holds no structuredContent. Without a store (fx ask --no-save runs without one, "Unsaved (--no-save, or no store)" in src/core/cli/cli_ask.zig), or past 8 MiB with one, serialize_capped cuts to the requested size using collect_result_text, which follows only the keys text, data, blob and content:

if (std.mem.eql(u8, entry.key_ptr.*, "text") or
    std.mem.eql(u8, entry.key_ptr.*, "data") or
    std.mem.eql(u8, entry.key_ptr.*, "blob") or
    std.mem.eql(u8, entry.key_ptr.*, "content"))

structuredContent is not followed on this branch. An oversize result with content empty becomes an envelope whose only text is the marker ... [mcp tool result truncated for <server>/<tool>: original <n> bytes; cap is <m> bytes], built by build_truncated_envelope. Embedded resource text sits under the resource key and is also not collected.

Non-text blocks: parseToolImages in src/core/images/image_data.zig lifts image blocks and image/ embedded blobs (png, jpeg, gif, webp) into CallResult.images. projectMediaForText in src/core/tooling/tool_content.zig then removes data and blob from the JSON and adds a delivery field: image content, unsupported media; content was not sent to the model, or binary resource content was not sent to the model. Audio therefore reaches the model as a block with no data. resource_link blocks and embedded text resources stay in the envelope as JSON. tool_mcp_registry.call returns .rich when images exist.

The provider request carries the envelope as the tool message text on every backend. src/gateway/vercel_protocol.zig write_tool_result_part writes {"type":"tool-result",…,"output":{"type":"text","value":<envelope>}}, or error-text on failure, for the default Vercel gateway. src/gateway/chat_completions_protocol.zig write_request writes {"role":"tool","content":<envelope>,"tool_call_id":…} for custom providers whose protocol is openai-chat-completions, one of the three accepted protocols with openai-responses and anthropic-messages (src/core/config/configured_provider.zig). src/gateway/responses_protocol.zig writes function_call_output with the envelope as output for Codex, Grok and openai-responses custom providers (src/gateway/configured_responses.zig). write_tool_result in src/gateway/anthropic_messages_protocol.zig writes {"type":"tool_result","tool_use_id":…,"content":<envelope>}, with "is_error":true on failure, for anthropic-messages custom providers, and src/gateway/configured_transport.zig adds anthropic-version for them. Other Claude models go through the gateway. Backends differ only in image placement: the gateway and chat completions send images in a follow-up user message (write_tool_image_user_message, write_tool_image_follow_up), Responses puts input_image parts in the output array, and Anthropic Messages puts image blocks after a text block holding the envelope in content. src/core/images/image_route.zig withholds images from a model the catalog lists without vision.

JS adapter: text and compact JSON joined, unless they are byte-identical

libfx apps pass an MCP client to createMcpAdapter, and sdk/package.json declares no MCP SDK dependency. Each tool’s execute calls client.callTool and then resultText:

function resultText(result) {
  const text = contentText(result?.content);
  if (result?.structuredContent !== undefined) {
    const structured = JSON.stringify(result.structuredContent);
    return text && text !== structured ? `${text}\n${structured}` : structured;
  }
  return text;
}

With both fields present the model receives the joined text, a newline, and compact JSON. The structured copy is the only one sent when the joined text equals JSON.stringify(structuredContent) exactly, so a pretty-printed mirror or one with reordered keys produces two copies. With content empty the model receives the compact JSON. There is no envelope. contentText keeps text blocks and embedded text resources and renders resource_link as <name>: <uri>. Audio and non-image blobs become an empty string with no note. Images go into a libfx.tool-result object, which hostToolContent in sdk/engine.js and parseRichResult in src/core/tooling/tool_content.zig turn into the same typed images the native path uses. An isError result throws an Error whose message is resultText, and sdk/engine.js uses that message as the tool content. Result _meta is not read. A successful result with no text and no structuredContent returns an empty string, and no placeholder replaces it in sdk/mcp.js, executeHostTool in sdk/engine.js, or the host tool reader in src/acp/prompt.zig. An isError result with empty text gets the message MCP tool <name> failed from sdk/mcp.js, and sdk/engine.js substitutes Tool <name> failed without a message for any empty error content (“Providers reject an empty error result, which would end the session.”).

outputSchema: stored and hashed, never checked

parseCallOutcome receives the schema and discards it:

_ = output_schema_json; // Tool semantics, including output assertions, belong to the server.

render does not pass one to extract anyway, so a mismatch has no effect and the result goes to the model unchanged. The test MCP tool call results preserve content types errors and server output in src/core/mcp/features/tools.zig pins a structuredContent string against {"type":"array"}. tests/tla/mcp/rules.md lists CAT-07 | SHOULD | Validate structuredContent against outputSchema, and the code does not do it.

The schema is used in two places. parseTool runs prepareSchema(output_schema, false), which requires an object and, when $schema is present, draft 2020-12 or draft-07, and Catalog.build in src/core/mcp_host/model.zig leaves out a tool that fails (“MCP tool left out”). digestTools in src/core/mcp/catalog_state.zig hashes it, so a changed schema changes definition_digest, and callTool returns McpAdvertisedToolChanged for a binding made against the old definition. It is not sent to a provider: buildToolSchemaJsonWithLimitMarker in src/core/mcp/selected_schema.zig passes only tool.input_schema_json.

sdk/mcp.js copies name, description and inputSchema from each listed tool and does not read outputSchema. Any validation there belongs to the client the host supplies, and a throw from client.callTool becomes the error text of the tool result in sdk/engine.js.

Other paths: fx mcp call prints only the data, and the deferred route ends at the same call

fx has no code mode, but a model-written shell command can call MCP tools. Verb in src/core/mcp_host/verbs.zig is list, show, add, remove, login, logout, approve, reject, call, and fx mcp call TOOL [JSON | -] (src/core/mcp_host/mcp_call_client.zig) works only inside a command that fx’s shell tool runs, on Linux and macOS (supported in src/core/tooling/mcp_call_capability.zig). On those platforms the toolbox menu in src/core/tooling/toolbox.zig (mcp_call_hint), when it lists an MCP server, tells the model: “When an MCP tool’s result would be large or needs filtering, run it from a shell command instead: fx mcp call TOOL_NAME '' > FILE. Only what the command prints returns to you.” src/tools/shell/shell.zig registers each shell call with the bridge in src/core/mcp_host/mcp_call_bridge.zig, and callBridgeTool in src/core/tooling/tool_runtime.zig runs the call through the same callTool, render and extract with a 16 MiB cap (max_result_bytes) instead of the model’s cap. The bridge runs over a Unix socket and meets the same permission check as a direct call (authorizeBridgeCall in src/core/tooling/tool_runtime.zig). bridgeResultData then takes the envelope apart:

/// Just the data of an MCP result envelope: its structured content as JSON
/// when it has some, otherwise its text content.

So the script receives compact structuredContent and a newline, and no text when both fields are present. A structuredContent that is an object holding only a result string (wrappedResultText, “how some servers, FastMCP’s among them, wrap a tool that returns text”) prints as that string. A test pins {"content":[{"type":"text","text":"ignored"}],"structuredContent":{"issues":[1,2]}} to {"issues":[1,2]}. With no structuredContent, or structuredContent: null, the script gets the text of each content block, one per line, and with no text either it gets the whole result object as compact JSON. Images and other media have already lost their data to projectMediaForText. A .tool_failure result goes through the same extraction, is written to stderr after fx mcp call: <tool> returned an error:, and exits 6. A protocol failure passes its model text through and exits 1. When stdout is not a terminal, shapeSummary writes one stderr line such as wrote <n> bytes of JSON: <shape>. The model sees only what the command prints, under the shell tool’s own output handling. fx mcp call help TOOL prints the name, description and inputSchema arguments (writeHelp in src/core/mcp/tool_lookup.zig) and does not read outputSchema.

Deferred tools: MCP servers are listed in the toolbox menu and their tools are kept out of the tools list. The model calls toolbox (src/tools/capabilities/toolbox.zig) with open, search or run, and a direct call of an unsent name gets notSelectedOutput from src/core/tooling/tool_mcp_runtime.zig. toolboxRunSubject in src/core/agent/runtime/orchestrator.zig turns a run into the agent’s own direct call of the tool, so it goes through tool_mcp_registry.call and the same callTool, and the result goes back under the toolbox call (carried_by).

Subagents use the same path. childToolContext in src/core/app/app_agent_runtime.zig copies the parent context, and src/core/subagent/agent_adapter.zig scopes it with mcp_access.

Hooks: HookKind in src/core/hooks/definitions.zig is pre_tool_use, stop, post_turn_end, attention_required, so no native hook runs on a tool result. libfx hooks receive tool.end and tool.result events with an output string (sdk/types/libfx.d.cts) and mcp.start, mcp.request and mcp.end events with identity and status (sdk/tool-observation.js). sdk/README.md describes these as observation, and callback results are not awaited.

ACP: an editor receives text, not the fields. toolUpdateContentText in src/acp/tool_call_presentation.zig clips most output to a 200-byte prefix of the same model text, so an editor sees the start of the envelope. src/acp/mcp_servers.zig parses servers an editor supplies into the same native host.

MCP Apps: no file under src/ or sdk/*.js mentions ui://, ui/resourceUri or MCP Apps, and nothing renders structuredContent.

audience and _meta: validated, then passed to the model as text

audience appears only in validateAnnotations in src/core/mcp/features/tools.zig, which requires an array of at most two values from user and assistant. A bad value fails the whole result with InvalidContent. A valid ["user"] block still reaches the model, with the annotation visible in the envelope. sdk/mcp.js does not read annotations.

No _meta key changes routing. Result-level _meta is dropped in classifyCall. Block-level _meta is size-checked and stays in the envelope. Tool-level _meta is stored as metadata_json, which has no read site except the digestTools hash, so _meta.ui.visibility has no effect and an app-only tool stays selectable by the model. The only _meta fx writes on a call is libfx/correlationId in sdk/mcp.js, when propagateCorrelation is true.

No other switch changes which field the model gets. The per-server Server struct in src/core/mcp_host/config.zig holds transport, auth and loading fields and none that touch the result. createMcpAdapter reads only the options prefix, serverName, propagateCorrelation, resources and prompts. The max_tool_result_bytes setting read in src/core/config/config_runtime.zig replaces default_max_tool_result_bytes for every tool, so it moves the size thresholds described under the model path.

Protocol revision: 2026-07-28 first, three 2025 revisions as fallback

Config in src/mcp/core/era.zig sets preferred = {"2026-07-28"} and legacy = {"2025-11-25", "2025-06-18", "2025-03-26"}. writeDiscover probes with server/discover, and writeInitialize offers config.legacy[0]. classifyInitialize accepts a version from either list and returns .other for anything else, including 2024-11-05. render passes .protocol = .modern to extract in every era, and classifyCall is shared, so result handling does not vary by revision. On the JS path the revision belongs to the host’s client.

The repo holds no MCP server that affects this path. src/core/mcp_host/fake_server.zig and the tests/e2e/fixtures/mcp-* files are test fixtures.

Upstream history: the envelope dates from the initial commit, and an open PR would keep only structuredContent

The clone is shallow with one commit, so git log and git blame there do not reach the history. The commit lists below come from gh api repos/vercel-labs/fx/commits?path=... and the file contents at each commit.

write_envelope is in src/core/mcp/tool_result.zig at 439f83c, the “Initial commit” of 2026-08-11, which has no PR and no message beyond its title. None of the ten later commits touching the file has a title about which field is sent. vercel-labs/fx#825, merged 2026-09-12, changed what the envelope carries by removing secret masking from the model path: “Tool results, tool arguments, and saved session history now reach the model verbatim (still encoding-sanitized and capped).”

resultText in sdk/mcp.js came in through #544 (“Build the libfx agent kernel”), merged 2026-09-02, where it returned the content text when there was any and JSON.stringify(structuredContent) only when there was none. #639 (“Rebuild MCP handling around independent servers”), merged 2026-09-05, changed it to the current join. The PR body’s only line on this is “Preserve typed images, structured results, cancellation, and saved history across native and SDK execution.” Neither PR has comments or reviews that discuss the rule.

#609 (“fix(mcp): prefer structured tool results”), opened 2026-09-03 by vrmiguel and still open with no comments or reviews, changes src/core/mcp/tool_result.zig to keep only structuredContent when both fields are present. Its rationale: “For MCPs that contain both forms, this duplicates the tool response, using more input tokens than it needed.” and "This PR makes it so that if the MCP server returned both forms, it’ll prefer keeping only structuredContent. Truncation is then applied only to the selected representation." It cites Codex and OpenCode’s code mode as doing the same.

#1516 (“Add fx mcp call to run MCP tools from shell commands”), opened 2026-10-29 and merged 2026-11-02, added the script route. Its body says it prints “only the tool’s data, so the command can save a large result to a file or filter it before anything reaches the model”, and lists "Print structured content that is only a result string, as FastMCP servers such as DeepWiki wrap a tool’s text, as that text, so a saved file holds the document rather than a JSON wrapper.“ It also lists ”Return results whole instead of cutting them at the model’s 64 KiB limit".

Searched: gh search prs and gh search issues in vercel-labs/fx for structuredContent, write_envelope, resultText, structured content, tool result envelope, duplicate tool result, outputSchema and MCP tool result; gh pr view on #544, #609, #639, #825 and #1516; and the commit lists for src/core/mcp/tool_result.zig and sdk/mcp.js. Quirks

Non-object structuredContent passes on the native path: tests in src/mcp/protocol/tools.zig and src/core/mcp/features/tools.zig accept [1,2] and the string "server result". In sdk/mcp.js, structuredContent: null is not undefined, so the model receives the text null, or the content text followed by null. bridgeResultData treats null as absent and prints the content text, and unwraps a lone {"result":"…"} string, so fx mcp call and the model path give different answers for the same result.

libfx does not truncate an oversize result. When the resultText string is longer than the session’s max_tool_result_bytes (64 KiB by default in src/acp/server.zig), the host tool reader in src/acp/prompt.zig replaces the whole result, text and structuredContent alike, with the failure text Host tool result exceeded the configured limit. The WebAssembly build gives the same text from src/core/hosts/js_host_tools.zig, where sdk/wasm-runtime.js refuses a non-image result over the smaller of that setting and a 64 KiB bridge cap.
