Ola’s MCP Tool Result Research

Notes checklist

which mcp tool result fields are used and how (clients)

Every client note answers each core item below. An answer can be “not read” or “not found”, stated with the search that showed it, for example "No file under src/ reads audience (grep returns only the generated schema)". Silence is not an answer. Answers go in the section of the note they belong to: Entry, Model path, outputSchema, Other paths, or Upstream history.

Quirks are recorded when a read turns them up. Nobody checks every client for them. They go in a ## Quirks section at the end of the note, so a page can list them without implying the other clients were checked. Quirk text already written elsewhere in a note stays where it is.

Core: every note

Entry

  1. The client library and version: SDK or hand-rolled, the pinned version, and where the SDK source was read.
  2. Whether structuredContent survives parsing, and what happens when the content key is missing.

Model path

  1. Both fields present, with the text an exact JSON mirror of structuredContent.
  2. Both fields present, with text that differs from the JSON.
  3. content: [] with structuredContent.
  4. Whether the client removes the duplicate when the text mirrors the JSON.
  5. The form structuredContent takes in the request: compact JSON, pretty JSON, a JSON value, or inside an envelope.
  6. Any placeholder substituted for an empty result.
  7. Whether non-text blocks (image, audio, resource) change which field wins, and whether they survive when structuredContent wins.

audience

  1. Whether annotations.audience is read on the model path, and whether a ["user"] block reaches the model.

outputSchema

  1. Whether it is validated, by whom, and the text the model sees on failure.
  2. Whether the schema reaches the model, through the tool declaration, the description, or code-mode types.

Other consumers

  1. Code mode or scripts: what the script receives.
  2. MCP Apps: which field the view gets, and whether _meta.ui.visibility is honoured.
  3. Hooks and plugins: what they see, and whether they can change what the model gets.
  4. Any switch that changes which field the model gets: a _meta key, per-server config, a constructor option, or the schema.

Upstream history

  1. The upstream PRs, issues or commits behind the routing rule, with any rationale they record. If none were found, say so and list what was searched.

Quirks: record when found

  • Non-object structuredContent (array, scalar, null) handled differently from an object.
  • {} treated differently from a missing field.
  • Unknown block types failing the whole result.
  • An answer that differs by provider backend.
  • Size caps or truncation that drop or reorder one of the fields.
  • Which field isError text comes from.
  • The client attaching its own audience label, or reading audience only on display paths.
  • The per-type rendering of non-text blocks, when it does not decide which field reaches the model.
  • ACP, editor and TUI output, history and replay, and telemetry.
  • The protocol revision, when it changes what structuredContent may contain.
