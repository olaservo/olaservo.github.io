Ola’s MCP Tool Result Research

How cline handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the cline source (clones/cline, checked out at commit 72b3d71, read 2026-11-13). File references are relative to the repository root. The repo is a monorepo: sdk/packages/core holds the agent runtime and the MCP extension, apps/vscode holds the VS Code extension, and apps/cli holds the CLI. Both apps run tool calls through the core runtime.

Entry: results enter as unknown through three clients, two of them SDK-backed

The lockfile resolves @modelcontextprotocol/sdk to 1.30.0 (bun.lock, "@modelcontextprotocol/sdk@1.30.0"); sdk/packages/core/package.json asks for ^1.29.0 and apps/vscode/package.json for ^1.25.1. Three client classes produce results. StdioMcpClient in sdk/packages/core/src/extensions/mcp/client.ts is a hand-rolled JSON-RPC client over stdio; its callTool returns this.request("tools/call", ...) with no schema parse. SdkUrlMcpClient in the same file wraps the SDK Client for SSE and streamable HTTP and calls client.callTool(...). createDefaultMcpServerClientFactory picks between them by registration.transport.type === "stdio". The VS Code extension uses its own McpHub (apps/vscode/src/services/mcp/McpHub.ts), whose callTool calls connection.client.request({ method: "tools/call", ... }, CallToolResultSchema, ...) and returns { ...result, content: result.content ?? [] }. The two core clients satisfy McpServerClient.callTool, whose return type is export type McpToolCallResult = unknown; (sdk/packages/core/src/extensions/mcp/types.ts); McpHub.callTool has its own signature and is adapted into the runtime by McpHubToolProvider.callTool in apps/vscode/src/sdk/vscode-runtime-builder.ts, which implements McpToolProvider. No client type names structuredContent; the identifier appears in no non-test source file. The field survives because the stdio client returns the raw JSON-RPC result, the SDK’s CallToolResultSchema declares structuredContent as optional on a loose object, and McpHub.callTool spreads the parsed result even though its declared return type McpToolCallResponse (apps/vscode/src/shared/mcp.ts) lists only _meta, content, and isError.

Model path: the whole envelope, JSON-stringified into one text block

createMcpTools in sdk/packages/core/src/extensions/mcp/tools.ts registers each MCP tool with execute: async (input, context) => options.provider.callTool(...), so the tool’s output is the entire result object. Before each model request the orchestrator’s beforeModel hook (createRuntimeHooks in sdk/packages/core/src/runtime/orchestration/session-runtime-orchestrator.ts) runs prepareMessagesForModelRequest, which converts agent messages through agentMessagesToMessages and back. That conversion passes every tool-result part through toPersistedToolResultContent (sdk/packages/core/src/session/persisted-tool-result-content.ts), which returns strings and arrays as-is and otherwise returns JSON.stringify(output). An MCP result is an object, so it becomes a JSON string. On the way back, toolResultContentToAgentPart in sdk/packages/core/src/runtime/config/agent-message-codec.ts sets output: block.content, now a string. The provider formatter toAiSdkToolResultOutput (sdk/packages/shared/src/llms/ai-sdk-format.ts) takes its first branch, typeof output === "string", and emits { type: "text", value: ... }.

The model therefore receives one text block containing the serialized CallToolResult: content, structuredContent, isError, and _meta together, with text blocks still nested as {"type":"text","text":...}. When both fields are present, both are in that string. When content is [] and structuredContent is present, the string carries "content":[] and the structured object; nothing substitutes a placeholder. A result with only structuredContent and no content key arrives the same way from the stdio client; the SDK and McpHub paths add content: []. An empty result {} reaches the model as {} from the stdio client and as {"content":[]} from the SDK path. Image, audio, and resource blocks are stringified with their base64 payloads intact. The image-hoisting code in toAiSdkToolResultOutput (isAiSdkContentBlockArray, stripImagesFromOutput) never runs on the MCP path because the output is already a string by the time the formatter sees it; it also keys on mediaType, which MCP blocks do not carry. JSON.stringify(output) in toPersistedToolResultContent takes no indent argument, so the envelope is compact JSON and structuredContent is a nested value under its own key. No step compares the content text with structuredContent, so a text block that mirrors the JSON reaches the model beside it in the same string.

No source file under sdk or apps, tests included, reads audience: a grep over *.ts, *.tsx and *.js returns only the banner targeting field in apps/vscode/src/shared/ClineBanner.ts, and annotations appears only in a comment in apps/cli/src/utils/helpers.ts. A block annotated audience: ["user"] reaches the model inside the stringified envelope with its annotations object intact.

MCP tools carry resultPolicy: "cache-oversized". MessageBuilder (sdk/packages/core/src/session/services/message-builder.ts) truncates the string past DEFAULT_MAX_TOOL_RESULT_CHARS = 8_000 with truncateMiddle, which inserts ...[truncated ${n} chars]... (TRUNCATE_MARKER_DEFAULT), and appends Full result is temporarily saved to ${recovery.uri}. Only read_files can access this cache URI. Use read_files with specific line ranges if omitted content is needed. The URI is cline://cache/<session>/<id>.result.txt (ToolResultCache.store in sdk/packages/core/src/session/services/tool-result-cache.ts). Past that limit the output changes shape: the single string becomes a content array of text parts, the middle-truncated JSON followed by the recovery notice, which isAiSdkContentBlockArray then sends as a content-type output. Providers in the openai-compatible family use the openai-chat protocol (inferProtocol in sdk/packages/llms/src/providers/builtins.ts), and createOpenAICompatible in sdk/packages/llms/src/providers/vendors/openai-compatible.ts does not set supportsMultiPartToolContent, so @ai-sdk/openai-compatible 3.0.67 sends a content output as JSON.stringify(output.value). On that protocol the tool message is a JSON array of text parts, with the truncated envelope JSON-encoded a second time inside the first part. The cached full copy is YAML from prepareToolResultRecovery (sdk/packages/core/src/session/services/tool-result-cache.ts), whose splitToolResultMedia does recognize mimeType on image blocks and replaces them with [image attached].

outputSchema: never read by client code; only the SDK HTTP path validates

outputSchema appears in no non-test source file. Every tools/list mapper rebuilds descriptors from name, description, inputSchema, and _meta: StdioMcpClient.listTools and SdkUrlMcpClient.listTools in client.ts, and McpHubToolProvider.listTools in apps/vscode/src/sdk/vscode-runtime-builder.ts. The SDK’s own validation runs only where client code calls Client.listTools and Client.callTool, which is SdkUrlMcpClient. In SDK 1.30.0 (src/client/index.ts, read from the published tag), listTools calls cacheToolMetadata, which fills _cachedToolOutputValidators; callTool then throws Tool ${params.name} has an output schema but did not return structured content when the field is absent and isError is false, and Structured content does not match the tool's output schema: ... on a mismatch. SdkUrlMcpClient.callTool catches that in handleOperationError, records it via markConnectionError, and rethrows new Error(message). McpHub calls client.request(...) directly for both tools/list and tools/call, so its validator cache is never filled and no validation occurs. The stdio client has no validator. outputSchema is not used in prompt text; defaultMcpDescription in tools.ts uses only description. The SDK throws these as McpError, whose constructor prefixes MCP error ${code}: (SDK 1.30.0 src/types.ts). executePreparedTool in sdk/packages/agents/src/agent-runtime.ts catches the rethrown error and records { error: message } with isError: true. That object is stringified like any other output, and toAiSdkToolResultOutput sends it as error-text, so the model sees {"error":"MCP error -32602: Structured content does not match the tool's output schema: ..."} or {"error":"MCP error -32600: Tool <name> has an output schema but did not return structured content"}.

Other paths: display extractors, hooks, ACP, and a dormant MCP Apps gate

Display paths read the object before it is stringified. extractToolOutputText in apps/vscode/src/sdk/message-translator.ts feeds the webview’s mcp_server_response row and falls back to JSON.stringify(output) for objects, so the webview shows the whole envelope. The CLI’s extractFullOutputText (apps/cli/src/tui/utils/tool-parsing.ts) joins content[].text and resource.text, prints image, audio and resource blobs as labelled base64, labels resource_link blocks, and falls back to pretty JSON whenever no parts come out, including content: [] (its test uses { structuredContent: { ok: true } }). The tool_result hook payload (runtimeToolRecord in sdk/packages/core/src/hooks/subprocess.ts, and the CLI’s apps/cli/src/utils/hooks.ts) sets output: ctx.result.output, the raw object. The VS Code extension excludes core’s file-hook extension (configExtensions filter in apps/vscode/src/sdk/vscode-session-host.ts) and runs its own adapter, apps/vscode/src/sdk/hooks-adapter.ts, whose postToolUse.result is String(ctx.result.output ?? "") (string result = 3; in apps/vscode/proto/cline/hooks.proto), so an MCP result object reaches VS Code hooks as the literal string [object Object]. The ACP agent sends rawOutput: e.error ?? e.output (apps/cli/src/acp/session-updates.ts). The subprocess tool_result hook, the file hook in sdk/packages/core/src/hooks/hook-file-hooks.ts, and the VS Code PostToolUse adapter return only stop control and appendContext, so they cannot change the result. Plugin extensions (sdk/packages/core/src/extensions/plugin/) register AgentRuntimeHooks, and an afterTool hook there may return result (AgentAfterToolResult in sdk/packages/shared/src/agent.ts). executePreparedTool in sdk/packages/agents/src/agent-runtime.ts replaces the tool result with it, and that replacement is what gets stringified for the model. A beforeModel hook may also return messages, which createRuntimeHooks puts into the request.

No code-mode or script path calls MCP tools. A case-insensitive grep for code mode, codemode, execute_code and run_code over sdk and apps matches only model and provider names: the Claude Code model helpers in sdk/packages/llms/src/providers/builtins.ts, the CommandCode and OpenCode descriptions in sdk/packages/llms/src/providers/providers.generated.ts, the Claude Code and VS Code LM provider settings in apps/vscode/webview-ui/src/components/settings/providers/, and a Claude Code model test in apps/vscode/src/sdk/model-catalog/store.test.ts.

sdk/packages/core/src/extensions/mcp/apps.ts defines an MCP Apps extension (MCP_APPS_EXTENSION_ID = "io.modelcontextprotocol/ui"). createMcpTools filters descriptors with isMcpToolVisibleToModel, which hides a tool when _meta.ui.visibility lacks "model". The client capability is advertised only when mcpApps is true in DefaultMcpServerClientFactoryOptions, which loadConfiguredMcpTools in sdk/packages/core/src/runtime/orchestration/runtime-builder.ts fills from the session config’s mcpApps (CoreRuntimeFeatures), and no non-test code in sdk or apps sets it to true. A session with it on gets a callMcpAppTool host method (sdk/packages/core/src/runtime/host/local-runtime-host.ts, backed by createMcpAppsRuntime in sdk/packages/core/src/extensions/mcp/session-apps.ts), which rejects tools failing isMcpToolVisibleToApp and returns the raw result to the host without adding it to the conversation. No _meta key on results changes routing. The only per-server knob touching results is timeout (McpServerRegistration.timeoutSeconds).

Protocol revision: 2024-11-05 on stdio, SDK default elsewhere

StdioMcpClient.connect sends protocolVersion: MCP_PROTOCOL_VERSION with const MCP_PROTOCOL_VERSION = "2024-11-05"; (client.ts). SdkUrlMcpClient and McpHub construct new Client(...) without a version override, so the SDK sends its LATEST_PROTOCOL_VERSION = '2025-11-25'.

Upstream history: no recorded rationale for the whole-envelope return or the stringify

The clone is shallow and git log reaches only 72b3d71, so the history was read through gh api commit listings by path. The SDK history in cline/cline begins at 78aedcde8 (“feat: agents, core, cli, llms sdk packages”, 2026-03-02), a commit with no parent. Its sdk/agents/src/tools/formatting.ts already has formatToolResult, whose doc comment reads “The result is serialized to a string (JSON for objects, string for primitives)”. createMcpTools arrived in 4738e8294 (“chore: clean up scripts and shared”, 2026-03-04) as sdk/packages/agents/src/mcp/tools.ts, with the same execute returning options.provider.callTool(...). It was renamed to sdk/packages/core/src/mcp/tools.ts in 6ae37eba7 (#83) and to its current path in 700095d17 (#87). The object-to-string branch moved into sdk/packages/core/src/runtime/agent-config-adapter.ts in 64c8ddbcc ("refactor: makes @clinebot/agents stateless (#219)", 2026-04-23), into agent-message-codec.ts in f6791fded (#346), and into toPersistedToolResultContent in 6d7e745fb (#13075, merged 2026-08-14). None of these commit messages gives a reason for returning the whole result or for the stringify. The low PR numbers in these SDK commit messages do not resolve in cline/cline (gh pr view 219 and gh pr view 346 fail), so those PRs were not read.

Issue #14421 (open, opened 2026-09-22) reports that “an MCP image result reaches the outgoing model request as JSON text containing the base64” in CLI 3.0.64 and the VS Code Next path, while the legacy VS Code implementation sends it as an image. #14483 (open) proposes recognizing mimeType in toAiSdkToolResultOutput and is not merged at 72b3d71. #13066, merged 2026-08-08, changed the CLI TUI display to render MCP result text in place of escaped JSON, after issue #13038; neither touches the model path. gh search issues and gh search prs in cline/cline for structuredContent, structured content, outputSchema, MCP tool result, mcp tool output JSON, mcp image tool result, createMcpTools and McpToolCallResult found no issue or PR about which field reaches the model.

Quirks

An MCP result with isError: true is returned, not thrown, so executePreparedTool in sdk/packages/agents/src/agent-runtime.ts records it with no isError on the tool result. The model receives it as text, not error-text, and the flag reaches the model only as "isError":true inside the stringified envelope.

Non-object structuredContent depends on the transport. The stdio client passes a string or null through inside the envelope. On the SDK path CallToolResultSchema types the field as z.record(z.string(), z.unknown()).optional() (SDK 1.30.0 src/types.ts), so Protocol.request rejects with the ZodError (src/shared/protocol.ts), SdkUrlMcpClient.handleOperationError rethrows its message, and the model sees {"error":"[...zod issues...]"} with no MCP error prefix.
