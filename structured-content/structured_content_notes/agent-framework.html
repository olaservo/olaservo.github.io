Ola’s MCP Tool Result Research

How agent-framework handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the Microsoft Agent Framework monorepo (clones/agent-framework, checked out at commit 92838b60498395142cb8b74693353163e95a0faf (92838b6), read on 2026-11-14). Python file references are relative to python/packages/, except uv.lock and SDK files. .NET file references are relative to dotnet/src/, except Directory.Packages.props and SDK files.

Python

Entry: results enter through the SDK Client, typed as CallToolResult, with structured_content kept

core/pyproject.toml declares "mcp>=2.2.0,<3", and uv.lock resolves mcp 2.3.0 and mcp-types 2.3.0. MCPTool.connect in core/agent_framework/_mcp.py constructs mcp.Client(server=..., read_timeout_seconds=..., ...) and wraps it in _ClientMCPConnection, whose call_tool calls self._client.call_tool(name, arguments=..., meta=meta). A caller-supplied ClientSession is wrapped in _SessionMCPConnection and calls session.call_tool directly. MCPTool._call_tool_with_retries receives the types.CallToolResult, records it with _capture_mcp_result(self, result), and passes it to parser = self.parse_tool_results or self._parse_tool_result_from_mcp.

The CallToolResult models in mcp-types, read at python-sdk tag v2.3.0 (src/mcp-types/mcp_types/_types.py and the _v2025_11_25 and _v2026_07_28 wire modules), declare content: list[ContentBlock] with no default and structured_content: Any = None. ClientSession.send_request in mcp/client/session.py validates the raw result against them, so a result without a content key raises pydantic.ValidationError. _call_tool_with_retries catches it in its final except Exception arm, and the model sees "Error: Function failed.".

Model path: structuredContent replaces content by default; a constructor mode selects the rule

MCPTool.__init__ takes tool_result_content: MCPToolResultContentMode = "structured_first", validated against five values. _parse_tool_result_from_mcp first converts every content block to a Content item: text as text, image and audio as Content.from_data, ResourceLink as Content.from_uri, text resources as text, blob resources as a data: URI, and any other block as Content.from_text(str(item)). It then builds structured_block = Content.from_text(json.dumps(mcp_type.structured_content, default=str)) when structured_content is not None. The mode decides the list. structured_first runs result = [structured_block], so with both fields present the model receives one JSON text block and every content block, non-text included, is dropped. content_first appends the JSON block only when not result. content_only leaves the content list. structured_only keeps only the JSON block. both appends the JSON block after the content items. With empty content and a structured value, every mode except content_only yields the one JSON block. A list left empty after selection becomes Content.from_text("null"). A custom parse_tool_results callable replaces the whole function.

No mode compares the text blocks with the JSON, so under both a text block that mirrors structuredContent reaches the model twice. _parse_tool_result_from_mcp does not read annotations, and no non-test file under python/packages/ reads audience. A block with audience: ["user"] is converted like any other block and reaches the model in every mode that keeps content items. _parse_content_from_mcp, on the prompt and sampling path, copies an embedded resource’s annotations into additional_properties.

On result.is_error, _call_tool_with_retries runs the parser, joins its text items, and raises _mcp_tool_execution_exception(text or str(parsed)). _function_execution_error_result in core/agent_framework/_tools.py turns any tool exception into the result "Error: Function failed.", and appends f" Exception: {exception}" only when include_detailed_errors is set.

The selected list becomes the function result items, and each provider converter decides what survives.

  • openai/agent_framework_openai/_chat_completion_client.py (Chat Completions) joins text items with "\n" and logs a warning that “Rich content items will be omitted” for data and uri items.
  • openai/agent_framework_openai/_chat_client.py (Responses) sends input_text parts plus prepared rich parts when SUPPORTS_RICH_FUNCTION_OUTPUT is true and any item is data, uri or hosted_file. foundry/agent_framework_foundry/_chat_client.py sets it to False.
  • anthropic/agent_framework_anthropic/_chat_client.py keeps text and image data or uri items and drops the rest with logger.debug("Ignoring unsupported rich content media type in tool result: %s", ...).
  • bedrock/agent_framework_bedrock/_chat_client.py keeps text items only and logs that rich content “will be omitted”.

MCPTool._parse_content_from_mcp, used for prompt and sampling messages, has a separate ToolResultContent arm with the inverse rule: result=self._parse_content_from_mcp(mcp_type.content) if mcp_type.content else mcp_type.structured_content.

outputSchema: never read by the client; validated by the SDK; the model sees a generic error

No file under core/agent_framework/ reads output_schema or outputSchema. Validation is the SDK’s. In mcp 2.3.0, ClientSession.call_tool (mcp/client/session.py) runs if isinstance(result, types.CallToolResult) and not result.is_error: await self.validate_tool_result(name, result), and Client.call_tool (mcp/client/client.py) revalidates claimed results on the same condition. validate_tool_result raises RuntimeError(f"Tool {name} has an output schema but did not return structured content") or RuntimeError(f"Invalid structured content returned by tool {name}: {error}"). _call_tool_with_retries catches it in its final except Exception arm and raises _mcp_tool_execution_exception(f"Failed to call tool '{tool_name}'.", inner_exception=ex). The model then sees "Error: Function failed.", with the exception text appended only under include_detailed_errors. The one other reader is the declarative workflow handler: DefaultMCPToolHandler._invoke_list_tools in declarative/agent_framework_declarative/_workflows/_mcp_handler.py writes "outputSchema" into the JSON catalog it returns for the reserved tool name "tools/list".

Other paths: Host payload, code-mode sandboxes, declarative workflows, _meta labels, hosted MCP

_MCPResultCapture.record stores model_dump(by_alias=True, exclude_none=True, mode="json", fallback=str) of the whole result, up to max_host_payload_size_bytes (default 1 MiB), under _mcp_tool_result_host_payload. ag-ui/agent_framework_ag_ui/_run_common.py _resolve_tool_result_host_payload sends that payload to the AG-UI client as the display and snapshot result, so the UI receives both fields regardless of mode. hyperlight/agent_framework_hyperlight/_execute_code_tool.py _make_sandbox_callback and monty/agent_framework_monty/_execute_code_tool.py _make_tool_callback call invoke(..., skip_parsing=True) on registered tools, so sandbox code receives the mode-selected list[Content]. Monty passes it through _ensure_json_value in _monty_bridge.py, which raises ValueError for anything other than JSON primitives, lists and dicts. When a registered tool raises, which an MCP isError result or an SDK outputSchema failure does, Hyperlight’s callback raises RuntimeError("Host tool execution failed.") into the sandbox and Monty’s _external_error resumes the script with {"exc_type": "RuntimeError", "message": "Host tool execution failed."}. The tool’s error text reaches sandbox code only when the CodeAct tool or provider is built with include_detailed_errors=True. The Python declarative DefaultMCPToolHandler builds an MCPStreamableHTTPTool without tool_result_content and returns call_tool output as MCPToolResult(outputs=...), so it follows structured_first. _invoke_connected_tool turns a ToolExecutionException with no __cause__, which an MCP isError result raises, into MCPToolResult(outputs=[Content.from_text(f"Error: {message}")], is_error=True, ...), and re-raises one with a cause, which an SDK outputSchema failure produces, so that failure fails the InvokeMcpTool action. Result _meta is copied onto each item as additional_properties["_meta"]. The Chat Completions, Responses and Anthropic function_result arms build the tool message from item.text and the media fields only, so _meta does not reach the model. _label_from_mcp_meta in core/agent_framework/security.py reads meta["ifc"] for integrity and confidentiality, and LabelTrackingFunctionMiddleware._should_hide replaces an item labelled untrusted with a variable reference when auto_hide_untrusted is on. The chat clients' get_mcp_tool (OpenAI, Anthropic, Foundry, Gemini) declares a provider-hosted MCP tool, and its results never pass through MCPTool.

No non-test file under python/packages/ reads resourceUri or a ui key in _meta, so _meta.ui.visibility is not honoured. Function middleware sees the mode-selected list[Content] in FunctionInvocationContext.result (core/agent_framework/_middleware.py), and the class docstring says “any middleware may overwrite it with a value of any type”.

Protocol revision: negotiated by the SDK in auto mode

MCPTool.connect passes no mode to Client, so the SDK default mode: ConnectMode = "auto" in mcp/client/client.py applies. negotiate_auto in mcp/client/_probe.py sends server/discover with LATEST_MODERN_VERSION and falls back to initialize(). In mcp_types/version.py that constant is "2026-07-28" and LATEST_HANDSHAKE_VERSION is "2025-11-25". An unnegotiated caller-supplied ClientSession is initialized with session.initialize().

Upstream history: the tool_result_content option

The option came in through microsoft/agent-framework#8274, merged 2026-09-15, fixing issue #7866, a report that the DeepWiki and MS Learn servers return the same payload in both fields and the model saw it twice. The first version of the PR preferred content. A reviewer asked for an explicit policy instead, because servers may also use the two fields as complementary data, and the maintainer who listed the five modes wrote that the default “should probably be to propagate from the most specific (structuredContent) to the more generic (content)”. The issue thread cites the MCP roadmap’s line that returning both fields “has confused server and client authors alike” and the deferral of SEP-2200 as the reason the specification gives no rule to follow.

.NET

Entry: the SDK’s McpClientTool is the AIFunction; two wrappers forward to it

Directory.Packages.props pins ModelContextProtocol and ModelContextProtocol.Extensions.Tasks at 2.2.0 and Microsoft.Extensions.AI at 10.11.0. The SDK source is not in the clone. SDK references below were read from modelcontextprotocol/csharp-sdk at tag v2.2.0, paths relative to src/ModelContextProtocol.Core/. McpClient.ListToolsAsync returns McpClientTool instances, which derive from AIFunction and are passed to agents as tools. Microsoft.Agents.AI.Mcp/McpClientTaskExtensions.cs ListAgentToolsWithTasksAsync wraps each in TaskAwareMcpClientAIFunction, which calls this._client.CallToolAsTaskAsync(...) and, for a task, deserializes the completed CallToolResult from GetTaskAsync. Microsoft.Agents.AI.Foundry.Hosting/FoundryToolboxService.cs wraps each in ConsentAwareMcpClientAIFunction, which returns this._inner.InvokeAsync(arguments, cancellationToken) and only intercepts McpProtocolException code -32006.

CallToolResult (Protocol/CallToolResult.cs) declares Content with the initializer = [] and StructuredContent as JsonElement?, so a result without a content key deserializes with an empty list and keeps structuredContent.

Model path: native content only when nothing else is present; otherwise the whole result as JSON

McpClientTool.InvokeCoreAsync (Client/McpClientTool.cs) returns native AIContent only under if (result.IsError is not true && result.StructuredContent is null && !HasApplicationResultMetadata(result.Meta)), then switches on result.Content.Count: case 1 returns the single ToAIContent value, and case > 1 returns the array when aiContents.All(static c => c is not null). Every other result returns JsonSerializer.SerializeToElement(result, McpJsonUtilities.JsonContext.Default.CallToolResult). HasApplicationResultMetadata is true for any _meta key other than MetaKeys.ServerInfo. TaskAwareMcpClientAIFunction.ProjectResult repeats the same condition and switch, and its class comment says “Its result projection matches McpClientTool”.

With both fields present the model receives the serialized CallToolResult, with content, structuredContent and the other fields. With empty content and a structured value, the structured check already routes to the same envelope. With empty content and no structured value, Count 0 matches neither arm and the model receives {"content":[]...}. An isError result is returned as the envelope, not thrown. ToAIContent in AIContentExtensions.cs maps text to TextContent, image and audio to DataContent, and embedded resources through Resource.ToAIContent(). Its _ => null arm covers ResourceLinkBlock, so any result that includes a resource link becomes the envelope.

No comparison of the text with structuredContent runs, so a mirrored payload reaches the model twice inside the envelope. ToAIContent does not read Annotations and copies only Meta into AdditionalProperties. No file under dotnet/src/ reads audience (grep returns no match). A block with audience: ["user"] reaches the model as native content, or inside the envelope with its annotations.

outputSchema: surfaced as ReturnJsonSchema, forwarded, not validated

McpClientTool.ReturnJsonSchema => ProtocolTool.OutputSchema in the SDK. TaskAwareMcpClientAIFunction, ConsentAwareMcpClientAIFunction and ClientAIFunctionDeclaration in Microsoft.Agents.AI.Hosting.OpenAI/Responses/OpenAIResponseRequestInfoBuilder.cs override it as this._inner.ReturnJsonSchema (this._innerFunction.ReturnJsonSchema in the last) and have no other reader in dotnet/src/. The SDK’s Client/McpClient.Methods.cs and Client/McpClientTool.cs at v2.2.0 contain no output-schema validation. No validation runs, so a mismatched structuredContent reaches the model inside the envelope like any other value. Microsoft.Agents.AI.Workflows.Declarative.Mcp/DefaultMcpToolHandler.cs SerializeToolsList writes tool.OutputSchema into the "tools/list" catalog text. No code under dotnet/src/ puts ReturnJsonSchema into a provider tool declaration. The Microsoft.Extensions.AI 10.11.0 provider adapters were not read, so whether they send it to the model is not determined.

Other paths: declarative workflows drop structuredContent; Hyperlight CodeAct serializes the projection

DefaultMcpToolHandler.InvokeClientAsync calls client.CallToolAsync directly and PopulateResultContent reads only result.Content. On IsError it emits one TextContent($"Error: {errorText ?? "Unknown error from MCP Server call"}") from the text blocks. On empty content it returns with no outputs. Otherwise it maps each block through ConvertContentBlock, which uses block.ToAIContent() and maps ResourceLinkBlock to UriContent. CreateClientAsync wraps the HTTP handler in McpResponseLimitHandler (MaxResponseBodyBytes and MaxSseEventBytes, default 4 MiB each), which throws HttpRequestException("The MCP response body exceeds the configured byte limit.") for a larger non-SSE body and InvalidDataException("The MCP SSE event exceeds the configured byte limit.") for a larger SSE event, so an oversized response raises an exception instead of producing outputs. InvokeMcpToolExecutor.ProcessResultAsync in Microsoft.Agents.AI.Workflows.Declarative/ObjectModel/ puts those outputs in a ChatRole.Tool message. Microsoft.Agents.AI.Hyperlight/Internal/ToolBridge.cs InvokeAsync calls tool.InvokeAsync and SerializeResult serializes the return value with AIJsonUtilities.DefaultOptions, so sandbox code receives the same native-or-envelope projection as JSON. When the tool throws, InvokeAsync returns SerializeError(includeDetailedErrors ? ex.ToString() : "Host tool execution failed."), with the flag taken from HyperlightCodeActProviderOptions.IncludeDetailedErrors (default false). No code in dotnet/src/ routes on result _meta beyond the SDK’s HasApplicationResultMetadata check.

No file under dotnet/src/ reads resourceUri or a ui key in _meta, so _meta.ui.visibility is not honoured. Microsoft.Agents.AI.GitHub.Copilot/GitHubCopilotAgent.cs copies an EnableMcpApps option into the GitHub Copilot session configuration. Microsoft.Agents.AI/FunctionInvocationDelegatingAgent.cs runs function middleware as a delegate that takes a next callback and returns ValueTask<object?>, so middleware sees the native-or-envelope value and its return value replaces it. The SDK’s McpClientTool offers WithName, WithDescription, WithProgress and WithMeta, and none of them changes the projection.

Protocol revision: SDK default, 2026-07-28 preferred with fallback

The one McpClientOptions.ProtocolVersion assignment in dotnet/src/ is DefaultMcpToolHandler's new McpClientOptions { ProtocolVersion = this.ProtocolVersion }, from an init-only ProtocolVersion property whose default is null (“to use its automatic negotiation”). In the SDK, McpClientImpl.ConnectAsync (Client/McpClientImpl.cs) uses _options.ProtocolVersion ?? McpProtocolVersions.July2026ProtocolVersion, sends server/discover, retries a server-named per-request-metadata version on UnsupportedProtocolVersionException, and otherwise falls back to the initialize handshake. The comment reads “A null ProtocolVersion prefers the 2026-07-28 revision and automatically falls back to the initialize handshake”.

Upstream history: the native-or-envelope rule in csharp-sdk

The rule came in through modelcontextprotocol/csharp-sdk#941, “Tweak how McpClientTool.InvokeAsync exposes some content”, merged 2025-11-07. It made InvokeCoreAsync return AIContent when the result has no isError, no structuredContent and no _meta, and the serialized CallToolResult otherwise. Before it, the method always returned the serialized CallToolResult. The code comment it added gives the rationale: “when there is additional information carried by the CallToolResult outside of its ContentBlocks, just returning AIContent from those ContentBlocks would lose that information. So, we only do the translation if there is no additional information to preserve.” The first version converted only when non-text content was present, and the author wrote that this was “to try to minimize the differences from today for the vastly most common case today (which is just text)”. A reviewer asked "Doesn’t this lose the "isError": true from the CallToolResult?“ and wrote that ”Changing the return type from AIContent[] to JsonElement based on a subtle change in the MCP server’s CallToolResult is a recipe for latent bugs." The author answered that always returning a JsonElement “means that logic like this can’t work”, linking OpenAIResponsesChatClient.cs in dotnet/extensions. Another reviewer approved and wrote “It has no way of combining AIContent conversion and structured output which might become an emerging pattern, given how it seems structured content is becoming a pseudo-metadata payload (ie OpenAI apps SDK). But one can do that conversion in middleware that will exist in such clients anyway.”

modelcontextprotocol/csharp-sdk#1752, merged 2026-07-27, replaced the result.Meta is not { Count: > 0 } test with HasApplicationResultMetadata. Its comment reads “Server identity is protocol metadata already exposed through McpClient.ServerInfo. It should not force an otherwise simple tool result into its JSON envelope.” The PR body ties the change to specification PR #3002, which put serverInfo in result _meta.

TaskAwareMcpClientAIFunction came in through microsoft/agent-framework#5994, merged 2026-05-22, and #7774, merged 2026-08-20. Their bodies and review comments record no rationale for the projection beyond the class comment. The commit history of src/ModelContextProtocol.Core/Client/McpClientTool.cs up to v2.2.0 and these searches found nothing further: gh search issues in csharp-sdk for “structuredContent InvokeAsync”, “McpClientTool JsonElement content” and “structured content AIContent”, and in agent-framework for “structuredContent .NET McpClientTool”.

Quirks

  • Python: _parse_tool_result_from_mcp tests structured_content is not None, so a structuredContent of JSON null is treated as missing. Arrays and scalars pass through json.dumps like objects.
  • Python: an empty result {} has no content key, so it fails CallToolResult validation and reaches the model as "Error: Function failed.", the same text _function_execution_error_result gives an isError result when include_detailed_errors is off.
