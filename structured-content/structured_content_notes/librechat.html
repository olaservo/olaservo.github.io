Ola’s MCP Tool Result Research

How LibreChat handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the LibreChat source (clones/librechat, checked out at commit fad2c51da41bb46c9cdd44a720cea4df0d47876b (fad2c51), read on 2026-11-14). File references are relative to packages/api/src/ unless they start with api/, client/ or packages/data-provider/ or name package-lock.json. Agent-runtime references are to @librechat/agents 4.2.2 (src/), and SDK references are to @modelcontextprotocol/sdk 1.32.1 (dist/esm/); package-lock.json resolves both at those versions, and the SDK range is "@modelcontextprotocol/sdk": "^1.32.1" in packages/api/package.json and api/package.json.

Entry: results enter through the SDK’s raw request, cast to MCPToolCallResponse, with structuredContent kept

MCPConnection in mcp/connection.ts constructs the SDK Client from @modelcontextprotocol/sdk/client/index.js. MCPManager.callTool in mcp/MCPManager.ts sends connection.client.request({ method: 'tools/call', params: { name, arguments } }, CallToolResultSchema, ...) and never calls Client.callTool. The comment above it reads "Deliberately use request: the typed wrapper also enforces the tool’s output schema and rejects task-required tools". Protocol.request (shared/protocol.js) runs safeParse(resultSchema, response.result) and rejects on failure. CallToolResultSchema (types.js) declares content: z.array(ContentBlockSchema).default([]) and structuredContent: z.record(z.string(), z.unknown()).optional(), so an absent content key becomes [] and a non-object structuredContent fails the parse. The parsed value is cast with const toolResult = result as t.MCPToolCallResponse;. MCPToolCallResponse in mcp/types/index.ts is undefined or { _meta?, content?, isError?, structuredContent?: Record<string, unknown> }. createToolInstance in api/server/services/MCP.js wraps the call as a LangChain tool through createMCPStructuredTool (mcp/tools.ts) with responseFormat: AgentConstants.CONTENT_AND_ARTIFACT, so each call yields a [string, artifacts] pair.

Model path: content only, structuredContent goes to the MCP Apps snapshot

formatToolContent in mcp/parsers.ts builds the model string from result?.content only. Its one read of structuredContent that feeds an output is structuredContent: result?.structuredContent inside the MCP Apps snapshot object, which goes into the UI resource artifact and not into the returned text. deriveResourceId also hashes result.structuredContent into the UI resource ID. When both fields are present, the model receives the text built from content and nothing from structuredContent. When content is empty or absent, the function returns ['(No response)', undefined] through if (!content.length && !hasSyntheticApp), or through parseAsString, whose first check is if (!content.length) { return '(No response)'; }. When MCP Apps is enabled and the tool declares an MCP App resource (hasSyntheticApp), empty content skips that early return, and the last line return [currentTextBlock || (artifacts !== undefined ? '' : '(No response)'), artifacts]; returns an empty string with the UI artifact attached for a recognized provider. For an unrecognized provider currentTextBlock starts as parseAsString(result), so the same case returns (No response) with the UI artifact attached. No code compares content with structuredContent, so a text block that mirrors the JSON reaches the model as written and nothing is removed as a duplicate. structuredContent is not serialized into the model request in any form, compact, pretty or enveloped. The only reads of structuredContent in first-party source outside tests are deriveResourceId and the snapshot in mcp/parsers.ts, the type in mcp/types/index.ts and packages/data-provider/src/schemas.ts, and buildAppToolResult in client/src/utils/mcpApps.ts.

Block handling depends on RECOGNIZED_PROVIDERS, a set of nine names: google, anthropic, openai, azureopenai, openrouter, xai, deepseek, ollama, bedrock. For a recognized provider, text blocks are joined with blank lines. image blocks are converted by imageFormatters.default to image_url parts and collected into artifacts.content. resource_link blocks become labelled lines from describeResourceLink. Embedded resources become Resource Text: plus URI and MIME lines, image blobs become image artifacts, and binary blobs become a byte-count line. Any other block type, including audio, is appended as JSON.stringify(item, null, 2). A ui:// resource with an inline body and a non-HTML MIME type, or plain HTML when legacyHtmlEnabled is on and the URI is not the tool’s declared App URI, becomes a UIResource in artifacts[Tools.ui_resources], and the model text gets UI Resource ID: and \ui{...} marker lines plus a fixed “UI Resource Markers Available” instruction block. For an unrecognized provider the text starts as parseAsString(result), which stringifies image blocks as JSON, so base64 data lands inline in the text. Its image blocks are also collected, but into imageAttachments beside an empty content ({ content: [], imageAttachments: imageUrls }), which getImageAttachmentContent in files/resize.ts hands to the attachment-saving code in api/server/controllers/agents/callbacks.js, so no image artifact is sent to the model. assertImageDataWithinLimit throws when a base64 image exceeds MCP_IMAGE_DATA_MAX_BYTES (default 10 MiB). Non-text blocks do not change which field reaches the model, because no branch of formatToolContent reads structuredContent for the text.

Image artifacts are merged into the provider request by projectServingArtifacts in @librechat/agents graphs/Graph.ts:

  • isAnthropicLike (Anthropic, or Bedrock with a Claude model): projectAnthropicArtifactContent (messages/core.ts).
  • isOpenAILike except DeepSeek (OpenAI, Azure, OpenRouter, xAI) and isGoogleLike (Google, Vertex AI): projectArtifactPayload, which replaces the tool message text with “Tool response is included in the next message as a Human message” and appends a HumanMessage holding the text and images.
  • Every other provider, including DeepSeek, Ollama and non-Claude Bedrock: return candidate;, so image artifacts are not sent.

An isError result is tagged by markMCPToolResultError (mcp/status.ts), and createMCPStructuredTool returns it as a ToolMessage with status: 'error' and the same text.

formatToolContent and parseAsString in mcp/parsers.ts do not read annotations, so a block with audience: ["user"] is handled like any other block of its type and reaches the model. No first-party file under packages/api/src/, api/server/, client/src/ or packages/data-provider/src/ reads a content-block audience. The only audience hits there are OAuth and JWT settings, in auth/, mcp/oauth/, schedules/, middleware/, packages/data-provider/src/mcp.ts and similar auth code. @librechat/agents 4.2.2 src/ has no occurrence of audience.

outputSchema: never read; no validation on the call path

outputSchema has no occurrence in first-party source outside tests. formatMCPServerTools in mcp/tools.ts builds each catalog entry as { name, description, parameters } from tool.inputSchema, and createToolInstance in api/server/services/MCP.js builds the LangChain schema from toolDefinition.parameters. Neither projection carries outputSchema into a description or prompt. The SDK’s Client.callTool (client/index.js) validates structuredContent against the cached output schema and throws McpError on a mismatch. LibreChat calls request directly, so that check does not run. The only schema applied is CallToolResultSchema. When that parse fails, Protocol.request rejects, the catch block in createToolInstance rethrows [MCP][server][tool] tool call failed: <message>, and the agent runtime’s formatToolErrorContent (tools/toolErrorContent.ts) gives the model Error: <message>\n Please fix your mistakes..

Other paths: programmatic tool calling, MCP Apps, app-originated calls

The programmatic tool calling runner is executeTools in @librechat/agents tools/ProgrammaticToolCalling.ts. LibreChat wraps its tool map with instrumentPtcToolMap (agents/ptc.ts), which emits trace events and returns results unchanged. executeTools invokes the same MCP tool with tool.invoke(normalizeToolInput(call.input, tool), { metadata }) and no toolCall, so _formatToolOutput in @langchain/core 1.2.8 (dist/tools/index.js) returns the first tuple element, the formatToolContent string. unwrapToolResponse(result, isMCPTool) runs maybeParseJSON only on tuples and content blocks, and a plain string falls through to return result;. Sandbox code sees the content text as a string and never structuredContent.

MCP Apps tool metadata is read from _meta in mcp/apps.ts. getToolUiResourceUri reads _meta.ui.resourceUri or _meta['ui/resourceUri'] and requires a ui:// prefix. isToolHiddenFromModel returns Array.isArray(visibility) && !visibility.includes('model'), and formatMCPServerTools skips such tools, so they never reach the model. isToolHiddenFromApp applies the same test to 'app' and gates MCPManager.appToolCall. When MCP Apps is enabled (mcpSettings.apps: true, since resolveMCPAppsPolicy in packages/data-provider/src/config.ts sets enabled: value === true) and a called tool has a resource URI, MCPManager.callTool reads it with client.readResource and passes it to formatToolContent, which attaches a UIResource snapshot carrying structuredContent, content, isError and resultMeta (the result _meta). In the browser, buildAppToolResult in client/src/utils/mcpApps.ts rebuilds { content, structuredContent, isError, _meta } from that snapshot, and client/src/hooks/MCP/useAppBridge.ts delivers it to the app iframe with sendToolResult. This is the only route on which structuredContent from a model-initiated call leaves the server.

MCPManager.appToolCall proxies tools/call requests from an app iframe with the same client.request(..., CallToolResultSchema, ...) call and returns the parsed result to the app without formatToolContent. That result does not reach the model.

Deployment plugins can declare hooks in ai.librechat/hooks/hooks.json (plugins/constants.ts), and plugins/hooks.ts runs them only when DEPLOYMENT_PLUGIN_HOOKS=true. The PostToolUse payload built by createPluginHookPayload in agents/hooks/runtime.ts carries tool_response: input.toolOutput. @librechat/agents tools/ToolNode.ts fills toolOutput with the ToolMessage content, which for an MCP tool is the formatToolContent string, so a hook never sees structuredContent. sanitizeOutput in agents/hooks/executor.ts passes updatedOutput through on PostToolUse, and ToolNode replaces the ToolMessage content with it, so a hook can change the text the model gets. Tool-approval hooks configured under endpoints.agents.toolApproval.hooks (agents/hitl/hookLoader.ts) are PreToolUse callbacks and do not see the result.

No _meta key, per-server option, constructor option or schema routes structuredContent to the model. The inputs to formatToolContent that change the model text are the provider name (RECOGNIZED_PROVIDERS), the MCP Apps policy (enabled, legacyHtmlEnabled), and the tool’s _meta.ui.resourceUri.

Protocol revision: SDK default, not pinned

LibreChat sets no protocol version. new Client({ name: '@librechat/api-client', version: '1.2.3' }, { capabilities }) in mcp/connection.ts adds only the MCP Apps UI extension capability, for the apps capability profile. The SDK’s Client.connect (client/index.js) sends protocolVersion: LATEST_PROTOCOL_VERSION, which is '2025-11-25' in types.js, and rejects a server reply outside SUPPORTED_PROTOCOL_VERSIONS (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05, 2024-10-07).

Upstream history: the validation comment, the maintainer’s position, open PRs

The "Deliberately use request" comment in mcp/MCPManager.ts arrived with LibreChat-AI/LibreChat#13831, the MCP Apps pull request merged 2026-09-24, which also added structuredContent to MCPToolCallResponse and to the MCP Apps snapshot. The raw request call dates from the first MCP support in December 2024, before the SDK’s callTool validated anything, so the comment explains a path that was never changed. The PR body and review threads do not discuss the bypass.

The maintainer’s stated position, from discussion #8450 in July 2025: “The structured content is for the output of the tool call, and mainly on the MCP server, not the client (LibreChat) to address.” Two pull requests that would serialize structuredContent at the (No response) sites, #14492 and #15236, are unmerged, with reports from users of the Airtable, Traccar and Microsoft WorkIQ servers, which send an empty content array.

Quirks

formatToolContent in mcp/parsers.ts keeps the App snapshot only if it fits mcpApps.maxPersistedAppBytes (default DEFAULT_MCP_APP_PERSISTED_BYTES). When the snapshot with the resolved body is too large, it retries without the body, and when that also fails fitsPersistedAppLimit, no UI resource is attached and structuredContent does not reach the app. buildAppToolResult in client/src/utils/mcpApps.ts forwards structuredContent only when it is a non-array object.
