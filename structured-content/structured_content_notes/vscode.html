Ola’s MCP Tool Result Research

How VS Code handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the VS Code source (clones/vscode, checked out at commit d53b9e1d, read on 2026-11-14). The clone is code-oss-dev 1.147.0 with the Copilot Chat extension vendored at extensions/copilot (copilot-chat 0.75.0). File references are relative to the clone root.

Entry: hand-rolled JSON-RPC, typed straight into MCP.CallToolResult

VS Code uses no MCP SDK on the client side. src/vs/workbench/contrib/mcp/common/mcpServerRequestHandler.ts owns the session: McpServerRequestHandler.create sends initialize, and callTool issues { method: 'tools/call', params } through a generic JsonRpcProtocol from src/vs/base/common/jsonRpcProtocol.ts. The @modelcontextprotocol/sdk dependency in extensions/copilot/package.json (^1.30.0) is imported only for McpServer, StreamableHTTPServerTransport and isInitializeRequest under extensions/copilot/src/extension/chatSessions/copilotcli/vscode-node/, where Copilot Chat acts as a server for the Copilot CLI. The root pnpm-lock.yaml resolves @modelcontextprotocol/sdk 1.29.0 for src/vs/platform/agentHost/node/claude/, which imports CallToolResult as a type only to convert VS Code’s own client tools for the Claude agent; it is not on the server-result path.

Bytes come off the wire as text. src/vs/workbench/api/node/extHostMcpNode.ts splits stdout on \n and forwards each line; src/vs/workbench/api/common/extHostMcp.ts forwards HTTP and SSE bodies. mainThreadMcp.ts (src/vs/workbench/api/browser/) does parsed = JSON.parse(message) in pushMessage and fires the object. JsonRpcProtocol._handleResult resolves the pending promise with response.result and nothing validates its shape. callTool returns that object as MCP.CallToolResult, with a detour through McpTask when the server answers with a task.

The result type is the generated schema in src/vs/platform/mcp/common/modelContextProtocol.ts. interface CallToolResult keeps content: ContentBlock[] and structuredContent?: { [key: string]: unknown }, so the field survives deserialization.

Model path: structuredContent replaces every text block, media still goes through

The conversion to the chat tool result lives in McpToolImplementation.invoke in src/vs/workbench/contrib/mcp/common/mcpLanguageModelToolContribution.ts. It calls this._tool.callWithProgress (McpTool._callWithProgress in mcpServer.ts) and loops over callResult.content.

The text branch reads if (isForModel && !callResult.structuredContent) before pushing { kind: 'text', value: item.text }. After the loop, if (callResult.structuredContent) pushes { kind: 'text', value: JSON.stringify(callResult.structuredContent), audience: [LanguageModelPartAudience.Assistant] }. The gate is truthiness, so structuredContent: {} also drops every text block and the model gets the text {}. So when both fields are present the model gets compact JSON of structuredContent and none of the text blocks. When content is empty and structuredContent is present the model gets the JSON alone. When only structuredContent arrives and content is absent, for (const item of callResult.content) throws a TypeError on undefined before the structured branch runs, and the call fails; Copilot Chat turns the thrown error into the model-visible text ERROR while calling tool: ... in toolCalling.tsx. A pretty-printed copy of the JSON goes into details.output for the user-facing view with the same assistant audience. The text blocks are dropped whether or not they mirror the JSON, and no comparison between them is made. The comment above the gate reads “structured content 'represents the result of the tool call', so take that in place of any textual description when present.” The gate reads no _meta key, setting, constructor option or outputSchema; its only input is the truthiness of callResult.structuredContent.

Non-text blocks bypass the structured gate. image and audio blocks go through addAsInlineData, which resizes via IImageResizeService and pushes { kind: 'data', value: { mimeType, data } }. resource_link blocks with an attachable image mime type are read from McpResourceURI and inlined; other links become a data part with mime type McpToolResourceLinkMimeType ('application/vnd.code.resource-link', mcpTypes.ts) carrying { uri, underlyingMimeType }. Embedded resource blocks inline as images when they are image blobs; otherwise their text or blob goes to the details view and the model gets a resource-link part pointing at a ChatResponseResource permalink. Per-block annotations.audience is honored: a block whose audience excludes assistant is skipped on the model path and a user text block is reported through progress.

IToolResult crosses to the extension host through LanguageModelToolResult.to in src/vs/workbench/api/common/extHostTypeConverters.ts, which maps text parts to LanguageModelTextPart and data parts to LanguageModelDataPart with audience preserved. Copilot Chat renders them in PrimitiveToolResult.render in extensions/copilot/src/extension/prompts/node/panel/toolCalling.tsx, filtered by hasAssistantAudience. onData returns '' for any data part other than a resource link, so audio and non-image binaries do not reach the model. Images are subject to CAPI_IMAGE_BUDGET_BYTES and a shared per-turn budget. ToolResult.onText writes any text part longer than chat.agent.largeToolResultsToDisk.thresholdBytes (default 8 * 1024, extensions/copilot/src/platform/configuration/common/configurationService.ts) to disk via IChatDiskSessionResources and substitutes a pointer string; if the text parses as JSON it also writes schema.json from toJsonSchema(parsed). Below that threshold, text is truncated to truncateAt tokens, set in agentPrompt.tsx as modelMaxPromptTokens * MAX_TOOL_RESPONSE_PCT with MAX_TOOL_RESPONSE_PCT = 0.5. PrimitiveToolResult.render wraps the rendered parts in <IfEmpty alt='(empty)'>, so a result with no assistant-audience parts reaches the model as (empty).

outputSchema: carried on the type, never read

MCP.Tool.outputSchema exists in the generated schema. McpServer._normalizeTool in mcpServer.ts spreads ...originalTool into the ValidatedMcpTool, so the field rides along, but the only schema work there is on inputSchema: it adds an empty properties and runs json.validate against https://json-schema.org/draft-07/schema. The IToolData built in mcpLanguageModelToolContribution.ts copies inputSchema: tool.definition.inputSchema and has no output schema field. A repo-wide search for outputSchema outside the schema files hits only agent-host protocol types under src/vs/platform/agentHost/. Nothing validates structuredContent, and nothing puts the schema into prompt text.

Other paths: MCP Apps, the gateway, and hooks

MCP Apps get the raw result. When a tool’s _meta.ui.resourceUri is set, invoke stores details.mcpOutput = callResult, and ChatMcpAppModel._sendToolResult in src/vs/workbench/contrib/chat/browser/widget/chatContentParts/toolInvocationParts/chatMcpAppModel.ts forwards it as ui/notifications/tool-result. The app can push context back through updateModelContext; the handler at if (params.structuredContent && Object.keys(params.structuredContent).length > 0) attaches it to the chat input as a generic attachment named 'UI Data'. Apps calling tools directly go through McpToolCallUI.callTool in src/vs/workbench/contrib/mcp/browser/mcpToolCallUI.ts, which hands the call to a transport: LocalMcpAppCallTransport.callTool returns content, isError, _meta and structuredContent untouched, and AhpMcpAppCallTransport.callTool, used for agent-host-resident servers, sends tools/call over the agent host mcp:// channel and returns the result as received. _meta.ui.visibility sets McpToolVisibility; a tool without the model bit is skipped in the IToolData registration loop. chat.mcp.apps.enabled (mcpAppsEnabledConfig in src/vs/platform/mcp/common/mcpManagement.ts, default true) gates only the mcpAppData attached to the tool registration; storing details.mcpOutput and the visibility filter run regardless of the setting.

The MCP Gateway re-exposes VS Code’s servers over local HTTP to agent hosts such as the Copilot CLI. McpGatewaySession._handleCallTool in src/vs/platform/mcp/node/mcpGatewaySession.ts returns the invoker’s result verbatim, except that its debug log line reads result.content.length eagerly, so a result with no content key is rethrown as JsonRpcError(MCP_INVALID_PARAMS, ...) there and in McpGatewayToolBrokerChannel; and McpGatewayToolBrokerChannel._listToolsForServer in src/vs/workbench/contrib/mcp/common/mcpGatewayToolBrokerChannel.ts republishes t.definition for model-visible tools, outputSchema included. Results from an agent host come back through toMcpCallToolResult in src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/stateToProgressAdapter.ts, which rebuilds { content, structuredContent, _meta, isError } for the MCP App notification only. Tools an MCP App registers through App.registerTool() are published to the agent host session as client tools by src/vs/workbench/contrib/chat/browser/agentSessions/agentHost/agentHostMcpAppToolsService.ts. Their results come from the app over a host-to-app tools/call, and _convertResult keeps every content block and appends JSON.stringify(result.structuredContent) as another text part, so the tool result holds both copies.

Copilot Chat’s PostToolUse hook receives toolResultToText(toolResult), which joins text parts with \n (toolCalling.tsx), so a hook sees the structured JSON string when one was substituted. Hook additionalContext and block decisions append LanguageModelTextPart entries wrapped in <PostToolUse-context>. IMcpSandboxService in mcpSandboxService.ts sandboxes the server process launch and does not touch results. The per-server configuration in src/vs/platform/mcp/common/mcpPlatformTypes.ts has no knob that changes result routing. No code-mode path exists. A case-insensitive grep for codeMode, code-mode and code_mode under src/vs/workbench/contrib/mcp, src/vs/workbench/contrib/chat and extensions/copilot/src hits only CSS (modernTab) and test identifiers (codeModel, modelD).

Protocol revision: 2025-11-25

MCP.LATEST_PROTOCOL_VERSION = "2025-11-25" in src/vs/platform/mcp/common/modelContextProtocol.ts. McpServerRequestHandler.create sends it as protocolVersion in initialize, and extHostMcp.ts sets the 'MCP-Protocol-Version' header to the same constant on the auth metadata requests of HTTP transports. The server’s reply is stored as _serverInit without a version check.

Upstream history: the replacement rule, the maintainer’s position, an open PR

The gate and the structured text part arrived with microsoft/vscode#257161, “mcp: support resource_links and structured output”, merged 2025-07-21 into src/vs/workbench/contrib/mcp/common/mcpService.ts. It closed the tracking issue #248418, “MCP: Adopt 2025-06-18 spec”, which lists “Structured output https://github.com/modelcontextprotocol/modelcontextprotocol/pull/371”. The PR body is the template plus the closing line, and its one review is an approval with no text, so the in-code comment is the only recorded rationale. The code moved to mcpLanguageModelToolContribution.ts in commit 2f3486fd81 (“mcp: implement autorun, rework trust”, 2025-07-24). #266072, merged 2025-09-10, added audience: [LanguageModelPartAudience.Assistant] to the structured parts and left the gate unchanged.

Issue #290063, “MCP: structuredContent in tool result overrides content[].text sent to model”, opened 2026-01-24, is open. The maintainer’s reply on 2026-01-29: “It turns out structuredContent actually should not be presented to the model, its use case is PTC. Discussion here: https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1624”. Later comments report Microsoft Fabric Data Agent and Fabric IQ servers whose answer is in content[].text while structuredContent holds only metadata. #342190, opened 2026-10-16 and unmerged, would forward model-audience text blocks and send the serialized structuredContent only when no block is meant for the model. Issue #297669, closed 2026-02-25, reported the TypeError for a result without content; the maintainer replied “You are still required to return a content array.”

The clone is shallow at depth 1, so git log and git blame reach only d53b9e1d. The history above comes from gh api commit listings for both file paths, gh search issues and gh search prs for structuredContent in microsoft/vscode, and gh pr view and gh issue view on the hits.

Quirks

The gate in invoke tests truthiness, so a falsy non-object structuredContent (null, 0, false, "") keeps the text blocks and adds no structured part, while an array or a non-empty string or nonzero number drops the text blocks and is sent through JSON.stringify (mcpLanguageModelToolContribution.ts).
