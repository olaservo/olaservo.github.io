How Mastra handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the Mastra monorepo (clones/mastra, checked out at commit 7277766d6c967c475675d58ff2d0e5c6d7be7c84 (7277766d), read on 2026-11-14). File references are relative to the repo root. SDK references are to the @modelcontextprotocol/client@2.4.0 tag of modelcontextprotocol/typescript-sdk at 2094c44, whose packages/client/package.json reads 2.4.0, the version pnpm-lock.yaml pins for @modelcontextprotocol/client and @modelcontextprotocol/core under packages/mcp.

Entry: results enter through the SDK Client.callTool and are reshaped inside each tool’s execute

MCPClient in packages/mcp/src/client/configuration.ts creates one InternalMastraMCPClient per server. InternalMastraMCPClient in packages/mcp/src/client/client.ts wraps Client from @modelcontextprotocol/client and forwards server.jsonSchemaValidator to it when one is configured. buildToolFromListEntry turns each tools/list entry into a Mastra tool with createTool, and is shared by live discovery (tools()) and cache hydration (toolFromDefinition). Its execute calls this.client.callTool({ name, arguments, _meta }, ...) and receives the SDK’s CallToolResult. It then returns one of three values. On isError with the default onToolError: 'throw' it throws a MastraError. On res.structuredContent !== undefined && !res.isError it returns attachMcpCallToolContent(res.structuredContent, res.content, ...), the structured value itself with content and result _meta stored on the non-enumerable symbols MCP_CALL_TOOL_CONTENT and MCP_CALL_TOOL_META. Otherwise it returns res, the whole envelope. Scalar or null structured values cannot carry the symbols.

The SDK’s CallToolResultSchema in packages/core/src/schemas.ts (SDK, read at 2094c44 through the GitHub API) declares structuredContent: z.unknown().optional() and content: z.array(ContentBlockSchema).default([]). The negotiated revision’s codec parses the wire body first. On 2026-07-28, decodeResult in packages/core-internal/src/wire/rev2026-07-28/codec.ts (SDK) parses with that revision’s CallToolResultSchema from rev2026-07-28/buildSchemas.ts, which declares content: z.array(ContentBlockSchema) with no default and structuredContent: z.unknown().optional(). structuredContent survives as any JSON value, and a result without a content key, an empty {} result included, is rejected with Invalid result for tools/call: ${parsed.error}. isReconnectableMCPError does not match that message, so execute rethrows it and the model sees the zod issue list as error text. On 2025-11-25, CallToolResultWireSchema in rev2025-11-25/buildSchemas.ts defaults a missing content to [], so execute handles it like an empty content array, and the revision’s structuredContent: z.record(z.string(), z.unknown()).optional() rejects a scalar, array or null structuredContent with the same Invalid result for tools/call: prefix.

Model path: the declared outputSchema decides between content text and structuredContent

buildToolFromListEntry attaches a model mapper only for tools with a schema: ...(tool.outputSchema ? { toModelOutput: createStructuredToolToModelOutput() } : {}). createStructuredToolToModelOutput reads the hidden content and returns { type: 'text', value: modelText } when extractModelTextFromToolContent finds text, otherwise { type: 'json', value: output }. extractModelTextFromToolContent keeps text blocks and the resource.text of embedded resources, joined with \n and trimmed. Core runs the mapper in computeModelOutputProviderMetadata (packages/core/src/loop/shared/steps/tool-result-commit-core.ts) and stores the result at providerMetadata.mastra.modelOutput. MessageList in packages/core/src/agent/message-list/message-list.ts substitutes the stored value into the tool-result output when it builds the prompt.

With a declared outputSchema and both fields present, the model receives the joined text and not the structured value. With a declared outputSchema, empty content (or content with no text) and structuredContent present, the model receives structuredContent as { type: 'json' }. Without a declared outputSchema, no mapper runs. The vendored AI SDK v5 convertToModelMessages (ai 5.0.285, re-exported by packages/_vendored/ai_v5/src/index.ts) then serializes the returned structured value as { type: 'json' }, so structuredContent replaces content whether content is empty or not. The symbols are non-enumerable, so content does not reach the model on that route.

The routes above apply whether the text is an exact mirror of the JSON or differs from it. Neither createStructuredToolToModelOutput nor the no-schema route compares the text with the JSON. Each sends one of the two fields, so a mirrored result reaches the model once. The exception is onToolError: 'return' with isError, where the envelope carries both fields. No placeholder is substituted for an empty result. The mapper returns either text or the structured value, and a result with content: [] and no structuredContent reaches the model as the envelope JSON. A search of packages/core/src/agent/message-list and packages/core/src/loop/shared for placeholder strings found none.

When structuredContent is absent, the envelope goes to the model as JSON. applyMcpContentToolResultOutputs in packages/core/src/agent/message-list/conversion/output-converter.ts rewrites that JSON into { type: 'content' } when convertMcpContentToolResultOutput finds an image or audio block with string data. It maps text to text, image and audio to media parts, and every other block to JSON.stringify(typedPart) text. The rewrite is skipped when a stored modelOutput exists, so it applies only to tools without a declared outputSchema. On the structured path no media survives. The mapper keeps text only, and the no-schema route drops content.

isError is checked first. Under 'throw', extractToolErrorText(res.content) joins the text and resource text, falling back to 'MCP tool execution failed', and the result becomes the MastraError text. structuredContent goes only to details.structuredContent as a JSON string. llm-mapping-step.ts records the failure with commitToolResult as { kind: 'error', errorText: reifiedError.message }, so the model sees the joined text. Under onToolError: 'return' the gate !res.isError fails and the whole envelope is returned, including isError and structuredContent.

annotations.audience is not read on the model path. extractModelTextFromToolContent, extractToolErrorText and convertMcpContentToolResultOutput select blocks by type only, so a ["user"] block reaches the model like any other block. A grep for audience in packages/mcp/src, packages/core/src, client-sdks and packages/playground-ui/src returns only OAuth token audience checks in packages/mcp/src/server/oauth-middleware.ts and packages/core/src/server/types.ts and Knowledge pin audiences in packages/core/src/knowledge, packages/core/src/storage/domains/knowledge and the Studio Knowledge components (packages/playground-ui/src/domains/knowledge, packages/playground-ui/src/domains/chat/tools/badges/knowledge-tool-badge.tsx).

outputSchema: read for model mapping and code-mode types, validated by the SDK or by Mastra depending on the tool’s origin

convertOutputSchema overwrites the validator on the schema handed to createTool with validate: value => ({ value }). The Tool.execute check in packages/core/src/tools/tool.ts (validateToolOutput(this.outputSchema, ...)) therefore always passes. outputSchema is also read to decide whether toModelOutput is attached, is copied into SerializableMCPToolDefinition by toSerializableDefinition, and becomes the code-mode return type (below).

The schema does not reach the model through the tool declaration or the description. buildToolFromListEntry sets description: tool.description || ''. prepareToolsAndToolChoice in packages/core/src/stream/aisdk/v5/compat/prepare-tools.ts builds each function tool as name, description, inputSchema, strict and providerOptions, with no output schema. A grep for outputSchema in packages/core/src/llm/model/aisdk/v6/model.ts, v7/model.ts and packages/core/src/stream/aisdk/v5/execute.ts returns nothing.

For live tools, listTools writes the SDK response cache and the SDK validates first. Client.callTool in packages/client/src/client/client.ts (SDK) throws ProtocolError with Tool ${name} has an output schema but did not return structured content when the field is absent, and with Structured content does not match the tool's output schema: ${errorMessage} on a mismatch. isReconnectableMCPError (packages/mcp/src/client/error-utils.ts) does not match those messages, so execute rethrows and the model sees the SDK message as error text.

For tools rebuilt with toolFromDefinition, the SDK cache is cold and the SDK skips validation. Mastra validates in execute with a validator from getJsonSchemaValidator, which uses the configured validator or AjvJsonSchemaValidator from @modelcontextprotocol/client/validators/ajv. On a mismatch it returns validation.error from validateToolOutput (packages/core/src/tools/validation.ts). That value is an object { error: true, message, validationErrors } whose message starts Tool output validation failed for ${toolId}. The tool returned invalid output:. It is returned as a successful result, and the mapper sends it as { type: 'json' } because it carries no hidden content. When jsonSchemaComplexity (packages/mcp/src/shared/json-schema-dialect.ts) rejects the output schema, a result with structuredContent throws MCP_CLIENT_OUTPUT_SCHEMA_TOO_COMPLEX (packages/mcp/src/client/client.ts) instead of being validated.

Other paths: code mode, Studio and MCP Apps, history

createCodeMode and createCodeModeTool in packages/core/src/tools/code-mode/code-mode.ts take any Mastra tools, MCP tools included. generateStubs in stub-generator.ts renders each tool’s outputSchema through schemaToTs into declare function external_<name>(input: ...): Promise<${outputType}>. An MCP tool’s schema becomes the stub’s TypeScript return type, and a tool without one returns Promise<unknown>. The dispatcher calls tool.execute, and StdioCodeModeTransport.serveRpc (transport.ts) sends the return value to the sandbox as JSON.stringify({ type: 'rpc-result', id, ok, result, error }). Scripts get structuredContent when it is present, without content because the symbols do not serialize, and the envelope otherwise. A thrown isError reaches the script as a rejected call. A returned ValidationError is turned into a throw by the isValidationError check in the dispatcher. The model sees the code-mode tool’s own { success, result, logs, error } object.

Studio renders the stored tool output. useMcpAppTools (client-sdks/react/src/hooks/mcps/use-mcp-app-tools.ts) maps tools whose definition has _meta.ui.resourceUri, and ToolCard (packages/playground-ui/src/domains/chat/tools/tool-card.tsx) mounts McpAppToolResult for them. McpAppViewer (packages/playground-ui/src/domains/mcps/components/mcp-app-viewer.tsx) passes an envelope through and wraps any other value as content: [{ type: 'text', text }], with text the string itself or JSON.stringify(toolResult), and adds structuredContent: toolResult when the value is a non-array object. An app receives a structured object result as both a JSON text block and structuredContent, and an array or scalar as the JSON text block only. An app’s ui/update-model-context request goes through modelContextText in the same file, which joins the app’s text blocks and JSON.stringify(params.structuredContent) under a Context from the "${toolName}" MCP App shown in this conversation: line and hands it to the chat’s setModelContext for the next turn. getMastraToolStrictMeta (packages/mcp/src/shared/mastra-tool-meta.ts) reads _meta.mastra.strict from the tool definition to set strict. No result _meta key changes what reaches the model.

useMcpAppTools reads tool definitions from client.getMcpServers(), which lists the MCP servers registered on the Mastra instance (mastra.listMCPServers() in packages/server/src/server/handlers/mcp.ts). _meta.ui.visibility is honoured. isModelVisible in packages/mcp/src/client/configuration.ts drops tools whose visibility array lacks 'model' from listTools, listToolsets, listToolDefinitions, their WithErrors variants and toolsFromDefinitions, so the model is not given app-only tools. The single-tool toolFromDefinition does not filter. In Studio, useMcpAppToolCall (packages/playground-ui/src/domains/mcps/hooks/use-mcp-app-tool-call.ts) refuses an app’s call to a tool whose visibility array lacks 'app'. useMcpAppTools reads only _meta.ui.resourceUri. stampServerIdInMeta in packages/mcp/src/client/client.ts adds ui.serverId to tool and result _meta and touches no other key.

Agent tool hooks see the execute return and cannot change it after the call. wrapToolWithHooks in packages/core/src/agent/agent.ts passes output to afterToolCall and ignores its return value. beforeToolCall can return { proceed: false, output }, which skips the MCP call and returns output in its place. Input processors can rewrite what the model gets. processInputStep receives the message list, and processLLMRequest (packages/core/src/processors/index.ts) receives the converted LanguageModelV2Prompt, with modelOutput already substituted, and may return a modified copy (runProcessLLMRequest in packages/core/src/loop/workflows/agentic-execution/llm-execution-step.ts). Tool payload transforms (ToolPayloadTransform in packages/core/src/tools/types.ts) target display and transcript, and MessageList builds the prompt with transformToolPayloads: false.

The switches that change which field the model gets are the declared outputSchema and the onToolError option. The other MCPClient server options in packages/mcp/src/client/types.ts (requireToolApproval, jsonSchemaValidator, tasks, forwardInstructions and the rest) do not touch the result routing.

History keeps the execute return as the tool invocation result and the mapped value at providerMetadata.mastra.modelOutput. Replay uses the stored modelOutput, so a reloaded thread sends the model what the live turn sent.

MCP tasks: a task’s final result takes the same return path, without the SDK check

The per-server tasks option (packages/mcp/src/client/types.ts, experimental, off by default) declares the Tasks extension (SEP-2663). interceptTaskResults in packages/mcp/src/client/tasks/intercept.ts rewrites a resultType: "task" response into a CallToolResult with isError: true and the handle under _meta['mastra.ai/mcp-task'], which keeps the SDK from applying the output schema. execute reads the handle with takeTaskHandle, awaitToolTask polls until a terminal status, and a completed task’s terminal.result goes through the same finishToolCall as a direct result, so the three return values above apply. The SDK does not validate that result. Mastra’s check in finishToolCall runs when structuredContent is present, and a result without it returns as the envelope. A failed or cancelled task throws MCP_CLIENT_TOOL_TASK_FAILED or MCP_CLIENT_TOOL_TASK_CANCELLED. A task that reaches input_required with no inputRequests handler configured suspends the call when the agent or workflow can suspend, and execute returns undefined. The resumed call answers the task and its result takes the same finishToolCall path.

With tasks set, taskToolBackgroundConfig gives the tool background: { enabled: true, defaultDisposition: 'deferred', maxRetries: 0, ... }, so on an agent with background tasks enabled the executor runs off the agent loop. applyBackgroundToolResult (packages/core/src/loop/shared/steps/background-task-result-core.ts) then replaces the placeholder result, runs toModelOutput on the real result, and overwrites providerMetadata.mastra.modelOutput. For a deferred task, tool-call-step.ts then calls agent.__notifyBackgroundTaskFinished, which, unless an untilIdle stream for the thread already handles the task or notifyAgentOnFinish is false, sends the thread a background-task notification signal naming the task, tool call and status but not the result.

Protocol revision: negotiated by the SDK in auto mode unless pinned per server

negotiationMode in packages/mcp/src/client/client.ts maps an absent protocolVersion to 'auto', 'legacy' to 'legacy', and anything else to { pin: protocolVersion }, passed to the SDK as versionNegotiation: { mode }. MCPClientProtocolVersion in packages/mcp/src/client/types.ts allows only MCP_CLIENT_PROTOCOL_VERSION = '2026-07-28' or 'legacy'. In auto mode the SDK probes with server/discover and falls back to the initialize handshake, whose LATEST_PROTOCOL_VERSION is '2025-11-25' (packages/core/src/constants.ts in the SDK). assertCurrentRevision fails subscriptions/listen when a different revision was negotiated.

Upstream history: the schema-gated mapper and the resource-text filter

The toModelOutput mapper came in through mastra-ai/mastra#20176, merged 2026-08-07, fixing issue #20168, which reported that the model received a large structured payload where it should receive the text of content. Both cite the specification’s description of the two fields. The PR body: "Per the MCP specification, content is the LLM-facing channel while structuredContent is intended for client/UI consumption." The costs named are tokens and the MCP Apps pattern of a short summary in content with the data in structuredContent. #27131, merged 2026-10-15, widened extractModelTextFromToolContent to embedded resource text after the GitHub MCP server added an outputSchema to its file tool and an agent could no longer read a file through mastra.

Quirks

The gate in finishToolCall is res.structuredContent !== undefined, so {} and null take the structured path while a missing field returns the envelope. A scalar or null structuredContent on a tool with an outputSchema reaches the model as { type: 'json' } even when content has text. attachMcpCallToolContent stores content only on objects and arrays, so createStructuredToolToModelOutput finds no hidden text for a scalar and falls back to the structured value (packages/mcp/src/client/client.ts). This applies on 2026-07-28 only, since on 2025-11-25 the SDK rejects a non-object structuredContent before execute sees it.
