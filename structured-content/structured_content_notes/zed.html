Ola’s MCP Tool Result Research

How zed handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the Zed source (clones/zed, checked out at commit 0cfc4a4, read on 2026-11-14). Zed’s own version is 1.30.0 (crates/zed/Cargo.toml). File references are relative to crates/.

Entry: results enter through a hand-rolled serde client; the type keeps structuredContent

Zed uses no MCP SDK. The context_server crate (context_server/Cargo.toml) depends on serde, serde_json and schemars and implements JSON-RPC itself. Client::request_with in context_server/src/client.rs parses the wire frame into AnyResponse, then deserializes the result field with serde_json::from_str(result.get()) into whatever type the caller asks for. For tools/call that type is CallToolResponse in context_server/src/types.rs, which has four fields: content: Vec<ToolResponseContent>, is_error: Option<bool>, meta (renamed from _meta) and structured_content: Option<serde_json::Value> with #[serde(default)]. The field is kept after parsing. content has no serde default, so a result that omits the key fails deserialization and the call returns an error. ToolResponseContent is an internally tagged enum with text, image, audio, resource and resource_link variants and no catch-all, so an unknown block type is also a deserialization error.

Model path: content only, structuredContent never read

The only client-side tools/call request is in ContextServerTool::run in agent/src/tools/context_server_registry.rs. It sends CallToolParams { name, arguments, meta: None }. On return it reads response.is_error and response.content and nothing else. response.structured_content and response.meta have no read sites anywhere under crates/; the only other occurrences of structured_content are the server half in context_server/src/listener.rs, test fixtures in agent/src/tests/mod.rs, and an unrelated ACP field structured_content: Vec<ToolCallContent> on acp_thread::ToolCall in acp_thread/src/acp_thread.rs.

When both fields are present, the model receives the content blocks and the structured payload is dropped. When content is empty and structuredContent is present, run produces an empty llm_output, and AgentMessage::to_request in agent/src/thread.rs, reached from Thread::build_request_messages, substitutes a fixed string: tool_result.content = vec!["<Tool returned an empty string>".into()];, guarded by is_content_empty() from language_model_core/src/request.rs. A result with only structuredContent and no content key fails to deserialize before any of this runs.

The outcome is the same whether the text mirrors structuredContent exactly or differs from it, because run never compares the two. No step removes a duplicate. structuredContent does not appear in the model request in any form. Non-text blocks do not change which field reaches the model.

No variant of ToolResponseContent in context_server/src/types.rs declares an annotations field, and the enum does not use deny_unknown_fields, so annotations.audience on a tool result block is discarded during deserialization. A text block annotated audience: ["user"] reaches the model like any other text block. The only reads of MCP audience under crates/ are on the prompts path (see Quirks).

Per block, run does the following. Text is pushed to llm_output as LanguageModelToolResultContent::Text, pushed to the ACP tool call content, and appended to concatenated_text. Image is pushed to the ACP content and converted with LanguageModelImage::from_base64_image; a conversion that returns None or an error is logged with log::warn! and the image is skipped on the model path. Audio, Resource and ResourceLink each hit a log::warn!("Ignoring ... content from tool response") and reach neither the model nor the UI. LanguageModelToolResultContent has exactly two variants, Text and Image. If the model does not support images, Thread::run_tool replaces each image part with the string [Tool responded with an image, but this model doesn't support images] when other parts exist, and returns an error result when the output was image-only. raw_output on AgentToolOutput is serde_json::Value::String(concatenated_text), the joined text blocks, so the ACP rawOutput channel also carries text only. An is_error result becomes an Err whose message is the concatenated text blocks.

outputSchema: deserialized from tools/list, zero read sites

Tool in context_server/src/types.rs declares pub output_schema: Option<serde_json::Value> with #[serde(default)], and ContextServerRegistry::reload_tools_for_server stores each Tool from ListToolsResponse whole inside a ContextServerTool. The only client-side read sites on Tool are name, description and input_schema (ContextServerTool::name, description, input_schema). A grep for .output_schema across crates/ returns no hit outside tests and the server-side listener.rs. Nothing validates structuredContent against it, and it is not folded into the tool description or any prompt text.

With no validation step there is no failure text for the model.

Other paths: none for results; MCP servers can be delegated to external agents

There is no code mode, sandbox or MCP Apps route for tool results in the native agent. ContextServerTool::replay is a no-op. _meta on the response is parsed into CallToolResponse::meta and never read, so no flag in it changes routing. Per-server configuration is the ContextServerSettings enum in project/src/project_settings.rs (enabled, remote, command, url, headers, timeout, oauth) and per-profile ContextServerPreset { tools: IndexMap<Arc<str>, bool> } in agent_settings/src/agent_profile.rs, which toggles tools on or off and does not affect result handling.

A grep for resourceUri, ui/ and visibility in context_server/src, agent/src and agent_ui/src finds no MCP Apps code, so _meta.ui.visibility is not read. No Rust file under agent/src or agent_settings/src matches hook or hooks, apart from the eval fixture agent/src/tools/evals/fixtures/disable_cursor_blinking/before.rs, which references command_palette_hooks. The extension API in extension_api/src/extension_api.rs exposes context_server_command and context_server_configuration, which supply the launch command and settings for a server. A grep for CallToolResponse across crates/ returns only context_server/src/types.rs, context_server/src/listener.rs and agent/src/tests/mod.rs, so no extension or plugin code receives a tool result.

A separate route exists for external ACP agents. AcpV2Connection in agent_servers/src/acp/v2.rs converts Zed’s configured servers into acp::McpServer::Stdio and acp::McpServer::Http entries and passes them in SessionContext::mcp_servers; AcpConnection in acp/v1.rs does the same through mcp_servers_for_project. The external agent then connects to those servers itself, and Zed sees only the ACP tool call updates it reports.

Zed also ships a server half. listener.rs derives output_schema with schemars from the tool’s Output type and emits structured_content in the CallToolResponse it returns on success, as None when the handler’s result is null or an error; output_schema is omitted when Output is ().

Protocol revision: 2025-11-25 requested, four versions accepted

LATEST_PROTOCOL_VERSION: &str = "2025-11-25" in context_server/src/types.rs. ModelContextProtocol::initialize in context_server/src/protocol.rs sends that value and accepts any of supported_protocols(), which lists 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05, failing with Unsupported protocol version otherwise. The negotiated version is set on the transport via set_protocol_version for the MCP-Protocol-Version HTTP header.

Upstream history: field added for the server half, no recorded rationale for the client

The clone is shallow (one commit), so history comes from the GitHub API. structured_content was added to CallToolResponse by zed-industries/zed#35068, "Add ability to register tools in McpServer“, merged 2025-07-25, for the server half. Its body reads: ”Instead of manually handling all tool-related requests, we can now directly register tools that implement a new trait in McpServer". output_schema was added to Tool by #35069, “McpServerTool output schema”, merged the same day, whose body reads: "Add an Output associated type to McpServerTool, so that we can include its schema in tools/list." The client loop that reads only response.content and logs Ignoring image content from tool response for other blocks first appears in agent2/src/tools/context_server_registry.rs in #36034, “Support profiles in agent2”, merged 2025-08-12, whose body is “We still need a profile selector.” Later changes to the same loop are #47095 (merged 2026-02-12, checks is_error) and #57134 (merged 2026-05-19, “Support image output from MCP tools”); neither body mentions structuredContent. The earlier agent/src/context_server_tool.rs used before agent2 was not traced. #55722, which would have kept outputSchema in listener.rs tool listings for external agents (issue #55642), was closed unmerged on 2026-05-05.

Searched: gh search prs and gh search issues in zed-industries/zed for structuredContent, structured_content, structured content, outputSchema, output_schema, structured output MCP tool and Tool returned an empty string, and the commit lists from gh api for context_server/src/types.rs, agent/src/tools/context_server_registry.rs, agent2/src/tools/context_server_registry.rs and agent/src/context_server_tool.rs. No PR or issue records a reason for leaving structuredContent off the model path.

Quirks

MCP audience is read only for prompts. MessageContent in context_server/src/types.rs, used for prompts/get messages, carries annotations: Option<MessageAnnotations> with audience, and mcp_annotations_to_acp in agent/src/agent.rs copies it onto the ACP content blocks built from prompt messages. Tool result blocks have no such field.
