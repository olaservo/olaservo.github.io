Ola’s MCP Tool Result Research

How eve handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the eve source (clones/eve, checked out at commit be1adda, read on 2026-11-14). File references are relative to packages/eve/src/ in the clone root unless they start with docs/. The MCP client wrapper is runtime/connections/mcp-client.ts, the deciding function is toConnectionToolResult in runtime/connections/tool-result.ts, and the catalog entry that joins them is execution/catalog/connection-entry.ts. The SDK and provider code is not in the clone. It was read from the published packages at the versions in pnpm-lock.yaml: @ai-sdk/mcp@2.0.99, ai@7.0.172, @ai-sdk/anthropic@4.0.104, @ai-sdk/openai@4.0.117, @ai-sdk/google@4.0.120.

Entry: results enter through @ai-sdk/mcp and arrive unchanged at toConnectionToolResult

eve has one conversational MCP client path. McpConnectionClient in runtime/connections/mcp-client.ts wraps createMCPClient from @ai-sdk/mcp, compiled into eve with three transport and handshake patches listed in packages/eve/scripts/vendor-compiled/@ai-sdk/mcp.mjs. None of the patches touches result parsing. It tries the http transport and falls back to sse on status 400, 404 or 405 (isMcpHttpFallbackRetryableError). runtime/connections/events/actions.ts opens a second createMCPClient for experimental.events catalog and subscribe calls, which send no tools/call.

#fetchToolsInner calls client.toolsFromDefinitions({ tools: projectedTools }). McpConnectionClient.executeTool runs that tool’s execute and returns its result. In @ai-sdk/mcp (dist/index.js), callTool parses the response with CallToolResultSchema, a union of three shapes. CallToolResultWithContentSchema requires a content array and keeps structuredContent as optional unknown. CallToolResultWithStructuredContentSchema accepts a result with no content key and synthesizes one block: text: JSON.stringify(result.structuredContent). The third accepts a legacy toolResult. A result with neither a content array nor structuredContent matches none of the three, and request throws MCPClientError with “Failed to parse server response”. eve passes that error through, so the model gets the error-text output MCPClientError: Failed to parse server response. The base schema is loose, so _meta and unknown keys survive. No field is dropped at this layer. The SDK’s own mcpToModelOutput is attached to the tool but eve never calls it, because eve takes only sdkTool.execute.

runConnectionTool in execution/catalog/connection-entry.ts then does const result = toConnectionToolResult(connection.protocol, tool, raw);, throws on !result.ok, and returns result.value. Everything after this point sees only that value. The _meta object, isError, and whichever field lost are gone for every later consumer.

Model path: structuredContent replaces the text blocks, and any non-text block replaces structuredContent

toConnectionToolResult decides the result in this order:

const blocks = Array.isArray(raw.content) ? raw.content.filter(isMcpContentBlock) : [];
...
if (raw.isError === true) { ... return { ok: false, error: detail }; }
if (blocks.some((block) => block.type !== "text")) return { ok: true, value: blocks };
if (raw.structuredContent !== undefined) return { ok: true, value: raw.structuredContent };
if (tool.outputSchema === undefined) return { ok: true, value: parseJsonText(text) };
return { ok: true, value: text };

With both fields present and only text blocks, the value is structuredContent and every text block is dropped. The test is !== undefined, so {} and null also replace the text. With content empty or absent and structuredContent present, the value is the same structuredContent. So the model sees the same thing whether or not the server wrote the text mirror. No code compares the text with structuredContent, so the text is dropped whether it mirrors the JSON or differs from it.

With both fields present and any image, audio, resource or resource_link block, the value is the block list and structuredContent is dropped. The text blocks in that list are kept. This is the only success case where a result carrying structuredContent puts server text in front of the model.

With no structuredContent and text only, the joined text ("\n") is parsed by parseJsonText when the tool declares no outputSchema and the trimmed text starts with { or [. A tool that declares a schema keeps the string. A result with an empty content array and no structuredContent gives the empty string. eve substitutes no placeholder for it. connectionToolModelOutput returns { type: "text", value: "" }, and the text branch of toolModelOutputSchema in harness/tool-model-output.ts is z.string() with no minimum. A grep of harness, execution and runtime for empty-result or no-output wording finds no substitution. What each provider package sends for an empty string was not checked.

isError: true becomes { ok: false, error }, where the error is the joined text, else JSON.stringify(raw.structuredContent), else The tool reported an error.. runConnectionTool throws it, and harness/call-executor.ts writes { type: "error-text", value: failure } with failure = modelFacingError(error), so the model reads Error: <detail>.

connectionEntry sets toModelOutput: connectionToolModelOutput. toolCallModelOutput in harness/tool-call-io.ts calls it from harness/call-executor.ts, and normalizeToolModelOutput in harness/tool-model-output.ts validates the shape. connectionToolModelOutput maps a non-text block list to { type: "content", value }, a string to { type: "text", value }, and anything else to { type: "json", value: output ?? null }. isMcpContentBlockList tests the value’s shape, so a structuredContent array whose items look like MCP blocks with at least one non-text also becomes content parts. A string structuredContent goes as text. docs/connections/mcp.mdx states "MCP connections have no per-result transform like an authored tool’s toModelOutput".

Non-text blocks are mapped in toModelOutputParts. image and audio become file parts when data and mimeType are strings. An embedded resource with blob becomes a file part with filename set to its URI. An embedded resource with text becomes a text part holding ${uri}\n${resource.text}. A resource_link becomes the text Resource link: ${name} ${uri}. A block type outside MCP_CONTENT_TYPES is filtered out at the top of toConnectionToolResult. If the mapping leaves no parts, the .min(1) in toolModelOutputSchema rejects it and the call settles as a failure.

File parts do not stay inline. stageToolResultMedia in harness/attachment-staging.ts, called from harness/step/intake.ts and harness/step/after-model.ts, writes each one to the sandbox under .eve/attachments and stores an eve-sandbox: reference in history. With no active sandbox, or a failed write, the part becomes the text Returned file ${filename} (${mediaType}) could not be stored.. hydrateToolOutput runs for each model call in harness/model-call/call.ts: it renders a text label naming the sandbox path, followed by the bytes only when inlinesSandboxRefAsBytes allows it. That covers images in INLINE_IMAGE_MEDIA_TYPES up to 3 MiB and 8000 px, and PDFs up to 20 MiB. Audio and everything else stay as the label.

The answer about which field reaches the model does not vary by backend. The ToolModelOutputValue is fixed before the provider is known, and only the encoding differs. A string model id routes through AI Gateway, which resolveModelProfile in harness/model-profile.ts marks with gateway: true, and the gateway’s own translation is not in these packages. In the direct providers, @ai-sdk/anthropic sends tool_result.content as JSON.stringify(output.value) for json, the string for text, and text, image or document blocks for content, with a warning and no block for other file types. @ai-sdk/openai Responses sends function_call_output holding JSON.stringify(output.value) for json, and input_text, input_image or input_file items for content. @ai-sdk/openai Chat Completions sends JSON.stringify(output.value) for both json and content. eve covers that case with filesOutsideToolResults: provider.endsWith(".chat"): moveToolResultFilesToUserMessages moves files into a following user message and leaves the stub Attached file ... follows this tool result.. @ai-sdk/google sends functionResponse.response.content as the JSON value itself, unstringified, and files as functionResponse.parts or legacy parts. An error-text output goes to @ai-sdk/openai, on both Chat Completions and Responses, as JSON.stringify({ error: output.value }), and to @ai-sdk/anthropic as the string with is_error: true.

capToolResults in harness/compaction/engine.ts caps oversized outputs in the older region of history during compaction, keeping head and tail with the annotation [Truncated by eve: tool result reduced during context compaction. Re-run the tool if you need the full output.]. No size cap applies to an MCP result before that.

outputSchema: never validated, rendered into the signature the model reads, and it switches JSON parsing of text

@ai-sdk/mcp can validate, but eve does not take that branch. In toolsFromDefinitions, const outputSchema = schemas !== "automatic" ? schemas[name]?.outputSchema : void 0;, and the execute body runs extractStructuredContent only when that value is non-null. eve passes no schemas option, so the default "automatic" applies and the result is returned unchecked. A mismatch has no effect, and a tool that declares a schema and returns no structuredContent is also accepted. The only schema validation in execution/catalog/connection-entry.ts is checkCall, on inputs.

#fetchToolsInner copies t.outputSchema into ConnectionToolMetadata.outputSchema. There are two uses. connectionToolSignature in execution/catalog/signatures.ts calls renderToolSignature in tools/signature.ts, which produces ${input.name}(input: ${inputType}): Promise<${outputType}>, with unknown when no schema is declared. That string is the signature field of each eve__search result (toolCandidate in execution/catalog/search.ts) and is appended as Signature: ... to input validation failures in checkCall, so it reaches the model as tool result text. The second use is the tool.outputSchema === undefined test in toConnectionToolResult, covered above. Connection entries are not in the model’s tool list, so the schema is not sent as a provider tool definition: connectionEntry sets deferred: true, description: "", and no outputSchema.

Other paths: no script path exists, hooks and clients read the routed value, and calls through the catalog run the same way

All connection tools are deferred. catalogTools in execution/catalog/catalog-tools.ts, added to the step’s tools by definitions/catalog.ts, supplies eve__search and eve__tool, and catalog.resolve in buildStepCatalog (execution/catalog/step-catalog.ts) turns eve__tool({ name, input }) into a call to connectionEntryNamed's entry, so the toModelOutput above applies. Model history keeps the eve__tool name. There is no direct listing of an MCP tool as a provider tool.

Scripts: there is no code mode. The header of runtime/connections/tool-result.ts says the value is “what the model receives for the call and what a code mode program receives later”, and evals/reported-tool-name.ts says “eve__execute isn’t a tool eve registers (it’s reserved for code mode)”. The provided workflow tool (tools/provided/workflow.ts, execution/dynamic-workflow/program-step.ts) runs model-written JavaScript with a frozen ctx holding only agent, so a program cannot call a connection tool. The only caller of client.executeTool is executeWithDeadline in connection-entry.ts.

Hooks and stream clients: call.settled carries the value from toConnectionToolResult through createRuntimeToolResultFromValue in harness/action-result-helpers.ts, whose comment says "the raw-output-vs-toModelOutput decision — always raw". Hooks read it with call(ctx.view, callId) or toolResultFrom (docs/guides/hooks.md) and cannot change what the model sees. So a hook gets the same field the model got, in raw form, with base64 intact for blocks. The ACP adapter in acp/adapter.ts callOutput sends the same value as rawOutput and stringified text. The text mirror and _meta are unavailable to all of them. The raw CallToolResult is seen only by isMcpAuthChallengeResult and by withMcpToolCallSpan (runtime/connections/mcp-tracing.ts, which calls createMcpTracing in tracing/eve/mcp.ts), which records a JSON result on its span only when output recording is on.

Subagents: callableOf in execution/catalog/step-catalog.ts builds each session’s catalog from ConnectionRegistryKey with the same connectionEntry, so a subagent’s connection call gets the same toModelOutput. docs/subagents says a subagent uses the root’s connections or its own connections/ directory. execution/tasks/render.ts renderModelOutputText flattens a task tool’s output to text with [file: ...] labels, and connection entries are not task tools.

MCP Apps: none. No code under packages/eve/src reads ui://, and eve does not call the SDK’s splitMCPAppTools. A result has no route to an app view.

Server side: public/channels/mcp.ts and internal/mcp/published-tools.ts publish an eve agent’s tools. For a tool with an outputSchema or an object output they emit structuredContent with one text block (published-tools.ts), and add isError: true when the tool’s model output is error-text. When an eve agent connects to another eve agent’s mcpChannel the client path above drops that text.

Switches: toConnectionToolResult takes only the protocol, the tool’s metadata and the raw result, so no connection option changes which field the model gets. The fields of McpClientConnectionDefinition in public/definitions/connections/mcp.ts cover the URL, description, protocol discovery, principal forwarding, auth, instance key, approval, headers, provided input arguments (toolCall), the tool filter (tools) and experimental.events. The tool’s declared outputSchema switches JSON parsing of text-only results, and mcp/www_authenticate under result _meta turns an error into sign-in, both covered in their sections.

audience and _meta: audience is unread, and one result _meta key triggers sign-in

No code reads audience on the result path. toModelOutputParts and toConnectionToolResult never touch block annotations, so a block marked audience: ["user"] reaches the model when the block list wins. The annotations read in mcp-client.ts is the tool-level readOnlyHint family, passed to approval policies by toolAnnotations in connection-entry.ts.

One result _meta key changes behaviour. MCP_WWW_AUTHENTICATE_META_KEY = "mcp/www_authenticate": isMcpAuthChallengeResult in mcp-client.ts returns true for isError: true with a non-empty string or list under that key, and executeTool then calls #requireAuthorization, so the call starts sign-in and the model does not receive the error. No other result _meta key is read.

_meta.ui.visibility is not honoured. listTools in the SDK returns every tool. ConnectionToolMetadata built in #fetchToolsInner has no _meta field, and listToolMetadata in execution/catalog/connection-auth.ts filters only by the connection’s tools.allow or tools.block (passesToolFilter), so a tool with visibility: ["app"] can be found by eve__search and called by the model. The SDK’s getMCPAppToolMeta still runs in toolsFromDefinitions and throws Invalid MCP App resource URI when a resourceUri is not a ui:// string, which fails the connection’s tool listing.

Protocol revision: 2026-07-28 by discovery, then 2025-11-25 by initialize, five revisions accepted

@ai-sdk/mcp sets LATEST_PROTOCOL_VERSION = "2026-07-28", LATEST_LEGACY_PROTOCOL_VERSION = "2025-11-25", and SUPPORTED_PROTOCOL_VERSIONS of 2026-07-28, 2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05. protocolVersionDiscovery defaults to true, and tryProtocolDiscovery sends server/discover under 2026-07-28. The SDK’s HttpMCPTransport sets waitsForProtocolVersionDiscovery, so discovery on HTTP has no 1 s timeout. On an ordinary failure the client falls back to initialize with 2025-11-25. eve’s supported-protocol-version-fallback patch makes error -32022 with data.supported negotiate the newest listed legacy version the client supports, and otherwise rethrows. A connection with protocolVersionDiscovery: false skips discovery and starts at initialize with 2025-11-25 (public/definitions/connections/mcp.ts, docs/connections/mcp.mdx). applyInitializeResult throws Server's protocol version is not supported for anything outside the list.

Upstream history: #3924 sent the text, #4023 made structuredContent the value two days later

runtime/connections/tool-result.ts and toConnectionToolResult arrived with vercel/eve#4023, “feat(eve)!: cache-stable connection_search and connection_execute”, merged 2026-09-30. The PR body says it “moves to code mode’s result format and protocol shape now, so a later code mode only has to replace the entry point.” It lists "Code mode’s result value. connection_execute returns MCP structuredContent or text (JSON-parsed when the tool declares no output schema), MCP media as file parts, and OpenAPI’s { status, statusText, body }.“ Its breaking changes include ”MCP results are no longer the raw envelope." The design is research/connection-execute.md. It is not in the clone at be1adda, whose research/ holds only a2a-channel.md, channel-text-answers.md, native-code-mode.md, recall-channel.md, slack-code-channels.md and stranded-session-revival.md. Its “Result format” table gives the same order. It gives one reason, for keeping blocks: "toModelOutput receives only the output, so a result with non-text content keeps its MCP content blocks in the value." Neither the PR body nor research/connection-execute.md says why structuredContent comes before the text. The review threads on tool-result.ts ask for unit tests of its branches and do not discuss the order.

vercel/eve#3924, “fix(eve): send only MCP content blocks to the model”, merged 2026-09-28, had the model receive the content text through the SDK’s toModelOutput. Its body: "This follows the MCP spec, which defines content as the model-facing result. structuredContent is for clients that want typed data, and servers are expected to repeat it as text in content.“ It gives the cost of sending the raw result: ”The data is there twice, once JSON-escaped." #4023 removed the connection_search tool path that #3924 changed, and its body does not mention #3924. A review on #3924 asked that an error with empty content and structuredContent keep a failure marker, and the fix returned Tool call failed: followed by the JSON.

vercel/eve#4400, “feat(eve): deferred tools and skills”, merged 2026-10-08, changed only the header comment of tool-result.ts. research/native-code-mode.md in the clone root lists under “What we take”: "From opencode: execute as the name, catalog changes delivered as appended messages, and MCP result handling (structuredContent, otherwise text parsed as JSON, and isError throws), which eve already matches." vercel/eve#2854, closed unmerged on 2026-09-01, would have synthesized a text block for Shopify’s catalog MCP results that carry structuredContent and no content.
