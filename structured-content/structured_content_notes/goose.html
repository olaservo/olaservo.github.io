Ola’s MCP Tool Result Research

How goose handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the goose source (clones/goose, checked out at commit 2365bc5, read on 2026-11-14). File references are relative to crates/ in the clone root. goose is version 1.59.0 per the workspace Cargo.toml.

Entry: results enter through rmcp 3.9.0 and keep structuredContent

The workspace Cargo.toml pins rmcp = { version = "3.9.0", default-features = false, features = ["schemars"] } and Cargo.lock resolves it to 3.9.0. There is no hand-rolled transport; goose/src/agents/mcp_client.rs wraps an rmcp client and its McpClientTrait::call_tool returns Result<CallToolResult, Error> using rmcp::model::CallToolResult. That struct carries content: Vec<ContentBlock>, structured_content: Option<Value>, is_error and meta, so the field survives deserialization. goose stores the whole value: goose-provider-types/src/conversation/message.rs defines pub struct ToolResponse { ... pub tool_result: ToolResult<CallToolResult> } and the state machine’s ToolBatch::record in goose/src/agents/state_machine/ops_toolcalling.rs pushes it into a user message with add_tool_response_with_metadata. tool_result_serde::call_tool_result serializes the full struct as {"status":"success","value":<CallToolResult>}, so structured_content is persisted in the sqlx session store and comes back on resume. The rmcp 3.9.0 source was read from the crates.io package (rmcp-3.9.0/src/model.rs), since the clone has no vendored copy. Its hand-written Deserialize for CallToolResult defaults a missing content key to [] ("Defaults content to [] when the field is missing (lenient per Postel’s law)") and fails the result only when content, structuredContent and isError are all absent (_meta does not count), so a result carrying only structuredContent parses with an empty content vector. A result with none of the three fields ({}, or {"resultType":"complete"} on 2026-07-28) does not parse as CallToolResult, so rmcp’s untagged ServerResult union matches a later variant (TaskAckResult or EmptyResult) and both branches of GooseClient::call_tool in goose/src/agents/mcp_client.rs return ServiceError::UnexpectedResponse (“Unexpected response type”). call_resolved in goose/src/agents/extension_manager/lease.rs turns that into ErrorData with code -32603, and the provider formatters send the error to the model as tool-result text: "The tool call returned the following error:\n{}" in formats/openai.rs, "Error: {}" with is_error: true in formats/anthropic.rs. tool_result_serde stores an error as err.to_string() and reads it back as ErrorData with code -32603 and that string as the message, so the code appears twice: observed with goose 1.58.0 (4facf56) as -32603: -32603: Unexpected response type in probe/runs/goose@1.58.0/default/both-stdio/tools.result.empty_object/model.jsonl in canimcp.

Model path: content only, filtered by audience, placeholder when empty

There is one agent loop at this commit. StateMachineServices::reply in goose/src/agents/services.rs calls start_reply, which ends with self.turn(session_config, cancel, turn_guard, true), turn calls run_machine, which builds the machine with create_state_machine, and run_live_delegation in goose/src/acp/server/live_voice.rs goes through the same reply; no flag selects another loop. The state machine’s inference step (goose/src/agents/state_machine/ops_llm.rs) delegates to the goose-agent crate (goose-agent/Cargo.toml describes it as “The GDK’s Agent Loop”) and both paths reach the provider through stream_response_from_provider in goose/src/agents/reply_parts.rs, which projects messages with Conversation::agent_visible_messages() and then runs fix_conversation. The goose-agent crate’s own InferenceRunner::infer in goose-agent/src/inference.rs applies the same two calls.

agent_visible_messages maps each message through Message::agent_visible_content, which calls filter_for_audience(Role::Assistant) on every block. For a ToolResponse, MessageContentBlock::filter_for_audience in goose-provider-types/src/conversation/message.rs rebuilds the result with tool_result.content = filtered_content, dropping blocks whose annotations.audience excludes Assistant, and copies the rest of the struct, so structured_content rides along unread. A block with audience: ["user"] does not reach the model, and a block with no annotations or no audience does (.unwrap_or(true) on the missing case). fix_conversation then runs fix_empty_tool_results in goose-provider-types/src/conversation.rs: when has_tool_result_content finds no non-empty text, resource text or image, it pushes ContentBlock::text("(empty result)").

Every provider formatter reads result.content alone. goose-provider-types/src/formats/anthropic.rs iterates result.content.iter() into text, image and PDF document blocks, joining text with "\n" when no media is present; formats/openai.rs does the same and joins text with a space, replacing images with a placeholder sentence and a separate user message when options.supports_vision, and otherwise with the sentence This tool result included an image that was omitted as the model does not support vision.; supports_vision comes from the model config or goose’s canonical model registry (goose-provider-types/src/model.rs) and is false for a model in neither (model_config.supports_vision.unwrap_or_default()); formats/google.rs builds a functionResponse from text plus inline media; goose/src/providers/formats/bedrock.rs maps blocks through to_bedrock_tool_result_content_block and returns an error for Audio and blob resources. The identifier structured_content appears in none of these files. Consequently, when both fields arrive the model sees content and nothing from structuredContent; when content is empty and structuredContent is present the model sees (empty result); a result with only structuredContent is the same case. Non-text blocks: text resources inline as text, images pass to vision-capable providers, Audio and ResourceLink fall through the Anthropic and OpenAI catch-alls and are dropped, while Bedrock renders ResourceLink as the text [Resource link] and returns an error for Audio. Before formatting, large_response_handler::process_tool_response in goose/src/agents/large_response_handler.rs rewrites any text block over GOOSE_MAX_TOOL_RESPONSE_SIZE characters (default DEFAULT_LARGE_TEXT_THRESHOLD: usize = 200_000) into a file pointer sentence and passes other blocks and the rest of the struct through unchanged. Because structuredContent never enters the request, goose has no duplicate-removal step for text that mirrors the JSON, and no serialized form of structuredContent (compact, pretty or enveloped) exists on the model path. A mirrored text block reaches the model once, as content text. No block type changes which field reaches the model, since no formatter has a branch that reads structured_content.

outputSchema: stored, never validated, exposed to code mode and ACP clients

rmcp deserializes tools/list into rmcp::model::Tool with output_schema, and goose keeps the list. No goose code validates structured_content against it; the only output_schema reads are function_details in goose/src/agents/platform_extensions/code_execution.rs, which emits "output_schema": tool.output_schema in the get_function_details tool’s JSON reply, and goose/src/acp/server/tools.rs, which copies it onto ToolListItem.output_schema for the _goose/unstable ACP tools listing. rmcp 3.9.0’s CallToolResult docs state “we don’t need to do json schema validation here”, so the SDK does not validate either. The schema is not appended to tool descriptions or the system prompt. The provider tool declarations carry input_schema only: formats/anthropic.rs sends "input_schema", formats/openai.rs, formats/openai_responses.rs and formats/databricks.rs send "parameters": tool.input_schema, formats/google.rs sends parametersJsonSchema, and formats/snowflake.rs sends "input_schema". No file under goose-provider-types/src/formats/ references output_schema. With no validation there is no failure text for the model.

Other paths: code mode reads content, ACP and the desktop get structuredContent

Code mode is the code_execution platform extension. Its callback_result_to_value in code_execution.rs joins content text blocks whose audience is absent, empty, or includes Role::Assistant with "\n" and runs serde_json::from_str(&text).unwrap_or(Value::String(text)); it never reads structured_content, and the unit test callback_result_ignores_hidden_structured_content_and_meta asserts that. This refutes the earlier survey claim that the sandbox prefers structuredContent.

The ACP surface forwards it. extract_tool_raw_output in goose/src/acp/server/tool_calls/conversion.rs returns result.structured_content.clone() and tool_call_update_fields_from_response places it in fields.raw_output, while build_tool_call_content maps content text, image and embedded resource blocks and returns None for Audio and ResourceLink. The _goose/unstable/tools/call custom request in goose/src/acp/server/tools.rs returns GooseToolCallResponse { content, structured_content: result.structured_content, is_error, meta }. The desktop adapter ui/desktop/src/acp/adapter/tools.ts sets toolResult.structuredContent = update.rawOutput and ui/desktop/src/acp/mcp-apps.ts passes it to the MCP Apps iframe.

_meta drives routing. A tool whose _meta.ui.resourceUri is set (get_tool_resource_uri in goose/src/agents/extension_manager/mod.rs) is excluded from the code-mode catalog, and after its call McpAppCall::attach_resource in extension_manager/lease.rs reads the ui:// resource and inserts it under __goose_tool_update_meta; remove_untrusted_mcp_app_meta strips any server-supplied copy of that key first. Tools with _meta.ui.visibility lacking "model" are hidden from the model by is_tool_visible_to_model in reply_parts.rs. A result’s _meta.platform_notification becomes a server notification. PostToolUse hooks receive tool name and input only; HookContext::with_tool_output in goose/src/hooks/mod.rs has no caller on the MCP path. Post-tool hooks cannot change what the model gets: with_hooks_and_recording in goose/src/agents/state_machine/ops_toolcalling.rs records the result into the ToolBatch before it calls emit_post_tool_hooks in goose/src/agents/state_machine/tool_hooks.rs, which runs emit_post_tool_use, and HookManager::emit returns (). gen_ai_telemetry::successful_tool_result_json serializes the whole CallToolResult to a span field when OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT is true. The CLI renderer in goose-cli/src/session/output.rs skips blocks whose audience excludes Role::User. No per-server config field changes any of this.

Protocol revision: 2026-07-28 preferred, 2025-11-25 fallback

GooseMcpClientCapabilities.protocol_version is None by default (StateMachineServicesConfig sets mcp_protocol_version: None in services.rs), and GooseClient::get_info in mcp_client.rs calls .with_protocol_version(self.capabilities.protocol_version.clone().unwrap_or_default()). The connection itself is negotiated in McpClient::connect: with no configured version it uses rmcp’s ClientLifecycleMode::Auto with preferred_versions: vec![ProtocolVersion::V_2026_07_28, ProtocolVersion::V_2025_11_25] and legacy_version: Some(ProtocolVersion::V_2025_11_25); with a configured version at or above STANDARD_HEADERS it uses Discover { preferred_versions: vec![protocol_version] }, otherwise Initialize. Two overrides exist: connect_with_legacy_retry in extension_manager/streamable_http.rs retries with ProtocolVersion::V_2025_11_25 after an empty discovery stream, and the mcp-probe CLI command’s McpProbeScript.protocol_version in goose-cli/src/cli.rs sets it explicitly. When the server negotiates V_2026_07_28, call_tool copies session and trace context into params.meta.

Upstream history: the audience filter, code mode, and the maintainer’s position

The clone is shallow (one commit, 2365bc5), so git log and git blame do not reach the history. The PRs below were found with gh search prs and gh search issues for structuredContent, structured_content, audience and callback_result in aaif-goose/goose, and the commit list for crates/goose/src/conversation/message.rs. No PR was found that chose content for the provider formatters, and none that made them read structured_content.

filter_for_audience came in with #6646, merged 2026-01-22, for compaction. Issue #6703 reported the developer shell tool’s output reaching the model twice, once per audience-tagged block: "The audience annotation should filter content so only assistant-targeted content goes to the model, but currently both are included.“ #6773, merged 2026-01-28, and #6728, merged 2026-01-29, fixed it. #6728’s summary reads ”Move filtering to stream_response_from_provider() so providers receive pre-filtered messages."

Code mode: #6190, merged 2025-12-19, made the sandbox “Prioritize structuredContent from MCP response when available”, because "JS code like result.content returned undefined because the MCP structuredContent field was ignored.“ #11471, ”fix(security): restrict code mode callback output", merged 2026-08-26, removed that branch and added callback_result_ignores_hidden_structured_content_and_meta. Its summary: “Restrict Code Mode nested-tool results to assistant-visible text blocks” and “Preserve JSON parsing for visible text while excluding structured metadata and non-text content.” #11744, open, would “treat an explicitly empty audience as hidden” in code mode.

ACP and the desktop: issue #10125 reported structuredContent missing from the tool result an MCP App received, and #10128, merged 2026-07-02, passes rawOutput through as structuredContent in the desktop.

The maintainer’s stated position is on open issue #13182, filed 2026-10-27 against v1.56.0, which reports a server sending content: [] with structuredContent and the model receiving nothing. DOsinga replied on 2026-10-29: “This is not a Goose bug under the MCP spec as written.” and "So a server that expects its result to be visible to models needs to mirror it into content. Goose forwarding only content to providers preserves that distinction and avoids sending structured client/application data to the model unexpectedly."

Quirks

An explicitly empty audience: [] is dropped on the model path, because filter_for_audience keeps a block only when roles.contains(&audience), while callback_result_to_value in code mode keeps it (audiences.is_empty() || audiences.contains(&Role::Assistant)).

rmcp 3.9.0 holds structured_content as Option<Value> and keeps a present structuredContent: null as Some(Value::Null), distinct from a missing field. A null-only result therefore parses as a CallToolResult (empty content, so the model sees (empty result)), and extract_tool_raw_output passes the null to ACP raw_output.

With GOOSE_TOOL_DEFERRAL=lookup (and code mode off), inference_tools in goose/src/agents/state_machine/ops_toolcalling.rs withholds non-platform MCP tools not listed in GOOSE_TOOL_DEFERRAL_ALWAYS_LOAD and adds a built-in enable_tools tool. Its handler returns CallToolResult::structured(serde_json::json!({"enabled": params.tool_names})), and enabled_tools re-derives the enabled set from the conversation by reading result.structured_content of those responses (value["enabled"].as_array()). This is goose’s own result, not a server’s; it reaches the model through content like any other, and the state-machine test deferred_tools_follow_the_conversation_lifecycle matches the model input on "enabled":["calculator__add"].
