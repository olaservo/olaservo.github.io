Ola’s MCP Tool Result Research

How deepagents handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the deepagents source (clones/deepagents, checked out at commit a93aed4bca3a5e4d45bff393e16092222767e6c3 (a93aed4), read on 2026-11-14). File references are relative to libs/ unless they name a dependency file. Dependency references are to the wheels pinned in code/uv.lock, read from downloads whose sha256 matches the lockfile: langchain 1.5.0 (langchain/mcp/), langchain-core 1.8.0, langgraph-prebuilt 1.1.0, fastmcp 4.1.2 (a metapackage over fastmcp-slim 4.1.2), mcp 2.3.0 and mcp-types 2.3.0. code/pyproject.toml declares "fastmcp>=4.0.0b4" and "mcp>=2.0.0". langchain-mcp-adapters is not in the lockfile.

Entry: results enter through a FastMCP router and langchain.mcp, typed as a FastMCP CallToolResult

code/deepagents_code/mcp_tools.py _mount_backends opens one StatefulProxyClient per configured server, calls backend.list_tools(), wraps each backend with create_proxy plus MCPBackendMiddleware (code/deepagents_code/mcp_proxy.py), mounts it on a local FastMCP(name="deepagents-code") router under namespace=name.encode().hex(), and returns FastMCPClient(router). _build_mcp_tool passes each discovered tool to as_langchain_tool(routed_tool, client) from langchain.mcp. In langchain mcp/tools.py, the tool coroutine calls client.call_tool(tool.name, arguments, raise_on_error=False), or _call_tool_with_interrupts (mcp/elicitation.py) when _drives_interrupts finds the client armed by MCPAdapter; deepagents passes FastMCPClient(router) and never uses MCPAdapter, so it takes client.call_tool. The result is the FastMCP CallToolResult dataclass (fastmcp/client/client.py), with content, structured_content, meta, data and is_error. On the backend hop, ProxyTool.run in fastmcp/server/providers/proxy.py calls client.session.call_tool (modern backends) or client.call_tool_mcp (legacy backends) and returns ToolResult(content=..., structured_content=..., meta=..., is_error=...), so structuredContent survives both hops. The stateless branch, _make_stateless_tool in mcp_tools.py, reloads the server through _load_tools_from_config on each call and runs the same adapted coroutine.

content is a required field on CallToolResult in mcp-types mcp_types/_types.py and in both wire models (mcp_types/_v2025_11_25/__init__.py, mcp_types/_v2026_07_28/__init__.py). mcp client/session.py ClientSession.send_request runs _methods.validate_server_result(method, version, raw) against the negotiated revision and then validates against the CallToolResult | InputRequiredResult adapter, so a result without content raises pydantic.ValidationError in the session that receives it. The backend hop is that session, since ProxyClient connects in legacy mode and _ForwardingClientSession overrides only validate_tool_result. The exception leaves ProxyTool.run, and MCPBackendMiddleware._recover (code/deepagents_code/mcp_proxy.py) re-raises it because it is neither a disconnect nor a re-auth failure. The router’s tools/call handler in fastmcp/server/server.py logs “Invalid arguments for tool” and re-raises it. mcp shared/jsonrpc_dispatcher.py handler_exception_to_error_data turns any pydantic ValidationError into ErrorData(code=INVALID_PARAMS, message="Invalid request parameters", data=""), so the front FastMCPClient(router) session raises MCPError: Invalid request parameters with no pydantic text. That is not a ToolException, so the call ends without a ToolMessage, as for the outputSchema RuntimeError below.

Model path: content only, structuredContent parked on ToolMessage.artifact

langchain mcp/tools.py _convert_call_tool_result decides the split. It converts every block with tool_content = [_convert_content_block(block) for block in result.content], raises _MCPToolExecutionError(tool_content) when result.is_error, and otherwise sets artifact = MCPToolArtifact(structured_content=result.structured_content) when result.structured_content is not None. as_langchain_tool builds the StructuredTool with response_format="content_and_artifact", so langchain-core tools/base.py _format_output returns ToolMessage(content, artifact=artifact, ...). The model receives content. artifact is host state, and no provider request is built from it.

With both fields present the model gets the converted content blocks and nothing from structuredContent. With content: [] and structuredContent present the result is a ToolMessage with empty content and the artifact set, with no fallback to the structured value. The one substitution is NemotronToolCallShim._normalize in deepagents/deepagents/profiles/harness/_nvidia_nemotron_3_ultra.py, which replaces empty content with "(empty tool result)" for the Nemotron 3 Ultra model specs it registers. On an isError result the exception is raised before the artifact is built, _handle_mcp_tool_error returns the converted blocks (or str(error) when there are none) as a status="error" message, and structuredContent is dropped.

Whether the text mirrors structuredContent or differs from it, the model gets the same converted content blocks. No step compares the two fields or removes a duplicate. structuredContent is not serialized into the provider request in any form: MCPToolArtifact holds the parsed value as structured_content. The str(error) text for an isError result with no content blocks is “The MCP tool reported an error with empty content.”, from _summarize_tool_error in langchain mcp/tools.py. Non-text blocks do not change which field reaches the model, and image and file blocks stay in content next to the artifact.

annotations.audience is not read on the model path. _convert_content_block reads only the block type, text, data, URI and MIME type, so a block annotated audience: ["user"] reaches the model like any other block. A search for audience returns no matches in langchain mcp/ or in non-test files under libs/. The only annotations read in either is the tool-level Tool.annotations, copied into tool metadata by _tool_metadata and by _build_mcp_tool in code/deepagents_code/mcp_tools.py.

_convert_content_block maps TextContent to a text block and ImageContent to a base64 image block. ResourceLink becomes a URL image block when its MIME type starts with image/ and a URL file block otherwise. EmbeddedResource becomes a text block for text contents, and a base64 image or file block for blobs. AudioContent raises NotImplementedError. That is not a ToolException, so handle_tool_error does not run, mcp_tool_middleware in code/deepagents_code/mcp_middleware.py re-raises it, and langgraph-prebuilt prebuilt/tool_node.py _default_handle_tool_errors re-raises anything other than ToolInvocationError, so the call ends without a ToolMessage. The image and file blocks are then converted by whichever LangChain provider package is installed; those converters are outside this repository.

outputSchema: never read by deepagents, validated by the mcp SDK on the router session, raised out of the tool call

output_schema and outputSchema have no occurrences under libs/ outside tests. _build_server in mcp_tools.py records only input_schema in MCPToolInfo. FastMCP copies the backend schema into the proxy in ProxyTool.from_mcp_tool (output_schema=mcp_tool.output_schema). mcp client/session.py ClientSession.call_tool runs await self.validate_tool_result(name, result) when not result.is_error, which raises RuntimeError(f"Tool {name} has an output schema but did not return structured content") or RuntimeError(f"Invalid structured content returned by tool {name}: {error}"). The backend session does not run that check: ProxyClient.__init__ in fastmcp/server/providers/proxy.py applies PROXY_TRANSPORT_OPTIONS, whose session_class is _ForwardingClientSession, and its validate_tool_result returns None. The front FastMCPClient(router) session is a plain ClientSession and runs the SDK check on successful results against the schema the proxy lists. The RuntimeError leaves client.call_tool in the langchain coroutine before _convert_call_tool_result runs. That is not a ToolException, so handle_tool_error does not run, mcp_tool_middleware re-raises it, and _default_handle_tool_errors re-raises it, so the call ends without a ToolMessage. FastMCP’s own _parse_call_tool_result (fastmcp/client/mixins/tools.py) builds data with a pydantic TypeAdapter and only logs on failure; langchain does not read data.

The schema does not reach the model. as_langchain_tool builds the StructuredTool from tool.name, tool.description and args_schema=_normalize_mcp_schema(tool.input_schema), and nothing in langchain mcp/tools.py reads output_schema or appends it to the description.

Other paths: hooks see the artifact, PTC and ACP see content only

code/deepagents_code/hooks/models/domain.py PostToolUseEvent.from_tool_result sends result.model_dump(mode="json"), the whole ToolMessage including artifact, as tool_response (hooks/projection.py _project_post_tool_use). A hook’s additionalContext is appended to the message content as a text block by _merge_tool_message_content in hooks/server_middleware.py, which reaches the model. hooks/reducer.py _merge_post_tool_use parses updatedMCPToolOutput and calls _diagnose_unsupported_field(state, handler_id, "updatedMCPToolOutput"), which logs “is not supported and was ignored”. _tool_result_error reads message.artifact only for the execute tool’s exit_code. It returns the message text for a ToolMessage with status="error", which is what an isError result becomes, so _maybe_post_tool_use sends a PostToolUseFailureEvent carrying call and error and no tool_response, and PostToolUse does not fire.

The js_eval interpreter (partners/quickjs/langchain_quickjs/_repl.py, wired by CostAwareCodeInterpreterMiddleware in code/deepagents_code/agent.py) can call MCP tools when interpreter_ptc names them or is "all"; the "safe" preset is {"read_file", "glob", "grep"} (code/deepagents_code/config.py). _ainvoke_tool_on_outer_loop calls tool.arun(args, ..., tool_call_id=(tool_call_id if _tool_uses_injected_tool_call_id(tool) else None)). MCP tools declare no injected id, and _format_output returns bare content when tool_call_id is None, so JS receives the content block list from coerce_tool_output_for_ptc (_format.py) and no artifact. These calls go to tool.arun directly, outside the agent middleware chain. The model sees the js_eval output, where _repl.py renders the script’s return value with stringify and format_outcome (_format.py) wraps it in <result> tags, so a returned block list reads as an unquoted-key literal such as [{type: "text", text: "..."}].

deepagents/deepagents/middleware/_message_eviction.py _build_evicted_tool_message, used by FilesystemMiddleware offload and SummarizationMiddleware clipping, replaces text with a preview and keeps artifact=message.artifact; this is the only line in the repository that reads an MCP artifact back. The TUI renders format_tool_message_content(message.content) (code/deepagents_code/tool_display.py, called from tui/textual_adapter.py). The ACP server in acp/deepagents_acp/server.py forwards str(content) in update_tool_call. It stores ACP-supplied mcp_servers in _session_mcp_servers and reads them nowhere else in that file. Neither deepagents nor langchain.mcp reads result _meta; _tool_metadata copies tool-level _meta into tool.metadata["mcp"]["tool"] and nothing reads it.

There is no MCP Apps support. Searches under libs/ and langchain mcp/ for ui://, resourceUri, io.modelcontextprotocol/ui, visibility and a "ui" key in tool _meta find nothing MCP-related, so no view receives either field and _meta.ui.visibility is not read. No switch changes which field the model gets. as_langchain_tool(tool, client) takes no result options, response_format="content_and_artifact" is fixed, and no non-test file under libs/ mentions structured_content or structuredContent.

Protocol revision: initialize on the backend hop, negotiated by the SDK in auto mode on the router hop

deepagents pins no protocol string. StatefulProxyClient(transport=..., log_handler=...) and FastMCPClient(router) are constructed without mode. ProxyClient.__init__ runs kwargs.setdefault("mode", "legacy"), so each backend connects through initialize, and create_proxy(connected[name]) passes a Client, so FastMCP’s mirroring of the front connection’s era does not apply. FastMCPClient(router) gets mode: ConnectMode = "auto" from FastMCP Client.__init__, and _negotiate calls the SDK’s negotiate_auto (mcp/client/_probe.py). That probes server/discover at LATEST_MODERN_VERSION (“2026-07-28”) and falls back to initialize at LATEST_HANDSHAKE_VERSION (“2025-11-25”), from KNOWN_PROTOCOL_VERSIONS in mcp-types mcp_types/version.py. ProxyTool.run branches on client.protocol_version in MODERN_PROTOCOL_VERSIONS, so backends take the client.call_tool_mcp path.

Upstream history: the artifact rule came from langchain-mcp-adapters and was ported into langchain.mcp

deepagents-code took the rule over in langchain-ai/deepagents#5922, merged 2026-09-18, which moved MCP onto FastMCP and langchain.mcp and removed langchain-mcp-adapters. Its body says tools are converted "through langchain.mcp" and does not discuss structuredContent. langchain.mcp arrived in langchain-ai/langchain#39939, merged 2026-09-03: "Tool results are ported from langchain-mcp-adapters, so a call reaches a model in the same shape either way. Results become LangChain content blocks (audio raises NotImplementedError); structured content becomes an MCPToolArtifact; args_schema is the tool’s input_schema." The module docstring of mcp/tools.py says the same.

The artifact rule itself came from langchain-ai/langchain-mcp-adapters#379, merged 2025-12-02, which closed issue #283. The issue reported that the adapter "is ignoring the structuredContent field from MCP CallToolResult responses, causing loss of structured data“. The PR body: ”We introduce a new MCPToolArtifact type that contains structured_output from the MCP tool, if available.“ On content it says non-text blocks ”used to“ go into the artifact and ”This content is intended to be in the chat history (images, files), so it makes more sense for it to be in content." Neither the PR body nor the issue thread gives a reason for keeping structuredContent out of the model’s content. A maintainer comment on the issue (2025-11-24) offered an interceptor workaround that put structuredContent in the artifact and noted that “the interceptor pattern allows you to also directly update langgraph state via Command()”. An earlier community PR, #300, closed unmerged on 2025-12-01, proposed the same content_and_artifact split.

At the time of reading, langchain-ai/langchain#41566 (closed unmerged on 2026-11-06) would have kept structuredContent as the artifact on isError results, and langchain-ai/langchain#40722 (open) would add MCP Apps tool visibility to langchain.mcp. The clone is a depth-1 checkout, so git log and git blame show only a93aed4 and could not trace the deepagents files further. Searches of langchain-ai/deepagents PRs and issues for structuredContent, structured_content and artifact mcp returned nothing.

Quirks

The backend hop validates results against the 2025-11-25 wire model, whose CallToolResult.structured_content is dict[str, Any] | None (mcp_types/_v2025_11_25/__init__.py), so a backend that sends an array or scalar structuredContent fails that validation in ClientSession.send_request. FastMCP’s own CallToolResult dataclass also types structured_content as dict[str, Any] | None.

format_outcome in partners/quickjs/langchain_quickjs/_format.py truncates the js_eval result to max_result_chars and appends “… [truncated N chars]”. deepagents-code passes interpreter.max_result_chars, whose default is 4,000 (INTERPRETER_MAX_RESULT_CHARS_DEFAULT in code/deepagents_code/config_manifest.py), so an MCP result returned from a script is cut there.
