Ola’s MCP Tool Result Research

How pi-mono handles MCP tool results

which mcp tool result fields are used and how (clients)

Notes from reading the pi-mono source (clones/pi-mono, checked out at commit 8636e21, read on 2026-11-14). File references are relative to packages/ in the clone root. The MCP client lives in mcp/, the model-facing adapter in coding-agent/src/extensions/mcp/, and the script path in coding-agent/src/extensions/codemode/ and codemode/.

Entry: results enter through a hand-rolled client that keeps structuredContent as unknown

pi has its own MCP client, @earendil-works/pi-mcp version 1.5.2 (mcp/package.json). mcp/README.md states “It does not depend on the official MCP SDK or other pi packages”; only the OAuth code is adapted from the TypeScript SDK v1.29.0, which is why mcp/THIRD_PARTY_NOTICES/ carries that license. McpClient.callTool in mcp/src/client.ts sends tools/call and passes the raw JSON-RPC result through validateCallToolResult. That function checks only that content, if present, is an array, and defaults a missing content to []; its comment says "content is required by the spec, but servers that only return structuredContent omit it". The result type is CallToolResult in mcp/src/protocol/content.ts, with content: ContentBlock[], structuredContent?: unknown, isError?: boolean, and _meta. No field is dropped at this layer. The coding agent creates the client in coding-agent/src/extensions/mcp/runtime.ts with name: "pi" and wraps each listed tool with createMcpToolDefinition in coding-agent/src/extensions/mcp/tools.ts.

Model path: content blocks only, structuredContent used solely as a fallback

convertMcpResult in coding-agent/src/extensions/mcp/tools.ts decides what the model sees: result.content.length > 0 ? await toModelContent(server, result.content, options) : toLlmContent(result). When both fields are present, only the content blocks reach the model and structuredContent is not read on this path. When content is empty, or absent and defaulted to [], toLlmContent in mcp/src/protocol/content.ts pushes one text block holding JSON.stringify(result.structuredContent, null, 2). mcp/test/content.test.ts pins both cases, including arrays and null. The rule is the same whether the text mirrors the JSON or differs from it. No step compares the text with structuredContent or removes a duplicate, and a mirrored result reaches the model once, as the content text. A content array holding only non-text blocks (image, audio, resource) is non-empty, so structuredContent is not used for it. When structuredContent is used, content is empty and there are no non-text blocks to keep. A non-error result with empty content and no structuredContent gets no placeholder from the adapter: converted stays [], and the provider adapter in ai/src/api/ decides what is sent.

ContentAnnotations.audience is declared in mcp/src/protocol/content.ts, and no code reads it. A grep for audience in the .ts files under packages/ returns only that declaration. A block annotated audience: ["user"] is converted and reaches the model like any other block.

Non-text blocks are handled in blockToLlmContent (mcp/src/protocol/content.ts) and blockToContent (coding-agent/src/extensions/mcp/tools.ts). Image blocks pass through as images. Audio becomes the text [audio ${block.mimeType} omitted]. A resource_link becomes a text line naming the URI, title, mime type, size, and the read_mcp_resource tool when the server has readable resources. An embedded text resource becomes its text. An embedded blob with an image/ mime type becomes an image. Other blobs with a text-like mime type (isTextMimeType) are decoded as UTF-8; the rest are written to a temp file by saveToTempFile and replaced by [Binary resource ${uri} (${kind}) saved to ${path}]. limitMcpContent then cuts text over MCP_OUTPUT_MAX_BYTES (20 KB) in the middle and saves the full text to a file named in the result. An isError result with no text gets MCP tool ${server}/${tool} returned an error.

The converted blocks become AgentToolResult.content. ToolResultMessage in ai/src/types.ts has no structuredContent field, and createToolResultMessage in agent/src/agent-loop.ts copies only content, details, usage, and isError, so structured content never enters the transcript sent to a provider. agent/src/types.ts documents the field as "Not sent to the model; content remains the model-facing result."

outputSchema: carried through, never validated, rendered into script declarations

Tool.outputSchema? is part of the tools/list type in mcp/src/protocol/types.ts. The isTool guard in mcp/src/client.ts checks only name and inputSchema. No code validates structuredContent against outputSchema; the only schema validation in the loop is validateToolArguments on inputs (agent/src/agent-loop.ts). A structuredContent that does not match the declared schema is passed on unchanged, so there is no failure text. createMcpResultSchema in coding-agent/src/extensions/mcp/tools.ts wraps the server’s schema as the structuredContent property of a CallToolResult-shaped object schema, rewriting local $refs with relocateSchema, and uses {} when the tool declares none (“Servers may send structured content without declaring a schema for it, and it may be any JSON value”). That wrapped schema becomes the pi tool’s outputSchema. It is not sent to the provider: toToolDeclaration in ai/src/utils/transcript.ts copies only name, description, parameters, and constrainedSampling. It is used for prompt text in codemode: renderToolSignature in codemode/src/declarations.ts renders name(args: T): Promise<R> from it, and describeScriptCall in coding-agent/src/extensions/codemode/tool.ts appends "Codemode: tools.x(args) resolves to ..." to a direct tool’s description.

Other paths: codemode scripts receive the whole CallToolResult

convertMcpResult sets structuredContent: scriptResult, where scriptResult is the full CallToolResult minus _meta, untruncated. toScriptValue in coding-agent/src/extensions/codemode/execute.ts hands a script result.structuredContent whenever the tool declares an outputSchema, which every MCP tool does, so scripts see { content, structuredContent, isError } as the server sent them. A result without a content key reaches scripts with the content: [] that validateCallToolResult adds. isError results still resolve in scripts. Only the script’s own output reaches the model (coding-agent/src/extensions/codemode/tool.ts header). That output has its own limit: truncateOutput in coding-agent/src/extensions/codemode/execute.ts cuts the script’s text in the middle at DEFAULT_MAX_OUTPUT_TOKENS (10,000 tokens at four characters each, settable per script with max_output_tokens), so a large result a script prints is cut by this budget, not by MCP_OUTPUT_MAX_BYTES. Exposure (direct, codemode, deferred, hidden, mapped by toToolExposure) decides whether the model sees a declaration at all. A deferred tool is declared once tool_search (coding-agent/src/extensions/tool-search/tool.ts) activates it, “so the next model call declares them”, and from then on it is called directly and its result goes through convertMcpResult like a direct tool’s. No switch changes which field the model gets. The mcp.json keys that apply per server are enabled, exposure, and toolExposure (coding-agent/src/extensions/mcp/config.ts), which decide whether a tool is declared. outputSchema changes only what toScriptValue hands a script, and convertMcpResult applies the same rule to every result.

MCP Apps: pi does not render them. The McpClient options in coding-agent/src/extensions/mcp/runtime.ts set name, version, requestTimeoutMs, and roots, and declare no extensions capability. coding-agent/src/extensions/mcp/resources.ts leaves ui:// and profile=mcp-app resources out of listings (“they are user interfaces for hosts that render them”). No code reads _meta.ui: a grep for visibility in mcp/src/ and coding-agent/src/extensions/mcp/ returns nothing, so a tool marked app-only is registered by createMcpToolDefinition like any other.

Hooks: the tool_result extension event (ToolResultEventBase.structuredContent in coding-agent/src/core/extensions/types.ts) and afterToolCall in agent/src/agent-loop.ts can replace both fields; replacing content alone drops structuredContent. UI: renderResult in tools.ts shows getTextOutput(result) and details.fullOutputPath. _meta: no routing flag is read; the client writes _meta.progressToken on requests and the adapter strips _meta from script results. read_mcp_resource in coding-agent/src/extensions/mcp/resources.ts runs resources/read contents through the same toModelContent and sets structuredContent: { server, uri, contents }.

The phrase “changing result shapes” does not appear in the source. The closest statements are the toLlmContent comment “servers should, but do not always, mirror structured results as text”, the additionalProperties: true entry in createMcpResultSchema annotated “Fields newer protocol versions add”, the coding-agent/CHANGELOG.md fix for non-object structuredContent (#10416), and the codemode/CHANGELOG.md entry removing the shared CallToolResult<T> type in favour of spelling each result type out per tool.

Protocol revision: 2025-11-25 requested, three older revisions accepted

LATEST_PROTOCOL_VERSION = "2025-11-25" and SUPPORTED_PROTOCOL_VERSIONS (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05) are in mcp/src/protocol/types.ts. McpClient.connect sends this.options.protocolVersion ?? LATEST_PROTOCOL_VERSION and throws MCP server selected unsupported protocol version for anything outside the list. mcp/src/transports/streamable-http.ts sets the MCP-Protocol-Version header to the negotiated value. Comments in content.ts and client.ts cite “MCP 2026-07-28” for structured content being any JSON value, but that revision is not in the negotiated list.

Upstream history: the rule arrived with MCP support in one PR, with no recorded rationale beyond a code comment

The clone is shallow (one commit), so git log and git blame do not reach the history. github.com/badlogic/pi-mono redirects to earendil-works/pi. The MCP client, the adapter, and the content-first rule with the structuredContent fallback arrived together in earendil-works/pi#10040, squash-merged as 8562bcf66 on 2026-09-29 and released in 0.99.0 (coding-agent/CHANGELOG.md, mcp/CHANGELOG.md). mcp/src/protocol/content.ts and coding-agent/src/extensions/mcp/tools.ts at 8562bcf66, read with gh api, already hold the toLlmContent fallback and the result.content.length > 0 branch, with structuredContent typed as Record<string, unknown>. The PR body and commit message say of results only: "Tools can also return structuredContent with an outputSchema, and can report errors with isError instead of throwing.“ The PR has no review comments, and its 16 conversation comments do not discuss which field reaches the model. One comment from noctuid on 2026-09-27 notes ”Tool inputs are validated, but structuredContent is not validated against the outputSchema. Maybe there could be optional validation?" The only recorded reason for the fallback is the toLlmContent comment in mcp/src/protocol/content.ts: “servers should, but do not always, mirror structured results as text”.

Before built-in MCP support, #5364 (closed 2026-06-03) proposed falling back to pretty-printed structuredContent "when the standard content text blocks are missing or empty“. badlogic closed it with ”pi has no built-in mcp support. bring this up with the maintainer of the mcp extension you are using." The 1.2.0 entries in both changelogs cite #10416 for accepting non-object structuredContent. That issue is still open and asks for MCP 2026-07-28 support and to “Keep Pi’s existing result-envelope contract”. Searched: gh search issues and gh search prs for structuredContent, “structured content”, “mcp audience”, and “mcp apps” in earendil-works/pi, and every CHANGELOG.md under packages/.

Quirks

The empty-result placeholder differs by provider API. With no text and no images, openai-completions.ts, openai-responses-shared.ts, and mistral-conversations.ts in ai/src/api/ send (no tool output), while google-shared.ts sends an empty string and convertContentBlocks in anthropic-messages.ts joins no text into an empty string.

An unknown block type does not fail the result: blockToLlmContent in mcp/src/protocol/content.ts turns it into the text [unsupported MCP content ${type}].

The 20 KB cut reorders blocks. limitMcpContent in mcp/src/output-limit.ts joins every text block into one, keeps the first and last 10 KB around a …N chars truncated… marker, prefixes Warning: truncated output (original token count: N) and the line count, appends [Full output: <path> (read it with offset/limit)], and puts any images after that single block. The script result in structuredContent is not cut.
