Ola’s MCP Tool Result Research

An MCP tool result has two payload fields. What happens to these results when consumed by different agents?

which mcp tool result fields are used and how (clients)

Which tool result field reaches the model?

A tool result carries content, a required array of typed blocks (text, image, audio, resource), and optionally structuredContent. structuredContent can be any JSON value and it’s expected to match the tool’s outputSchema when one is included. The specification recommends that a server that returns structuredContent also serialize the same JSON into a text block in content, for backwards compatibility.

A client can have several possible consumers for one tool result. This might include the model’s context, a script the model wrote, a render for the user, an MCP App's view. Each may want a different shape, a different redaction, and a different amount of the same data.

Each implementer has a lot of decisions to make about how to use each field, including whether or not to pass it along to the LLM’s context. The protocol does specify an explicit audience signal, the audience annotation. This sits on individual content blocks, is advisory, and is not included for structuredContent. This means that today, a server author cannot tell from the result alone whether the model will see the JSON, the text mirror of the JSON, or both.

This page records what a sample of open source clients do with tool results based on analyzing their source code.

The validation it skips on purpose

The call goes through the SDK’s raw request rather than its typed callTool, and the comment above it says why. packages/api/src/mcp/MCPManager.ts:

// Deliberately use `request`: the typed wrapper also enforces the tool's output schema and

So a structuredContent value that does not match the declared outputSchema is never rejected here; the model sees the content text either way. Why this row moved, with the source

The August reading had one line deciding the model path: if (res.structuredContent !== undefined) return res.structuredContent;. The client now attaches a model-output mapper only to tools that declare an outputSchema, and that mapper prefers the text of content. packages/mcp/src/client/client.ts:

...(tool.outputSchema ? { toModelOutput: createStructuredToolToModelOutput() } : {}),

function createStructuredToolToModelOutput() {
  return output => {
    const modelText = extractModelTextFromToolContent(getMcpCallToolContent(output));
    if (modelText !== undefined) {
      return { type: 'text', value: modelText };
    }
    return { type: 'json', value: output };
  };
}

execute still returns structuredContent as the tool’s value, with the content blocks attached on a non-enumerable symbol so the mapper can read them without changing the return shape. A tool without a schema gets no mapper, so the AI SDK sends the structured value as JSON. Whether the server declared a schema is what decides which field the model sees, and this is the only client of the twenty where outputSchema does that.

The change came in through mastra-ai/mastra#20176, merged 2026-08-07, fixing issue #20168, which reported that the model received a large structured payload where it should receive the text of content. Both cite the specification’s description of the two fields. The PR body: "Per the MCP specification, content is the LLM-facing channel while structuredContent is intended for client/UI consumption." The costs named are tokens and the MCP Apps pattern of a short summary in content with the data in structuredContent. #27131, merged 2026-10-15, widened the text filter to embedded resource text after the GitHub MCP server added an outputSchema to its file tool and an agent could no longer read a file through mastra.

Why this row moved, with the source

In August the parser walked content and appended structuredContent as a trailing JSON text block, so both copies reached the model. That behaviour is now one of five modes on a constructor option, and the default drops content whenever the structured value is present. python/packages/core/agent_framework/_mcp.py:

tool_result_content: MCPToolResultContentMode = "structured_first",

elif mode == "content_first":
    if not result and structured_block is not None:
        result.append(structured_block)
elif mode == "structured_first":
    if structured_block is not None:
        result = [structured_block]

The other modes are content_first, content_only, structured_only and both. Image and audio blocks are dropped with the text under the default. An application that wants the August behaviour passes tool_result_content="both". This is the one client whose routing switch lives in its own constructor rather than in _meta or in what the server sent.

The option came in through microsoft/agent-framework#8274, merged 2026-09-15, fixing issue #7866, a report that the DeepWiki and MS Learn servers return the same payload in both fields and the model saw it twice. The first version of the PR preferred content. A reviewer asked for an explicit policy instead, because servers may also use the two fields as complementary data, and the maintainer who listed the five modes wrote that the default “should probably be to propagate from the most specific (structuredContent) to the more generic (content)”. The issue thread cites the MCP roadmap’s line that returning both fields “has confused server and client authors alike” and the deferral of SEP-2200 as the reason the specification gives no rule to follow.

Same client, different answer per model backend

The MCP tool dumps the whole CallToolResult to a dict with the wire key names (_dump_mcp_model in tools/mcp_tool/mcp_tool.py), and the Gemini backend sends that dict as the function response, structuredContent included. The Anthropic backend reformats function responses before sending them and keeps only the content list when it is non-empty. src/google/adk/models/anthropic_llm.py, _part_to_message_block:

if (
    "content" in response_data
    and isinstance(response_data["content"], list)
    and response_data["content"]
):
    content_items = []
    for item in response_data["content"]:
        if isinstance(item, dict):
            if item.get("type") == "text" and "text" in item:
                content_items.append(item["text"])
            else:
                content_items.append(str(item))

Only when content is empty does it fall back to json.dumps(response_data), which is when the structured value reaches Claude. The same agent therefore sits in the both-fields group on Gemini and in the content-first group on Anthropic.

The content branch was added by commit 1dd97f5b on 2025-11-17, an internal change with no pull request and no message body. The whole-dict dump came from commit 4df92638, whose message says the aim was that “what ADK runtime sees is identical to what is persisted in the session event list”. No issue or pull request in the repository discusses the Anthropic path dropping structuredContent. Issue #7073 raised the same Gemini-versus-Claude gap for dicts with a result key and left the MCP content branch out of scope on purpose.
